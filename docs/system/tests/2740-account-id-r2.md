Account-id rules finished here (rows in `1980-account-id-r1.md` updated): 1981 (R2 half: a moved record resolves at neither address even with a stale index), 1987, 1988 (a pre-claimed `login:{to}` is a retry; a left-over `login:{old}` signs nothing in), 1989, 1990 (two-step, active brand, Google link, feed and booking pointers follow; `carryFeedLogin`/`carryBookLogin`), 1992 (the Composio user id is keyed by scope and does not change), 1993 (the account keeps its key), 1996-1998, 1999 (R2 half: `wipeAccount` forgets the wishlist by id and address, source check).

Rulings:
- `ownerHasData` is kept, gated by `!OPAQUE_IDS`, not deleted (deviation from the "R2 enable" row): deleting it while the constant is off would let R1's copy path wipe an owner's work. It goes with R1's copy in the contract release after the flip.
- `addressBlocked` is not gated by the constant (L3 must hold if the constant is ever turned off again after accounts moved). With the constant off it finds nothing, at the cost of reads made side by side with the existing checks, plus one read in `createUser`.
- A legacy member record (`member:{login}`) keeps R1's copy when its address changes (spec: "Members unchanged").
- A partner's address is refused, including on a revert (a partner hijack is support's case).
- The revert always drops the Google link and ends every session; the person gets a reset token rather than keeping the old password.

Not pinned: push subscriptions keep the old login label after a move; a busy calendar lock during the carry leaves that link's `login` stale until the next sync; crash residue between the account write and the person row is finished by a retry, not by a sweep.

## Release step

**Expand** (rule 679), constant off. Rollback floor unchanged: nothing new is written while the constant is off (referral rows gain `id`, which older builds ignore; the wishlist key is the same bytes for every existing account; the console rows gain a field). The flip pull request later carries "rollback floor: R1" and "rollback floor: M1"; after the flip, a moved account cannot be served by a build below this one (no L3 guard). Preconditions for the flip, not for merging this branch: R1 live 7 days (from 2026-10-19, so on or after 2026-10-26), `scripts/account-ids.ts` reports 0 conflicts, and the Paymob or Geidea saved-card check of the spec's section 7 passes on staging.
