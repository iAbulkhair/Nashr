# Coverage: a connection's token is refreshed only under its own lock (rule 2192)

Status on 2026-10-18 on branch `claude/distracted-tharp-551077` (cut from `claude/api-platform-integrations-ce2972` 8efbadd4, local, not pushed). Rule 2192 is reserved by the Salla Easy Mode spec (`docs/superpowers/specs/2026-10-18-salla-easy-mode-design.md` section 8.2, branch `claude/salla-easy-mode-spec`, rules 2180-2199) and lands on its own first because it protects X today.

Before: `getFreshConnection` (`src/lib/connectors/fresh.ts`) tried the plain lock `connlock:{scope}:{provider}` 20 times, and when it never won it went on and refreshed anyway; its `finally` called plain `db.unlock`, which deletes whatever lock is there, including one another request took after this one's 30 s lapsed. X rotates its refresh token on every use and Salla revokes every token when one is used twice, so both paths spent a single-use refresh token twice.

| # | Rule | Verified today | First test to write |
|---|---|---|---|
| 2192 | `getFreshConnection` takes the refresh lock with `db.lockOwned` and releases it with `db.unlockOwned`, so it never frees another holder's lock. It never refreshes without the lock: after each 250 ms wait it re-reads the connection and returns it when the holder saved a token that is no longer due (null when the connection is gone, `ReconnectRequired` when it was marked); after 20 tries it throws `RefreshBusy` (message `busy`) and nothing was refreshed or sent. The connect route (`POST /api/connect/{provider}`, its catch and `ownerRefresh`) and the publish route (`publish_failed` whose cause is `RefreshBusy`) answer 503 `{ok:false, error:"busy"}` with `Retry-After: 5` (`BUSY_RETRY_S`); `mayHavePosted` counts `RefreshBusy` as not posted; `RefreshButton` and the Integrations page (`CONNECT_ERRORS.busy`, `src/lib/connect-errors.ts`) show "try again in a few seconds" | `tests/oauth-connect.test.ts` (rule 2192: busy holder means no refresh and the holder's lock stays; uses what the holder saved; a lapsed lock does not free the next holder's; the connect route's 503 with Retry-After), `tests/security-gates.test.ts` (`mayHavePosted(new RefreshBusy)`), `tests/composio-social.test.ts` (`refreshNote` busy, both languages), `tests/uiux-phase0.test.ts` (rule 976 now finds `busy` in the connect route and requires its message in both languages) | The publish route's 503 `busy` end to end (pinned only through `mayHavePosted` and the route's `instanceof` branch).
