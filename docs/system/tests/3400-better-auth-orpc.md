# Coverage: better-auth and oRPC behind AUTH_ENGINE (rules 3400-3434)

Status on 2026-10-23 on branch `claude/sup-foundation-migration`. Spec: `docs/superpowers/specs/2026-10-23-better-auth-orpc-migration.md`. Release step: **expand**. With `AUTH_ENGINE` unset nothing changes: no new route answers, no new cookie, key or field is written. Every test below runs with the switch off and on where the rule has two sides.

| # | Rule | Verified today | First test to write |
|---|---|---|---|
| 3400 | `AUTH_ENGINE=better-auth` turns the better-auth engine on; it is read at call time (`authEngine()` in src/lib/auth-engine.ts), so one build serves both engines and a rollback is one variable. Any other value, or none, is the legacy engine | `tests/better-auth-adapter.test.ts` (rule 3400) | none |
| 3401 | The engine also needs `BETTER_AUTH_SECRET` of 32 characters or more; a missing or short secret keeps the legacy engine (fails closed) and nothing logs the value | `tests/better-auth-adapter.test.ts` (rule 3401) | none |
| 3402 | better-auth 1.7.10, @orpc/server, @orpc/client and @orpc/tanstack-query 1.15.7 and @tanstack/react-query 5.104.3 are pinned exactly in package.json and package-lock.json, and the lockfile keeps the `@rolldown/binding-linux-*` entries (CLAUDE.md lockfile rule) | `tests/better-auth-adapter.test.ts` (rule 3402) | none |
| 3403 | The adapter's `user` is the login, projected and never written: by `email` through `getLogin` (the projected address must equal the asked one), by `id` through the person record and `getLogin` with the same pid. `emailVerified` is true, the password hash never appears; a query by any other field answers nobody | `tests/better-auth-adapter.test.ts` (rule 3403: owner, member, unknown, other spelling) | none |
| 3404 | The adapter's `account` rows are `credential` (the person's bcrypt hash, `accountId` = pid) when a hash exists, and `google` only when `googlesub:{login}` and `google:{sub}` name each other; a query without `userId` answers nothing | `tests/better-auth-adapter.test.ts` (rule 3404) | none |
| 3405 | `verification` rows live at `ba:verify:{sha256(identifier)}` (`globalKey.baVerify`) with a TTL from `expiresAt` (at most an hour), are never written already expired, and are consumed once with GETDEL; an id that is not a 64-hex hash builds no key | `tests/better-auth-adapter.test.ts` (rule 3405), `tests/key-registry.test.ts` (byte row) | none |
| 3406 | The adapter reads a `session` only by token and only when the record resolves as `currentUser` resolves it (`sessionForEngine` in src/lib/auth.ts): an impersonation, a session issued before `sessionsAfter`, an unverified owner read as nobody. | 3407 | The adapter writes a `session` only for a 64-hex token the session gate approved in this process within 30 s (src/lib/better-auth/approvals.ts), and writes it with `issueSession`, the body `createSession` runs: the same record keys, cookie and device entry. An approval is used once | `tests/better-auth-adapter.test.ts` (rule 3407) | none |
| 3408 | The adapter refuses every write better-auth has no business making: creating or editing users and accounts, refreshing a session | `tests/better-auth-adapter.test.ts` (rule 3408) | none |
| 3409 | A better-auth sign-out deletes the session record and its device entry, as `destroySession` does | `tests/better-auth-adapter.test.ts` (rule 3409) | none |
| 3410 | One session cookie: better-auth's endpoints read `thakeen_session` (the wrapper signs better-auth's internal `thakeen.session_token` from it with `BETTER_AUTH_SECRET` and ignores any better-auth cookie the browser sends) and every `Set-Cookie` better-auth answers is dropped. A better-auth sign-in writes the legacy record (`{email, at, pid?, acct?}`) and cookie through `issueSession`; `get-session` answers a legacy session exactly when `currentUser` resolves it; a session made while on survives the switch going off; `sign-out` drops the record, the device entry and the cookie | `tests/better-auth-server.test.ts` (rule 3410) | none |
| 3411 | The session gate (`databaseHooks.session.create.before`, src/lib/better-auth/gate.ts) runs `admitLogin`, the function the legacy sign-in runs: the same status and body for a wrong password, an unknown address, a suspension (with `until`), a member of an unverified owner, a paused member and two-step sign-in, which opens the same challenge and mints NO session (rule 1934). Any path but `/sign-in/email` and `/magic-link/verify`, or no endpoint, is refused; an unverified owner gets a session and `verify: true` as before | `tests/better-auth-server.test.ts` (rule 3411, both engines on the same fixtures) | none |
| 3412 | No session token, IP address, user agent, password hash or provider token in any better-auth answer; better-auth's own error bodies come back as the legacy codes only (`invalid`, `forbidden`, `slow_down`, `failed`, or a gate refusal's known fields) | `tests/better-auth-server.test.ts` (rule 3412) | none |
| 3413 | An allow-list of method and path in the route wrapper (`BA_ROUTES` in src/lib/better-auth/handler.ts): only `POST /sign-in/email`, `GET /get-session`, `POST /sign-out`, `GET /list-accounts` (plus the magic link of rule 3415).
