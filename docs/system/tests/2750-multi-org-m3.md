# Coverage: multi-workspace M3, the lifecycle release (rules 2750-2759)

Status on 2026-10-21 on branch `claude/wave3a-m3-lifecycle`: the spec's "M3 lifecycle" row (`docs/specs/2026-10-18-multi-org.md` sections 9, 11, 13, 14 and 16; plan `docs/superpowers/plans/2026-10-21-multi-org-m3.md`). Everything user-facing is behind `MULTI_ORG` (false in production): every new route answers 404 with it off (`tests/multi-org-flag-off.test.ts`). Release step: expand. New keys `xfer:{aid}` (7 days) and `invitesfor:{email}` (7 days) are written only with the flag on; old code never reads them. Rollback: M2. One change is live with the flag off: a session written before R1 is now refused for a suspended person (rule 2131, pre-R1 half; nothing in production writes a person suspension yet, so nothing changes until one is written). One new account field, `ownerSince` (ISO, written by the accept only, so only with the flag on; an older build ignores it). One new script, `scripts/multi-org-links.ts` (rule 2756), the precondition of M4, run by hand from the live M3 build on the founder's yes. Rules 2750-2758 are used; 2759 is free.

The spec's own rules for this release live in `docs/system/tests/2110-multi-org.md` (2124, 2127, 2128, 2129, 2130, 2131); the rows below are the M3 build's own.

Rulings (fail-closed where the spec is silent):
- Only an `a_` account owned by a `p_` person, offered to a `p_` admin, transfers. Until M4/S2 a legacy account record is also its owner's credential record, so moving it would strand or delete credentials.
- A partner account never transfers: its commission and bank details are keyed by the account and must not follow it to a new owner.
- No mail configured means no offer: the mailed link is the only copy of the token. A send failure withdraws the offer.
- The owner's Reem calendar links (their own calendar) are revoked after a transfer.
- The cap failure keeps the offer so the person can free a slot and accept; any other change voids it.
- The "Team log tab" is a section of the Members page (owner and admin), read on demand.
- Delete person takes every membership the person has a row in, paused ones included (`heldAnywhere`), not only the live ones `heldAccounts` lists: a paused membership left behind would name a deleted person.
- Delete person keeps the waiting invitations themselves (they belong to the inviting accounts and expire in 7 days); only the address's inbox index goes.
- The people view is behind `MULTI_ORG` like every other M3 route (404 while off, after the console gate), so the release changes nothing live; the workspace view stays the console's lookup until the flag flips.
- The people view lists accounts with a membership row, paused ones included (`heldAnywhere`, as delete person), not only the live ones `heldAccounts` lists: the console must see what the person holds, and `paused` says which are paused. The last sign-in is the person's (devices are kept per sign-in address), not per account.
- The pre-R1 person-suspension check (rule 2131) is not behind `MULTI_ORG`: it is a security check every resolver already makes, and it changes nothing live while no person row says suspended. It adds one command to the first round of a pre-R1 session, not a round; a resolved person other than the session's id (an owner record with a different `ownerPid`) costs one more read.
- A card is the owner's at the time of the checkout (rule 2757): `ownerSince` is compared with our own intent's `createdAt` (every intent has written one since billing began), so the check is the same for any provider that saves a card through the shared path.
- The links script (rule 2756) stamps a link only when M3's own check answers the same before and after, so it never brings a dead link back nor kills a live one; a link it leaves is counted (exit 1) for the founder to look at before M4. It leaves the legacy pointers and the legacy brand key to M4's S2.
- The rail switcher asks for the invitations inbox only when it is opened (once per page), not on every workspace change; a person with one workspace sees no switcher, so the rail no longer hints at waiting invitations for them (the workspaces page and the mail still do).
- A person whose login has no password (Google sign-in only) is told to set one with "Forgot password" before deleting the login or offering a transfer.
- A deleted person's `trialUsedAt` goes with the row. A person who used a trial owned an account, which must be deleted first; account deletion already frees the address the same way, so this adds no new path to a second trial.
