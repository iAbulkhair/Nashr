Of the last 100 runs, 84 passed, 8 were cancelled, 5 failed and 4 were re-run attempts, over 41 branches (2.4 runs each).

- Green reuse: a reused run is checkout with full history, the key, the lookup, Scope and the secret scan, about 1 minute against 16-19. It fires on a re-run of a green run, a reopened PR, `gh pr ready` on a tree that already passed, and above all on "merge main into the PR right before it is merged" (CLAUDE.md, rule 772) when main has not moved since the PR's last full run: the merge commit's tree is then the tree GitHub already checked. Saving: 15-18 minutes each time it fires.
- Affected unit tests: replayed on the last 16 merged pull requests (`git diff` of each merge against its first parent, run through the script on today's tree), 8 gave `all` (7 touch `src/lib/keys.ts`, which most features do, one the lockfile) and the others selected 85, 101, 118, 258, 267, 274, 301 and 303 of 347 files. About 72 files (the folder readers) always run. Locally the 102 files of PR #400's change ran in 57 s against 106-164 s for the whole suite (348 files, `npm run check` on 2026-10-20); scaled to CI's times that is roughly 2 minutes on a small change instead of about 5 minutes, and nothing saved on a change that reaches a hub module.
- Per pull request, at the CLAUDE.md rhythm (one or two draft pushes, one ready run, the main merge before the merge): 15-18 minutes when the main merge is reused, plus up to about 3 minutes per draft push on a small change. Roughly a third of a PR's minutes when the reuse fires, 0-15% when it does not. These are estimates from the measured step times; read the real figures off the first runs (PR body).

## Notes

- A cache saved by a pull request is read only by that pull request's later runs (and caches of its base branch, but `main` runs no CI, rule 988). So a record never crosses pull requests: the release PR into `production` gets no reuse from the PRs it carries, and always runs in full.
- The tree of the merge commit already holds `ci.yml` and the script; their hash is named in the key as well, so the key says what it depends on.
- A reused run still runs the secret scan, because the scan reads the PR's commits, not its tree: a new commit can carry a secret that a later commit deleted.
- Nothing stored changes shape. Release step: none (rule 679 not involved). No environment variable is added. The deploy path (Hostinger from `production`) is not touched.

## Not pinned

- That `actions/cache/restore` sets `cache-hit` to `true` only on an exact key match, and that a PR's cache serves only that PR, is GitHub's behaviour, read off the first runs, not a unit test.
- A draft can miss a unit test that reads a file through a path built at run time outside a template (string concatenation, `path.join` of separate parts) without reading a folder; the ready run runs every test before the merge, so the gap is a draft's only.
