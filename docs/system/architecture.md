## 1. Summary

Nashr is a single Next.js 16 app-router application (TypeScript, React server components, no separate backend) deployed on Vercel. It serves a bilingual (Arabic default, English) marketing site and an authenticated app under `/{lang}/app` in which a small-business owner, and since 2026-09-29 the admins and members the owner invites into the account, talk to eight AI agents (Noor marketing, Sami sales, Razan finance, Faris growth, Dana reporting, Majed executive, Layan product, Reem secretary; `src/lib/agents.ts`). Seven of them produce content "tasks"; Reem owns no task type and keeps the owner's own to-do list instead (`src/lib/secretary.ts`), for free. Agents call Anthropic models through `@anthropic-ai/sdk`, produce content "tasks" that land in an approval inbox, and can publish approved items to third-party platforms through connectors. All state lives in one Upstash Redis database reached through a thin adapter (`src/lib/db.ts`); when no Redis credentials are present the adapter silently falls back to a process-local in-memory `Map` (`memory`, `src/lib/db.ts:183`). There is no SQL database, no queue and no background worker: long work runs inside the request (route `maxDuration` up to 300 s), after the response via Next `after()` (`judgeLater`, `src/lib/judge.ts:192`, and the opportunistic media sweep `maybeSweep` in `src/lib/media/jobs.ts`), or in six Vercel cron jobs and one Upstash QStash schedule (Reem's tick, `/api/cron/secretary`, since 2026-09-30). Images and video come from fal.ai, kie.ai and Higgsfield and are copied to a Vercel Blob store (section 4(e)). Usage is metered in credits held on the owner's user record, shared by everyone in the account, and, since 2026-10-01, chat in messages: a monthly allowance per plan for the whole account, past which chat pauses unless the owner chose to continue on credits (`src/lib/chat-allowance.ts`, section 4(c)); who may do what inside an account is one role table (`src/lib/roles.ts`). The same agent capabilities are exposed to external AI clients through an MCP endpoint (`/api/mcp`) protected by personal bearer tokens or by a built-in minimal OAuth 2.1 authorization server; through it an owner's own Claude or ChatGPT subscription can also read the brand rules, check a draft and save it into the approval inbox without spending credits (`save_draft`, `src/lib/external-drafts.ts`; action `drafts`).

## 4. Request lifecycles

### (a) Marketing page
1. Browser requests `/`. `proxy.ts:19` redirects to `/{lang}`. Other marketing paths do not match the proxy matcher and go straight to the route.
2. `src/app/[lang]/layout.tsx` and the page render on the server from static dictionaries. No session lookup, no Redis access.
3. Public forms call `/api/support`, `/api/affiliates`, `/api/tools/{tool}` from the browser. Only the tools route calls a model (anonymous limit 5 per IP per day, `api/tools/[tool]/route.ts:25-26`).

### (b) Authenticated app page
1. Request to `/{lang}/app/...` matches the proxy, which sets `x-pathname` (`proxy.ts:27`).
2. `app/layout.tsx` calls `currentUser()`, which resolves the session to the ACCOUNT, the owner's `User`, with `actor`, `brandId` and `scope` set, or `null` (section 4(f)).
3. Anonymous and not a public path: redirect to `/{lang}/app/login` (`layout.tsx:26`). The redirect is skipped when `x-pathname` is empty.
4. Each page repeats its own guard (`currentUser()` then `redirect`) and reads data with `sc(u)` or, on several pages, `u.email` (see `permissions.md` section 2).
5. Client components then call JSON APIs with the same cookie.

### (c) Streaming chat turn with a tool call that generates content
1. `ChatPanel` posts `{text, conv, agent, stream:true}` to `POST /api/chat` with header `x-lang` (`src/components/app/ChatPanel.tsx:482`).
2. Route checks `currentUser()` (`api/chat/route.ts:28`), trims text to 4000 chars (`:31`, 400 `empty` when nothing is left), validates `agent` with `isAgentId`. Then, before anything is saved or a stream is opened: the per-account burst limit (`chatAllowed`, `:37`: 40 an hour and 200 a day, `rate:chat:h:{email}` and `rate:chat:d:{email}`; 429 `slow_down`), and since 2026-10-01 the plan's monthly chat allowance (`reserveChatTurn`, `:38`, `src/lib/chat-allowance.ts`): the message is counted on the account's counter with INCRBY; past the allowance it is taken back and the answer is 402 `{error: "chat_allowance", chat, credits}` (paused), unless the owner of a paid plan turned "continue on credits" on and the balance is at least `chatOverflowHold()` (5 credits, the most one message can cost), in which case the message goes ahead with nothing taken from the balance (the turn's own tools may spend it), or 402 `chat_credits` when the balance is below that. Only then it opens a `ReadableStream` SSE response with a 10 s `: ping` heartbeat (`:59`) and runs the turn through `runChatTurn` (`:61`), which settles it on every path.
3. `chat()` (`src/lib/chat.ts:305`): takes the turn's deadline first (`:307`, `deadlineFor(CHAT_MAX_DURATION_S)` = start + 285 s, since the route passes none), pushes the user message to `chat:{scope}[:{conv}]`, loads brand, this agent's preferences (`listPreferencesFor`), memory files, file names, connections, the thread (sent to the model through the history guard, `:337`, since 2026-10-01: `trimHistory` keeps the newest 16 messages that fit 24,000 characters, each cut to 6,000, a thread that starts with the first-run onboarding's assistant messages as it is, and `fitFirstCall` then drops the oldest until the first call has at least 4,000 output tokens) and the agent's recent feedback (`feedbackFor` with chat thumbs, in the uncached block) and, since 2026-09-30, the handoff notes other agents left for this one (`handoffNotesFor`, passed to `system` as the `handoffBlock` data block, uncached) in one `Promise.all` (`:329`), builds the system prompt (`system`, `:200`, called at `:331`; its uncached block starts with `nowLine`: the current date and time in the brand's zone), and, for each of at most `CHAT_MAX_CALLS` (5) calls, first works out its `max_tokens` (since 2026-10-01: the first call's from `fitFirstCall`, every later call's from `nextMaxTokens`, `:346`: what is left of the $0.35 per-message ceiling `CHAT_TURN_MAX_USD` after what the turn already cost and an upper estimate of this call's input, at most 8,000; below 2,048 no call is made and the turn ends with `CAPPED_REPLY`, or, when even the first call has no room, with `LARGE_REPLY`, which says the workspace is too large for one message and is not counted), then calls `client.messages.stream` with `CHAT_MODEL` (`claude-opus-5`) and the fifteen tools (`:351`; the nine content tools, Reem's five free to-do tools (four since 2026-09-29, `agenda_next` added on 2026-09-30) and, since 2026-09-30, the agents' handoff note `handoff_note` (a note that runs nothing, refused over MCP; not Majed's handoffs), all offered to every agent like the others; Majed's turns add `propose_handoff`, `toolsFor`; since main's security gates were merged in, the memory files sit in one fenced `workspace_files` block). Usage is metered per agent (`:355`), and each call's cost is added to the turn's total, which the route reads as `ChatTurn.usd` and never sends to the browser (`runChatTurn` strips it). A call the model ended at `max_tokens` (`:357`) is never acted on: its tool calls do not run, and its text is kept with `CUT_NOTE`.
4. The model returns a `tool_use` for `generate_content` or `draft_items`. `runTool` (`:486`, with the turn's deadline) first refuses, for `draft_items`, any type outside `DRAFT_TYPES` in code (`isDraftType`, `chat.ts:527`, since 2026-09-30, rule 250) before any read or charge, then hands the batch to `generateBatch` (with that deadline, which bounds the batch's cross-agent review) (`src/lib/generate-batch.ts`, `flows.md` 8.13, which also refuses a small ask of any other type): requires a brand, loads governance, rejects expired trials, `charge(user.email, cost, {scope, agent: agentForTask(type), cap: gov.agentCaps[agent]})` under `lock:user:{email}` (`credits.ts:72`), calls `generate()` (`noor.ts:173`: Opus generation, then Sonnet reviewer `critique`, optional dash stripping, then the cross-agent review when the type has reviewers and `gov.crossReview` is on). At the agent's monthly cap the tool returns a sentence and pushes `limit:agent_cap` (`batchRefused`, `chat.ts:452`), and the reply carries `limit: "agent_cap"`. On a thrown error the credits are refunded with the charge's receipt, which also lowers the agent's counter, and the error becomes an `is_error` tool result. A `generate_image` call renders against the same deadline and starts nothing with less than 60 s of it left (`CHAT_RENDER_MIN_MS`, `:713`); its charge goes through `startMedia` with the item's owning agent and cap, like the image route.
5. Each item becomes a task in `taskFromItem` with the status `initialStatus` gives on the item's type, channel, title and body (`approved` when `gov.autoApprove[type]`, no brand rule is broken, an unfilled placeholder included, and no reviewing agent flagged it, else `pending`), and the batch is saved together (`Promise.all`) as `task:{scope}:{id}`, ids pushed to `tasks:{scope}`. `judgeLater` schedules scoring after the response (`judge.ts:192`), which later writes `quality` on the task through `updateTask` (`judge.ts:145`, on the task as stored then; an automatic fail sends an item only auto-approval passed back to `pending`) and may push a notification.
6. Tool result goes back to the model (up to 5 calls, each within what is left of the ceiling). The final text is pushed to history with `items` cards (and, in Majed's turns, the handoff card, whose proposal is marked shown only after that push). Since 2026-10-01 the turn is then settled (`settleChatTurn` in `chat-allowance.ts`): a message inside the allowance stays counted; one that threw, made no model call or cost nothing (paused, mock) is given back; an over-allowance message is billed after the reply its metered cost at the floor rate, at most `chatOverflowHold()` (5) credits and at most what the balance still holds, the remainder under one credit carried (`settleChatOverflow`, `credits.ts`), and the credits billed are added to `usage:{email}:{YYYY-MM}:chat_cred`; a failed one is not billed. When the loop ends without a closing answer, a limit a tool hit still raises its dialog (`withLimit`). The reply is sent as `{type:"message", message, credits, limit, chat, charged}` (`api/chat/route.ts:64`): `chat` the account's `ChatStatus` after the turn, `charged` the credits this message cost (0 inside the allowance). `track(email,"chat")` and `touchConversation` run before the final event.
7. If the client disconnects, work continues and the reply is still saved (`api/chat/route.ts:57`), and the turn is settled the same way.

### (d) Cron run
1. Vercel Cron issues `GET /api/cron/{daily|weekly|golden|media|routines|evening}` with `Authorization: Bearer $CRON_SECRET` (Reem's tick, `POST /api/cron/secretary`, comes from Upstash QStash instead; section 2.6).
2. Route compares the bearer to the env value with `sameSecret` (`cron/daily/route.ts:125`, `cron/weekly/route.ts:15`, `cron/golden/route.ts:12`, `cron/media/route.ts:17`, `cron/routines/route.ts:34`, `cron/evening/route.ts:25`); 401 otherwise or when the variable is unset.
3. `allUsers()` (`schedule.ts:211`, the `users` of `dailyRoster`, `:192`) expands every email in `users:all` into one `User` per active brand with `scope` set, skipping `suspended` accounts. The daily cron also takes `dailyRoster`'s `idle` scopes (archived brands, suspended accounts) and runs only Reem's purge there (`purgeIdle`). The media cron does not fan out per user: it reads the open job sets.
4. Daily: `renewIfDue`, `sweepOnboardHolds` (once per account, on its default brand's entry, since 2026-09-30), `secretaryDaily`, nudge email, `runLifecycle`, `runDaily`, `followUps`, optional brief email; for an idle scope, only `purgeIdle`. Weekly: `runWeekly` per scope, charging credits and refunding on failure. Golden: `runGolden("cron")` under `golden:lock`. Media: `sweepMedia` (section (e), step 6). Routines: `dueRoutines` turns the users into (scope, routine) items that are on and due, and `runRoutine` runs each, charging the owning agent and refunding on failure.
5. JSON summary is returned; weekly returns `runCronBatch`'s report, whose `results` are keyed by `u.scope ?? u.email` (`cron/weekly/route.ts:17,20`); media returns `{open, advanced, done, failed, dropped, skipped}`.

### (e) Media render (image or video)
1. `POST /api/tasks/{id}/image {model?}` or `POST /api/tasks/{id}/video {model}` (`maxDuration = 120`). One deadline for the whole request, `deadlineFor(120)` = start + 105 s (`src/lib/media/keys.ts`); every step gets `min(its own maximum, time left)`. `currentUser` (401; any role), then `getTask(sc(u), id)` and `getBrand(sc(u))` (404).
2. `renderImage` / `renderVideo` (`src/lib/media/start.ts`) refuse before any charge: trial ended (402 `trial_over`), a model id that is not a catalogue id of that kind (400 `bad_model`; the image route defaults to `img-fast`, the video route has no default), a task type outside `IMAGE_TYPES` / `VIDEO_TYPES` (400 `wrong_type`), a trial account asking for a video model outside `TRIAL_VIDEO_MODELS` (402 `plan_required`), a model that is not available (`modelAvailable`: provider keys, the Blob store for kie and Higgsfield, `MEDIA_MODELS_ON`, not in `media:off`; 409 `model_unavailable`, except `img-fast`, which falls back to the uncharged placeholder card), and Photo to motion without our own image (409 `needs_image`). The placeholder card is written through `updateTask` on the task as stored, and only while it has no artwork: an item that already has a generated image, or gets one while the placeholder waits for the task lock, keeps it and the answer is 409 `model_unavailable` with nothing charged (`src/lib/media/start.ts:63-68`); one that finishes after the card was written replaces it, since the card leaves `task.mediaJob` alone.
3. `startMedia` (`src/lib/media/jobs.ts`): the owning agent's monthly cap and the balance pre-check (402 `agent_cap` / `no_credits`), flight lock `mflight` (409 `in_progress` with the running job), account limits (429 `too_many`), the trial video marker (402 `trial_video_used`), the kie create throttle or Higgsfield admission (429 `busy` / `one_open`), then `charge` with the item's owning agent and its cap (`flows.md` section 8 steps 9 and 12). The job is saved `queued` together with its open-set member and `task.mediaJob[kind]` (through `updateTask`) in one round whose three writes all settle; a failure there refunds at once through `refundOnce` (502 `media_failed` with the balance), and if that refund fails too the job, its member and the pointer are written again, the flight lock stays held and the answer is 502 `media_pending`, so the next poll or sweep ends the job `submit_lost` with the refund. Then the prompt (Sonnet, at most 20 s, or the fixed template) and one submit, never retried, under the job lock.
4. fal answers in the request: the image is copied to Blob (or hot-linked), the task gets it, 200. kie and Higgsfield answer a task id: the job becomes `running` with its `mjobref` pointer, 202, and the inbox polls. A submit refused, failed or out of time fails the job and refunds it once.
5. `GET /api/media/{jobId}` (`maxDuration = 120`; any role): `getJob(sc(u), jobId)` (404 for another account's id, no provider call), 120 polls per minute per account, then `advance`: at most one provider status call per job per 4 s (`mpoll`) under the job lock, a finished result copied through `safeFetch` (https on every hop) to Blob and written to the task (`updateTask`) before the job is saved `done`, a failure, a content refusal or a render past its max age (image 10 minutes, video 30) failed and refunded exactly once (`refundOnce` and its `mrefund` marker). A task write that fails at finalize leaves the job `running` with its result for the next pass, and `task.mediaApplied` keeps that retry from counting the render twice.
6. `POST /api/media/hook/{provider}` is a hint: per-IP limit, 64 KB body cap, the kie signature when `KIE_WEBHOOK_HMAC_KEY` is set; only the provider task id is read, the job is found through `mjobref` under its stored scope, and `advance` runs in `after()` without `force`, sharing the poll throttle. The start and poll routes schedule `maybeSweep` in `after()`, and `/api/cron/media` runs `sweepMedia` daily for whatever is left. flows.md section 23 has the details.

### (f) Resolving who is acting (2026-09-29)
1. `currentUser()` reads cookie `nashr_session` and `session:{token}` (`{email, at, imp?, kp?, as?}`; an `imp: "key"` session is checked against the current key and its key session first, one more read, and renews that key session at most once a minute), then, in one parallel round, `user:{login}`, `member:{login}` and `activebrand:{login}` (`resolveSession` in `src/lib/auth.ts`).
2. Owner login (the `user:` record exists; it wins should a member record exist too): `null` when suspended or when `at` predates `sessionsAfter`. Otherwise the record itself, `scope = scopeFor(owner, brandId)`, and actor `{kind:"owner", role:"owner"}`, or `{kind:"founder", role:"owner", impersonating: imp}` when the session carries `imp`.
3. Member login: `null` when the record is disabled, its role or `memberOf` is malformed, the session carries `imp`, or `at` predates the member's `sessionsAfter`. Then `user:{memberOf}` and `brands:{memberOf}` in one round: `null` when the owner is missing or suspended, when `at` predates the owner's `teamSessionsAfter`, or when the member's `acceptedAt` is earlier than the owner's `createdAt`. Otherwise the OWNER's record, with `brandId` = the member's own active brand when it is one of the owner's active brands (else `default`), `scope = scopeFor(owner, brandId)`, and actor `{kind:"member", email, name, lang, role}`.
4. Every caller keeps using `sc(u)`, `u.email` (the account) and `charge(u.email, ...)` unchanged; role checks read `u.actor` through `can()` and `forbid()` (`src/lib/roles.ts`), which refuse a `User` without an actor. `saveUser` strips `actor`, `scope` and `brandId`, so none is ever persisted.
5. MCP: `userFromBearer` resolves `mcptoken:{token}` to an owner account only (a member login's email is refused), with the owner's active brand and actor `{kind:"token", role:"owner"}`. The cron's `allUsers()` builds users without an actor.
6. Founder console: `adminActor(req)` answers `"key"` for the admin key (header `x-admin-key`) or a live key session (cookie `nashr_admin` = a random id; `adminKeySession()` looks up `adminsession:{sha256(id)}`, checks the stored fingerprint against the current key and both limits (15 minutes idle, 12 h at most), and renews it at most once a minute), the founder's email when `isFounderActor(currentUser())` (actor kind `owner`, actor email equal to the account email, in `ADMIN_EMAILS`), else `null`; `isAdmin` and `isAdminCookie` follow it.
