## 1. Summary

Nashr is a single Next.js 16 app-router application (TypeScript, React server components, no separate backend) deployed on Vercel. It serves a bilingual (Arabic default, English) marketing site and an authenticated app under `/{lang}/app` in which a small-business owner, and since 2026-09-29 the admins and members the owner invites into the account, talk to seven AI agents (Noor marketing, Sami sales, Razan finance, Faris growth, Dana reporting, Majed executive, Layan product; `src/lib/agents.ts:21`). Agents call Anthropic models through `@anthropic-ai/sdk`, produce content "tasks" that land in an approval inbox, and can publish approved items to third-party platforms through connectors. All state lives in one Upstash Redis database reached through a thin adapter (`src/lib/db.ts`); when no Redis credentials are present the adapter silently falls back to a process-local in-memory `Map` (`memory`, `src/lib/db.ts:107`). There is no SQL database, no queue and no background worker: long work runs inside the request (route `maxDuration` up to 300 s), after the response via Next `after()` (`judgeLater`, `src/lib/judge.ts:179`, and the opportunistic media sweep `maybeSweep` in `src/lib/media/jobs.ts`), or in five Vercel cron jobs. Images and video come from fal.ai, kie.ai and Higgsfield and are copied to a Vercel Blob store (section 4(e)). Usage is metered in credits held on the owner's user record, shared by everyone in the account; who may do what inside an account is one role table (`src/lib/roles.ts`). The same agent capabilities are exposed to external AI clients through an MCP endpoint (`/api/mcp`) protected by personal bearer tokens or by a built-in minimal OAuth 2.1 authorization server; through it an owner's own Claude or ChatGPT subscription can also read the brand rules, check a draft and save it into the approval inbox without spending credits (`save_draft`, `src/lib/external-drafts.ts`; action `drafts`).

Bounded lists (2026-09-18): `pushCapped` in `db.ts` trims on write. The chat page's "waiting for you" card is a separate 90-day recency view of the same queue and is deliberately not exhaustive.

## 4. Request lifecycles

### (a) Marketing page
1. Browser requests `/`. `proxy.ts:19` redirects to `/{lang}`. Other marketing paths do not match the proxy matcher and go straight to the route.
2. `src/app/[lang]/layout.tsx` and the page render on the server from static dictionaries. No session lookup, no Redis access.
3. Public forms call `/api/support`, `/api/affiliates`, `/api/tools/{tool}` from the browser. Only the tools route calls a model (anonymous limit 5 per IP per day, `api/tools/[tool]/route.ts:15-20`).

### (b) Authenticated app page
1. Request to `/{lang}/app/...` matches the proxy, which sets `x-pathname` (`proxy.ts:27`).
2. `app/layout.tsx` calls `currentUser()`, which resolves the session to the ACCOUNT, the owner's `User`, with `actor`, `brandId` and `scope` set, or `null` (section 4(f)).
3. Anonymous and not a public path: redirect to `/{lang}/app/login` (`layout.tsx:24`). The redirect is skipped when `x-pathname` is empty.
4. Each page repeats its own guard (`currentUser()` then `redirect`) and reads data with `sc(u)` or, on several pages, `u.email` (see `permissions.md` section 2).
5. Client components then call JSON APIs with the same cookie.

### (c) Streaming chat turn with a tool call that generates content
1. `ChatPanel` posts `{text, conv, agent, stream:true}` to `POST /api/chat` with header `x-lang` (`src/components/app/ChatPanel.tsx:169`).
2. Route checks `currentUser()` (`api/chat/route.ts:24`), trims text to 4000 chars, validates `agent` with `isAgentId`, opens a `ReadableStream` SSE response with a 10 s `: ping` heartbeat (`:52`).
3. `chat()` (`src/lib/chat.ts:195`): takes the turn's deadline first (`:197`, `deadlineFor(CHAT_MAX_DURATION_S)` = start + 285 s, since the route passes none), pushes the user message to `chat:{scope}[:{conv}]`, loads brand, this agent's preferences (`listPreferencesFor`), memory files, file names, connections, last 16 messages and the agent's recent feedback (`feedbackFor` with chat thumbs, in the uncached block) in one `Promise.all` (`:217`), builds the system prompt (`system`, `:108`, called at `:223`), and calls `client.messages.stream` with `claude-opus-5` and the nine tools (`:227`). Usage is metered per agent (`:229`).
4. The model returns a `tool_use` for `generate_content` or `draft_items`. `runTool` (`:299`, with the turn's deadline) hands the batch to `generateBatch` (`src/lib/generate-batch.ts`, `flows.md` 8.13): requires a brand, loads governance, rejects expired trials, `charge(user.email, cost, {scope, agent: agentForTask(type), cap: gov.agentCaps[agent]})` under `lock:user:{email}` (`credits.ts:70`), calls `generate()` (`noor.ts:167`: Opus generation, then Sonnet reviewer `critique`, optional dash stripping). At the agent's monthly cap the tool returns a sentence and pushes `limit:agent_cap` (`batchRefused`, `chat.ts:270`), and the reply carries `limit: "agent_cap"`. On a thrown error the credits are refunded with the charge's receipt, which also lowers the agent's counter, and the error becomes an `is_error` tool result. A `generate_image` call renders against the same deadline and starts nothing with less than 60 s of it left (`CHAT_RENDER_MIN_MS`, `:417`); its charge goes through `startMedia` with the item's owning agent and cap, like the image route.
5. Each item becomes a task in `taskFromItem` with the status `initialStatus` gives (`approved` when `gov.autoApprove[type]` and no brand rule is broken, else `pending`), and the batch is saved together (`Promise.all`) as `task:{scope}:{id}`, ids pushed to `tasks:{scope}`. `judgeLater` schedules scoring after the response (`judge.ts:179`), which later writes `quality` on the task through `updateTask` (`judge.ts:140`, on the task as stored then) and may push a notification.
6. Tool result goes back to the model (up to 5 turns). The final text is pushed to history with `items` cards and sent as `{type:"message", message, credits, limit}` (`api/chat/route.ts:57`). `track(email,"chat")` and `touchConversation` run before the final event.
7. If the client disconnects, work continues and the reply is still saved (`api/chat/route.ts:47`).

### (d) Cron run
1. Vercel Cron issues `GET /api/cron/{daily|weekly|golden|media|routines}` with `Authorization: Bearer $CRON_SECRET`.
2. Route compares the bearer to the env value with `sameSecret` (`cron/daily/route.ts:68`, `cron/weekly/route.ts:15`, `cron/golden/route.ts:12`, `cron/media/route.ts:17`, `cron/routines/route.ts:19`); 401 otherwise or when the variable is unset.
3. `allUsers()` (`schedule.ts:157`) expands every email in `users:all` into one `User` per active brand with `scope` set, skipping `suspended` accounts. The media cron does not fan out per user: it reads the open job sets.
4. Daily: `renewIfDue`, nudge email, `runLifecycle`, `runDaily`, `followUps`, optional brief email. Weekly: `runWeekly` per scope, charging credits and refunding on failure. Golden: `runGolden("cron")` under `golden:lock`. Media: `sweepMedia` (section (e), step 6). Routines: `dueRoutines` turns the users into (scope, routine) items that are on and due, and `runRoutine` runs each, charging the owning agent and refunding on failure.
5. JSON summary is returned; weekly returns a map keyed by account email (`cron/weekly/route.ts:21`); media returns `{open, advanced, done, failed, dropped, skipped}`.

### (e) Media render (image or video)
1. `POST /api/tasks/{id}/image {model?}` or `POST /api/tasks/{id}/video {model}` (`maxDuration = 120`). One deadline for the whole request, `deadlineFor(120)` = start + 105 s (`src/lib/media/keys.ts`); every step gets `min(its own maximum, time left)`. `currentUser` (401; any role), then `getTask(sc(u), id)` and `getBrand(sc(u))` (404).
2. `renderImage` / `renderVideo` (`src/lib/media/start.ts`) refuse before any charge: trial ended (402 `trial_over`), a model id that is not a catalogue id of that kind (400 `bad_model`; the image route defaults to `img-fast`, the video route has no default), a task type outside `IMAGE_TYPES` / `VIDEO_TYPES` (400 `wrong_type`), a trial account asking for a video model outside `TRIAL_VIDEO_MODELS` (402 `plan_required`), a model that is not available (`modelAvailable`: provider keys, the Blob store for kie and Higgsfield, `MEDIA_MODELS_ON`, not in `media:off`; 409 `model_unavailable`, except `img-fast`, which falls back to the uncharged placeholder card), and Photo to motion without our own image (409 `needs_image`). The placeholder card is written through `updateTask` on the task as stored, and only while it has no artwork: an item that already has a generated image, or gets one while the placeholder waits for the task lock, keeps it and the answer is 409 `model_unavailable` with nothing charged (`src/lib/media/start.ts:63-68`); one that finishes after the card was written replaces it, since the card leaves `task.mediaJob` alone.
3. `startMedia` (`src/lib/media/jobs.ts`): the owning agent's monthly cap and the balance pre-check (402 `agent_cap` / `no_credits`), flight lock `mflight` (409 `in_progress` with the running job), account limits (429 `too_many`), the trial video marker (402 `trial_video_used`), the kie create throttle or Higgsfield admission (429 `busy` / `one_open`), then `charge` with the item's owning agent and its cap (`flows.md` section 8 steps 9 and 12). The job is saved `queued` together with its open-set member and `task.mediaJob[kind]` (through `updateTask`) in one round whose three writes all settle; a failure there refunds at once through `refundOnce` (502 `media_failed` with the balance), and if that refund fails too the job, its member and the pointer are written again, the flight lock stays held and the answer is 502 `media_pending`, so the next poll or sweep ends the job `submit_lost` with the refund. Then the prompt (Sonnet, at most 20 s, or the fixed template) and one submit, never retried, under the job lock.
4. fal answers in the request: the image is copied to Blob (or hot-linked), the task gets it, 200. kie and Higgsfield answer a task id: the job becomes `running` with its `mjobref` pointer, 202, and the inbox polls. A submit refused, failed or out of time fails the job and refunds it once.
5. `GET /api/media/{jobId}` (`maxDuration = 120`; any role): `getJob(sc(u), jobId)` (404 for another account's id, no provider call), 120 polls per minute per account, then `advance`: at most one provider status call per job per 4 s (`mpoll`) under the job lock, a finished result copied through `safeFetch` (https on every hop) to Blob and written to the task (`updateTask`) before the job is saved `done`, a failure, a content refusal or a render past its max age (image 10 minutes, video 30) failed and refunded exactly once (`refundOnce` and its `mrefund` marker). A task write that fails at finalize leaves the job `running` with its result for the next pass, and `task.mediaApplied` keeps that retry from counting the render twice.
6. `POST /api/media/hook/{provider}` is a hint: per-IP limit, 64 KB body cap, the kie signature when `KIE_WEBHOOK_HMAC_KEY` is set; only the provider task id is read, the job is found through `mjobref` under its stored scope, and `advance` runs in `after()` without `force`, sharing the poll throttle. The start and poll routes schedule `maybeSweep` in `after()`, and `/api/cron/media` runs `sweepMedia` daily for whatever is left. flows.md section 23 has the details.

### (f) Resolving who is acting (2026-09-29)
1. `currentUser()` reads cookie `nashr_session` and `session:{token}` (`{email, at, imp?}`), then, in one parallel round, `user:{login}`, `member:{login}` and `activebrand:{login}` (`resolveSession` in `src/lib/auth.ts`).
2. Owner login (the `user:` record exists; it wins should a member record exist too): `null` when suspended or when `at` predates `sessionsAfter`. Otherwise the record itself, `scope = scopeFor(owner, brandId)`, and actor `{kind:"owner", role:"owner"}`, or `{kind:"founder", role:"owner", impersonating: imp}` when the session carries `imp`.
3. Member login: `null` when the record is disabled, its role or `memberOf` is malformed, the session carries `imp`, or `at` predates the member's `sessionsAfter`. Then `user:{memberOf}` and `brands:{memberOf}` in one round: `null` when the owner is missing or suspended, when `at` predates the owner's `teamSessionsAfter`, or when the member's `acceptedAt` is earlier than the owner's `createdAt`. Otherwise the OWNER's record, with `brandId` = the member's own active brand when it is one of the owner's active brands (else `default`), `scope = scopeFor(owner, brandId)`, and actor `{kind:"member", email, name, lang, role}`.
4. Every caller keeps using `sc(u)`, `u.email` (the account) and `charge(u.email, ...)` unchanged; role checks read `u.actor` through `can()` and `forbid()` (`src/lib/roles.ts`), which refuse a `User` without an actor. `saveUser` strips `actor`, `scope` and `brandId`, so none is ever persisted.
5. MCP: `userFromBearer` resolves `mcptoken:{token}` to an owner account only (a member login's email is refused), with the owner's active brand and actor `{kind:"token", role:"owner"}`. The cron's `allUsers()` builds users without an actor.
6. Founder console: `adminActor(req)` answers `"key"` for the admin key (header `x-admin-key` or cookie `nashr_admin`), the founder's email when `isFounderActor(currentUser())` (actor kind `owner`, actor email equal to the account email, in `ADMIN_EMAILS`), else `null`; `isAdmin` and `isAdminCookie` follow it.
