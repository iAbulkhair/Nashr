# Nashr: flows (as implemented)

Step-by-step behaviour with the files involved. Paths relative to the repository root. "scope" is `sc(u)`: the account (owner) email for the default brand, also while a member is acting, `email#brandId` for extra brands (`src/lib/auth.ts:26`, `src/lib/brands.ts:27`). Statements describe the code at HEAD `4959f7e`, updated since; section 23 and the role notes in the other sections describe the teams code of 2026-09-29 (roles and gates: `permissions.md` 0.1).

## 1. Signup (email first, then name and password)

Files: `src/app/[lang]/app/signup/page.tsx`, `src/components/app/AuthForm.tsx:16-70`, `src/app/api/auth/signup/route.ts`, `src/lib/auth.ts`, `src/lib/referral.ts`, `src/lib/track.ts`.

1. Page redirects an already signed-in user to `/{lang}/app` (`signup/page.tsx:11`).
2. Client step 1: email is validated with `^[^\s@]+@[^\s@]+\.[^\s@]+$` (`AuthForm.tsx:33`). Step 2 asks for name and password; the client requires length >= 8, one letter, one digit (`AuthForm.tsx:29`). Query params read: `ref` (referral code), `url` (site for onboarding), `next` (must start with `/` and not `//`, `AuthForm.tsx:23`).
3. `POST /api/auth/signup` with `{email, name, password, lang, ref, phone?}`.
4. Server: rate limit 5 per IP per hour (429 `slow_down`); normalizes email (trim, lowercase); `validEmail` (the address regex, and no `:` or `#`); `strongPassword` (8+, a letter, a digit); optional phone needs >= 9 digits. Then, inside `withLoginLock(email)` (`lock:login:{email}`, the lock invite acceptance takes too), `getLogin(email)`: an owner account or a member login at the address gets 409 `exists`, the same answer for both (2026-09-29); otherwise `createUser`.
5. `createUser` (`auth.ts:57`): bcrypt cost 10, plan `trial`, 50 credits, `trialEnds` = now + 3 days, name clipped to 80 chars. Writes `user:{email}`, adds to `users:all`. It also stamps `sessionsAfter` = `createdAt`, so a session issued for an earlier account at the same address never works again. Member logins are never created here (section 23).
6. `registerCode` writes `ref:{CODE}`. If `ref` matches `^[A-Za-z0-9]{6,10}$`, `applyReferral` runs (section 15).
7. `createSession(email)` sets cookie `nashr_session`. `track(email,"signup")`.
8. Client navigates to `next`, or `/{lang}/app/start?url={url}` when a site URL was carried (the owner reviews and confirms it there before anything is read, section 6), else `/{lang}/app/start`. A carried URL never starts onboarding by itself: until 2026-09-28 it went straight to `/{lang}/app/chat?onboard={url}`, so a link like `/en/app/signup?url=attacker.example` chose the new workspace's brand.
9. Rate limit 5 per IP per hour; no email verification, no CAPTCHA on this route.

## 2. Login

Files: `login/page.tsx`, `AuthForm.tsx:72-110`, `src/app/api/auth/login/route.ts`.

1. `POST /api/auth/login {email, password}`.
2. Rate limits 20 per IP and 8 per login per 15 min (429 `slow_down`). `getLogin(email)` finds the login: the owner record `user:{email}` or a member record `member:{email}` (the owner record wins should both exist). bcrypt compares against THAT login's own hash, so the owner's password never opens a member login and a member's never opens the owner's. Unknown login or bad password: 401 `invalid` (same response for both).
3. Owner: 403 `suspended` (only after a correct password). Member (2026-09-29): 401 `invalid` when the owner record is missing, `memberOf` does not name it, or the member was accepted before the owner record was created; 403 `suspended` when the owner is suspended; 403 `disabled` when the member is paused by the seat limit (section 23 step 13).
4. `createSession(login email)`, `track(owner email, "login")` (analytics count accounts), `{ok:true}`. Client goes to `next` (same `/` and not `//` rule) or `/{lang}/app`. Every later request resolves a member session to the owner's account again (section 5).
5. No lockout beyond the rate limits.

## 3. Logout

`src/components/app/LogoutButton.tsx` posts to `POST /api/auth/logout` (`src/app/api/auth/logout/route.ts`), which calls `destroySession()` (`auth.ts:86`): deletes `session:{token}` and the `nashr_session` cookie. It does not touch `nashr_admin`, `nashr_return` or `nashr_impersonate`.

## 4. Password reset

### Forgot
Files: `forgot/page.tsx`, `AuthForm.tsx` (`ForgotForm`), `src/app/api/auth/forgot/route.ts`, `src/lib/notify.ts`, `src/lib/rate.ts`.

1. `POST /api/auth/forgot {email, lang}`. Bad email format: 400.
2. Rate limits: 8 per 15 min per IP and 3 per 15 min per email. When exceeded the route still answers `{ok:true, mail}` (`forgot/route.ts:23`).
3. `getLogin(email)`. When the login exists and mail can reach a customer (`mailReady()`: `RESEND_API_KEY` and `MAIL_FROM` both set): a 32-byte hex token is generated, its SHA-256 is stored as `pwreset:{hash}` with `{email, kind}` (`kind` is `owner` or `member`) for 3600 s, and a link `${ORIGIN()}/{lang}/app/reset?token=...` is emailed to the login's own address. A member whose owner record is gone gets no link and the same answer.
4. Response is always `{ok:true, mail:boolean}`; `mail` says whether email delivery is configured, not whether the account exists. The forgot page shows a WhatsApp link when `SUPPORT_WHATSAPP` is set.

### Reset
Files: `reset/page.tsx`, `AuthForm.tsx:150-166`, `src/app/api/auth/reset/route.ts`.

1. `POST /api/auth/reset {token, password}`. Rate limit 10 per 15 min per IP (429).
2. Password rule server-side: length >= 8, one Unicode letter, one digit. Token must match `^[a-f0-9]{64}$`.
3. Looks up `pwreset:{sha256(token)}`. Missing: 400 `bad_token`. Single use: `pwresetuse:{hash}` is taken with SET NX (1 h) before the record is deleted, so two requests racing on one link cannot both pass (the second gets 400 `bad_token`).
4. `getLogin(record.email)`: the login must still be of the kind the record names (a record without `kind`, written before teams, is an owner's), else 400 `bad_token`, so a member removed since, or an address that changed sides, gets nothing. A suspended owner (for either kind) gets 403 `suspended`; the token is spent either way.
5. Owner: the new hash, `revokeSessions` and `revokeTeamSessions` in one save inside `withUserLock`, then `revokeAllMcp` and `createSession(owner)`. Every owner session, every member session and every MCP token dies with the old password; each member signs back in with its own.
6. Member (2026-09-29): under `withMemberLock` the member record alone gets the new hash and `sessionsAfter = now`, which signs out that member's other devices; the owner's hash, sessions and tokens are untouched. Then `createSession(member)`, unless the member is seat-paused: the password is set but the answer is 403 `disabled` with no session.

### Change password while signed in
`PATCH /api/account {currentPassword, newPassword}` (`src/app/api/account/route.ts`): session and `forbid(u, "password.change")` (every login; refused to a founder impersonating); `strongPassword`; the current password is checked against the ACTING login's own hash, never the account's for a member (401 `wrong_password`). Owner: new hash and `revokeSessions` inside the user lock, then `revokeAllMcp`. Member (2026-09-29): the member record only, under `withMemberLock`, with its own `sessionsAfter = now`; the owner's hash, sessions, MCP token and connected apps are untouched. Either way this device's session is destroyed and a new one issued for the same login, so only the other devices are signed out.

## 5. Session handling and cookie names

| Cookie | Set by | Value | Attributes | Lifetime |
|---|---|---|---|---|
| `nashr_session` | `createSession` (`src/lib/auth.ts`), `api/admin/impersonate/route.ts` (restores the founder's saved token) | 32-byte hex token; server side `session:{token}` holds `{email, at, imp?}`: the LOGIN email (owner or member), the issue time, and on an impersonation session the founder behind it (`imp`) | httpOnly, sameSite lax, `Secure` unless plain http to the loopback interface, path `/` | 30 days (cookie and Redis TTL); 2 hours for an impersonation session |
| `nashr_admin` | `api/admin/login/route.ts:18` | The raw `WAITLIST_ADMIN_KEY` value | httpOnly, lax, secure in production | 30 days |
| `nashr_return` | `api/admin/users/[email]/route.ts:87` | The founder's own session token, saved while impersonating | httpOnly, lax, secure in production | 2 hours |
| `nashr_impersonate` | `api/admin/users/[email]/route.ts:88` | Email of the impersonated user (display and audit only) | httpOnly, lax, secure in production | 2 hours |
| `nashr_lang` | `src/components/LangToggle.tsx:8` (client JS) | `ar` or `en` | not httpOnly, lax | 1 year |

`currentUser()` (`src/lib/auth.ts`, `resolveSession`; rewritten 2026-09-29): cookie, `session:{token}`, then in one parallel round `user:{login}`, `member:{login}` and `activebrand:{login}`.

- Owner login (`user:` exists; it wins should both exist): `null` when suspended or when the session predates `sessionsAfter`. Otherwise the record with `brandId`, `scope` and actor `{kind:"owner", role:"owner"}`, or `{kind:"founder", role:"owner", impersonating: imp}` when the session carries `imp`.
- Member login: `null` when the member is disabled, its role or `memberOf` is malformed, the session carries `imp`, or the session predates `member.sessionsAfter`. Then the owner record and the owner's brand list are read in one round, and `null` again when the owner is missing or suspended, the session predates `owner.teamSessionsAfter`, or the member's `acceptedAt` is earlier than the owner's `createdAt`. Otherwise the OWNER's record with actor `{kind:"member", email, name, lang, role}` and scope `scopeFor(owner, brandId)`, where `brandId` is the member's own active brand when it is one of the owner's active brands, else `default`.

Membership is re-read on every request; a session never caches the owner. `saveUser` strips `actor`, `scope` and `brandId`. Sessions are not rotated and not bound to IP or user agent; they stop working through the revocation stamps (Revocation, below), suspension (read time), the login being removed, or the account being wiped (the record is gone).

## 6. First-run onboarding inside the chat

Files: `start/page.tsx`, `src/components/app/StartWizard.tsx`, `src/app/api/onboard/confirm/route.ts`, `src/lib/onboard-confirm.ts`, `chat/page.tsx:28-41`, `src/components/app/ChatPanel.tsx:112`, `src/app/api/onboard/route.ts`, `src/lib/crawl.ts`, `src/lib/onboard.ts`, `src/app/api/onboard/plan/route.ts`, `src/components/app/OnboardCards.tsx`.

1. A user without `brand:{scope}` is redirected from the inbox, chat and reports pages to `/{lang}/app/start`. The wizard collects a site URL; a manual alternative links to `/{lang}/app/onboarding` (brand form, `PUT /api/brand`). A URL carried in from a link (signup `?url=`, start `?url=`, chat `?onboard=`) only pre-fills the field and shows a review note ("Check this link before Noor starts"); nothing is read until the owner presses Go.
2. Go posts `{url}` to `POST /api/onboard/confirm`: session and admin+ (`onboard`) required, URL trimmed and clipped to 300 characters (`onboardUrl`), length >= 4 else 400 `bad_url`, 409 `already_onboarded` when the workspace has a brand. It writes `onboardok:{scope}` = the URL (1 day) and nothing else: no crawl, no model call. The session cookie is SameSite=Lax, so another site cannot submit it for a signed-in owner. The wizard then routes to `/{lang}/app/chat?onboard={url}` (also on 409, where the chat opens as usual).
3. The chat page without a brand reads `onboardok:{scope}` and hands that URL to `ChatPanel`. The `?onboard=` value itself is never used to build: without a confirmation the page redirects to `/{lang}/app/start?url={value}` so the owner reviews it.
4. `ChatPanel` posts `{url}` to `POST /api/onboard`. Server requires a session, admin+ (`onboard`) and a URL of length >= 4, then, in this order: 409 `already_onboarded` when `brand:{scope}` exists; 403 `unconfirmed` unless the URL equals `onboardok:{scope}` (checked in code, before the paused check, the daily allowance, the lock and the crawl, so an unconfirmed URL costs nothing); 503 `paused`; 429 after three runs a day per account; lock `onboardlock:{scope}` (240 s), a second concurrent run gets 409 `busy`.
5. SSE stream (10 s ping). Steps: intro message, `crawl(url)` of the confirmed URL (server-side fetch of the user URL, 9 s timeout, follows redirects, `crawl.ts:44`), then `buildFromSite`: three parallel `claude-opus-5` calls from the same snapshot (core: brand, brand.md, plan, goal, summary; identity: guidelines, opportunities; market: research, strategy), one retry per part; the status line advances as each part lands.
6. Writes: `saveBrand(scope)`, each returned file via `writeFile(scope, ...)`, `preferences.md` if absent, `onboardplan:{scope}`, and deletes `onboardok:{scope}`: one confirmation, one build. Every assistant message is persisted to `chat:{scope}` via `push`. A failed or paused run keeps the confirmation, so "refresh to try again" works for a day.
7. Onboarding charges no credits (`onboard/route.ts:25`) and runs once per workspace (409 once `brand:{scope}` exists) and at most three times a day per account.
8. `GET /api/onboard/plan` returns the stored plan; `POST {index, added}` flips the `added` flag (admin+, `onboard`). Phone is requested in-thread and saved through `PUT /api/profile` (`OnboardCards.tsx:75`), which needs `profile.account` (owner); the card is still shown to admins and members (`permissions.md` 5.26).
9. While the stream runs, `OnboardProgress` (`ChatPanel.tsx`) shows each `status` event as a completed step with a bar that never reaches 100% before `done`. After it, the launch journey (section 19) celebrates its first milestone.

12. Goal, reviewer and judge (2026-09-29). Every generation and chat turn reads `memoryBlock(scope)` (`files.ts`), which opens with the owner's onboarding goal from `onboardplan:{scope}` when there is one: one line of at most 140 characters, flattened by `goalLine` so it cannot open a fake file section. Callers read it with the preferences, memory and data inside the refunding `try`. The golden set passes neither.

## 8. Credits: charge and refund

Files: `src/lib/credits.ts`, callers in `api/generate/route.ts:25`, `chat.ts:228,258,331`, `api/mcp/route.ts:71`, `api/tasks/[id]/image/route.ts:16`, `schedule.ts:45`, `routines.ts` (`routineFor`).

1. `withUserLock(email)`: spin on `lock:user:{email}` (SET NX, 10 s TTL), 60 tries at 50 ms (3 s) then throws `user_lock_timeout`. Re-reads the user inside the lock.
2. `charge(email, cost, meta?)`: fails without change when `credits < cost` (`reason: "no_credits"`, with `need`) or, with `meta`, when the agent's monthly cap would be passed (`reason: "agent_cap"`, step 9); else subtracts and saves, with `meta` also adding to the agent's counter in the same save.
3. `refund(email, n, spend?)` adds `n` back; balance is floored at 0 and deltas are truncated to integers. With the charge's result as `spend` it also lowers that agent's counter (step 9); without it, it is `adjust(email, +n)`.
4. Pattern: charge before the model call, refund in `catch`. Credits belong to the account, not the brand: every scope of one account draws from `user:{email}.credits`.
5. The lock guards only the read-modify-write of the user record and expires after 10 s. `unlock` is an unconditional `DEL` (`db.ts:56`), so a holder whose lock already expired would delete the next holder's lock.
6. Other balance writers: `renewIfDue` (monthly reset to plan allowance for non-trial plans, `credits.ts:58`), `POST /api/admin/plan` (under lock), `applyReferral` (+50 both sides), `POST /api/referral/share` (+20 per platform).
7. Writers that save the whole user record outside the lock: `PUT /api/profile` (`profile/route.ts:39`), `PATCH /api/account` (`account/route.ts:15`), `POST /api/auth/reset` (`reset/route.ts:22`). These persist the `credits` value read at request start.
8. Trial expiry is checked in `/api/generate`, chat tools `generate_content` and `draft_items`, `runWeekly` and `runRoutine`. It is not checked in MCP `generate_content`, `generate_image` (chat tool and route), onboarding, catalog import, or free tools.
9. Per-agent spend and caps (2026-09-29). Attribution: a charge belongs to the agent that owns the task type (`agentForTask(type)`, computed in code, never taken from the request); an image belongs to the owner of the item it illustrates; the weekly plan is Noor's; a routine's batch belongs to the owner of its type (Dana, Noor, Razan or Majed). Chat turns are never charged credits (only metered), so a cap bounds batches, drafts and images, not chat. Every charging path (`/api/generate`, `POST /api/tasks/{id}/image`, MCP `generate_content`, chat `generate_content`, `draft_items` and `generate_image`, `runWeekly`, `runRoutine`) reads governance BEFORE charging and calls `charge(email, cost, {scope, agent, cap: gov.agentCaps[agent]})`. Inside the same lock, `charge` refuses with `{reason: "agent_cap", spent, cap, agent}` when `spent + cost > cap`, without touching the balance; otherwise it debits and adds the cost to `User.agentSpend.by[scope][agent]` in the same `saveUser`, so parallel charges can never pass the cap. A record from an earlier month counts as empty: the month is the UTC calendar month and rolls at 00:00 UTC on the 1st, while `renewIfDue` resets the balance later, at the 05:00 UTC daily cron. Every refund after a metered charge passes the charge's result, and the counter goes down by the refund (never below 0) only while the record is still in the charge's month. `adjust` (referral and share bonuses), `POST /api/admin/plan` and `renewIfDue` never touch the counters.
10. At 100%: `/api/generate` and the image route answer 402 `{ok:false, error:"agent_cap", agent, spent, cap}` before any model call; MCP `generate_content` returns a tool error (`isError`) with the same facts in a sentence, like its insufficient-credits answer; chat tools return a sentence for the model to relay and push `limit:agent_cap`, which `/api/chat` returns as `limit: "agent_cap"`; `runWeekly` and `runRoutine` return `agent_cap` (not a retry). The app's limit dialog (`LimitModal`, `limitFromError("agent_cap")`) explains the cap and links to Governance instead of billing. At 80%: the charge that crosses 80% of the cap returns `warn80`, and `warnAgentCap` (`notifications.ts`, called by every charging path) pushes one `credits` notification per brand scope, agent and month (fingerprint `agentcap80:{scope}:{agent}:{YYYY-MM}`, 35 days) naming the agent, the brand the cap belongs to (the name given to the brand, else its brand file's; the bell is per account and Governance shows the open brand, so the body says to switch to that brand) and "X of Y credits this month".
11. ### OAuth 2.1
1. Discovery: `/.well-known/oauth-authorization-server` and `/.well-known/oauth-protected-resource` (rewrites). Issuer and endpoints derive from `APP_ORIGIN`.
2. Client registration: `POST /api/oauth/register` is open to anyone. Keeps up to 10 `http(s)` redirect URIs, issues `client_id`, and a `client_secret` only when `token_endpoint_auth_method = client_secret_post`. Rate limited to 30 per IP per hour (429 `slow_down`); no expiry.

4. Approve: `POST /api/oauth/approve` (form post, session required) re-validates client and redirect URI, requires `code_challenge_method=S256`, issues a 10 min single-use code bound to client, redirect URI, challenge, email and `scope` (free text from the request, default `noor`). - Weekly (`src/app/api/cron/weekly/route.ts`, `schedule.ts` `runWeekly`): skips when no brand, `weeklyPlan` off, trial over, weekly cap reached (`gov.weeklyCap`, counts `source:"scheduled"` tasks in 7 days, the routines' included), Noor's monthly credit cap reached in that brand (`agent_cap`) or insufficient credits (`no_credits`). Response body maps account email to result string.
- Golden (`cron/golden/route.ts`, `golden.ts`): fixed fictional brands, meters usage under `golden@nashr.internal`, notifies founder accounts on regressions.
- Routines (`src/app/api/cron/routines/route.ts`, `src/lib/routines.ts`, 2026-09-29), daily at 06:00 UTC, after the 05:00 daily job has renewed credits. Four routines, each for an agent with real input data: `dana_weekly_report` (Dana, `weekly_report`, weekly), `noor_cart_recovery` (Noor, `cart_recovery`, weekly), `razan_cash_forecast` (Razan, `cash_forecast`, monthly) and `majed_monthly_review` (Majed, `strategy_review`, monthly). The other agents have none until they have a data source. All are off by default; the owner turns each on per brand on the Scheduled tasks page (`PUT /api/schedule {routines: {id: boolean}}`, only known ids with boolean values, merged per id into `schedule:{scope}.routines`). There is no "Run now" for a routine.
  1. Items: `dueRoutines(allUsers())` reads every (user, active brand) schedule in parallel, then the last runs of the routines that are on, and keeps those that are on and have not run in their period (the UTC week from Sunday, `weekStartUtc`, or the UTC month, `monthKey`). `runCronBatch` with job `routines`, period = today's UTC date, id `{scope}:{routineId}`, four at a time, no new item after 160 s, markers for 2 days. One item is one generation. A missed day needs no catch-up route: the next day's run asks again and the period check decides. The batch's attempt count is per day, so charges left by killed runs are bounded by the runner's own count per routine and period (step 4).
  2. `runRoutine(user, id)` in this order: brand (`no_brand`); switched on (`off`); not yet run in its period (`routinelast:{scope}:{id}`, `already_this_period`); model state (`retry:paused` while paused, `skip:mock` without a key, since placeholders must never be charged); lock `routinelock:{scope}:{id}` (300 s, `retry:locked`); trial (`trial_over`); the last run read again under the lock; the gate; the weekly cap and the batch's hold; the attempt count (`attempts_exhausted`); the charge. The hold is deleted and the lock released in a `finally`, after the batch is saved.
  3. Gates, checked in code; a gate that fails answers `idle` or `no_data`, charges nothing and is final for the day (the next day's run asks again). Only Noor's gate asks for data newer than the routine's last run; Razan's and Majed's look at a fixed window, so they can run again in the next month on the same sync or decisions. Dana: an item the owner created or any decision in the last 7 days (light index `createdAt`/`decidedAt`, newest decision record), or a store sync (`storesales:{scope}.at`) or an ad-account read (`adsync:{scope}:{provider}`) in the last 7 days; items the weekly plan or a routine created on their own do not count, or the routines would keep each other busy for an absent owner. Noor: abandoned-cart data (`missingData` is null, else `no_data`) synced after the routine last ran (else `idle`). Razan: a store sales snapshot from the last 35 days (else `no_data`). Majed: decisions on at least 3 different items in the last 30 days, from the decision records or the light index's `decidedAt` (else `idle`).
  4. Weekly cap: the `source:"scheduled"` items of the last 7 days, plus the batches the brand's other routines hold right now (`routinehold:{scope}:{id}` = their `TASK_COUNT`), plus this batch's `TASK_COUNT` must not pass `gov.weeklyCap` (`cap_reached`); the weekly plan and the routines share it. The cron runs a brand's routines side by side, so this check and setting the routine's own hold (360 s) happen under a short lock per brand (`routinecap:{scope}`, waited for up to about 2 s, else `retry:locked`); holds are read before the items, and a run deletes its hold only after its batch is saved (in `runRoutine`'s `finally`), so every batch is counted once in one of the two. Then the attempt count `routinetry:{scope}:{id}:{period}` (8 or 35 days) is raised before the charge and lowered again when the charge is refused or refunded; a platform kill leaves it raised, and once two such charges are left in the period the routine answers `attempts_exhausted` (final for the day, nothing charged) until its next period. Then `charge(email, TASK_COST[type], {scope, agent, cap: gov.agentCaps[agent]})` (`agent_cap`, `no_credits`) and `warnAgentCap`.
  5. Inside the refunding try, one round: `listPreferencesFor`, `memoryBlock`, `statsFor(type)` (Dana and Majed: WORKSPACE DATA, plus STORE DATA when a store was synced; Noor: CART DATA; Razan: STORE DATA) and `feedbackFor`; then `generate` with the routine's note. A throw refunds with the charge's receipt, lowers the attempt count and is rethrown (the cron counts a failed attempt).
  6. The batch is saved in one parallel round with `source:"scheduled"` and `brief` = the routine id, judged with the same grounding (`judgeLater`), `routinelast:{scope}:{id}` is set, and one `pending` notification goes to the account (fingerprint `routine:{scope}:{id}:{period}`, 8 or 35 days). The answer is `ok:N`.
- Users can trigger their own runs: `POST /api/schedule {run:"weekly"|"daily"}`. Any login may (the run is charged to the account); turning routines or the weekly plan on or off (`PUT /api/schedule`) needs admin+ (`schedule.write`).

## 20. Campaign results import (CSV)

Files: `src/lib/perf-import.ts`, `src/lib/perf-store.ts`, `src/app/api/performance/route.ts`, `src/components/app/PerformanceImport.tsx` (on the reports page).

1. The owner exports an ad-level report (Meta, Snapchat, TikTok, Google Ads, or an email tool) and drops the CSV on the reports page. The browser reads the text (2 MB at most) and posts `{csv, file, metric?}` to `POST /api/performance`.
2. `readRows`: RFC 4180 parse with the delimiter detected from the header; the header is the first of the first twelve rows naming two known columns (English or Arabic synonyms, most specific first: "link clicks" before "clicks"); totals lines are skipped; at most 5,000 rows. Names and text are stripped to one plain line (`clean`). Missing name column or metrics: 422 with a reason code.
3. `analyze`: the metric defaults to what the file supports (ROAS, then cost per result, CTR, open rate, conversion rate) and can be switched. A row is ranked only above the metric's sample minimum (500 impressions for CTR, 30 clicks for cost per result, 50 spend for ROAS, 30 clicks for conversion rate, 100 sends for open rate). Findings: top and bottom three, best against the median, wording patterns (offer, number, question, Arabic, short) compared by pooled metric when both groups have three or more ads and differ by 20% or more, best and weakest placement, and spend with no result when it is 10% or more of spend. Confidence is "medium" at ten times the sample minimum with five or more ads, otherwise "low"; never "high".
4. `savePerf` stores the snapshot in `perfimport:{scope}` and writes `performance-learnings.md`, which `memoryBlock` includes, so every later generation, the weekly plan included, reads it. The file states that quoted names are data, not instructions, and that findings are comparisons, not promises. The reports card links to chat with prompts to write variants of the winners or plan next week.
5. No model call and no credits. `DELETE` removes the snapshot and the file. An upload replaces the last snapshot and the file, so replacing is deleting: `POST` needs admin+ (`performance.import`) and `DELETE` needs admin+ (`performance.delete`). A connected ad account's sync (section 21) reads the account's own numbers and stays open to every login. A member sees the findings with a note instead of the upload and remove controls.

## 23. Teams: members, invites and seats (2026-09-29)

Files: `src/lib/team.ts`, `src/lib/roles.ts`, `src/lib/auth.ts` (`resolveSession`, `getLogin`, `PLAN_SEATS`, `seatLimit`), `src/app/api/team/*`, `src/app/[lang]/app/team/page.tsx` (`TeamPanel`, `teamPerms`), `src/app/[lang]/app/join/page.tsx` (`JoinForm`, `inviteToken.ts`), `src/app/api/admin/plan/route.ts`, `src/lib/account.ts`. Design: `docs/superpowers/specs/2026-09-29-teams-design.md`. Roles and gates: `permissions.md` 0.1.

1. Model. The account stays the owner's `User` at `user:{owner}`: plan, credits, brands, scopes, governance, usage and cron are unchanged. A member is a separate login at `member:{email}` (`{email, name, lang, passHash, memberOf, role, invitedBy, acceptedAt, sessionsAfter, disabled?}`), listed in `members:{owner}`. It never passes through `saveUser` or `createUser`, never enters `users:all`, and gets no trial credits, referral code or signup tracking. An email is one login across `user:` and `member:`: signup and accept both create logins under `lock:login:{email}`.
2. Members page (`/{lang}/app/team`, every role; "Members" / "الأعضاء"). Server-rendered from `teamView(u)`, the same body `GET /api/team` returns: the acting person, seats used of the limit, the roster (owner first; each member's role, `acceptedAt` and `disabled`) and, for admin and owner, the pending invites. The controls come from `teamPerms(u)`, which is `can()`; after every change the panel reloads `GET /api/team`.
3. Invite (`POST /api/team/invite {email, role, lang?}`). Needs `team.invite.member` (admin+); `role: "admin"` needs the owner; a founder impersonating cannot invite. Rate limits `team:invite:acct:{owner}` 20 a day (5 on a trial, which anyone can open with one signup), `team:invite:ip:{ip}` 30 an hour and `team:invite:to:{sha256(address)}` 5 a day across all accounts, counted on every attempt, because each answer says whether an address is free and each emailed invite is mail from the product's own domain to a stranger. `createInvite`: the role must be `admin` or `member` (400 `invalid_role`); the email is normalised and must pass `validEmail` (400 `invalid_email`); the acting member's record must still hold its role (403). The owner's or the inviter's own address is 409 `unavailable`; then, under `lock:team:{owner}`, an existing owner or member login anywhere, or a pending invite for the address in this team, gets the same 409 `unavailable`, and seats used + 1 over the limit gets 409 `{error:"seats", used, limit}`. The token is 32 random bytes (64 hex); only its SHA-256 is stored, as `invite:{hash}` (`{email, role, owner, invitedBy, createdAt, expiresAt, lang}`, TTL 7 days) plus an entry in `invites:{owner}`. The link is `${ORIGIN()}/{lang}/app/join#t={token}`: the token is in the fragment, so it never reaches a server or an edge log. When `mailReady()` the link is emailed in the invite's language from a fixed template that names only the inviting login's address (never a display name or brand name, which are free text the sender chose), and the link goes to the invited address or nowhere: when that send fails the invite is withdrawn under `lock:team` (`discardInvite`) and the answer is 502 `{error:"send_failed"}` with no link, so an inviter cannot take an address they do not control by making the send fail. Only when mail is not set up at all does the response carry `link` once for the inviter to pass on (the Members page then says a link is created, not that an email is sent). It can never be shown again (only the hash exists); to resend, cancel and invite again. The account's bell gets an item that names neither the invited address nor the role (the bell is shared by every login, and pending invites are admin+) and says whether an email went out. Response: `{ok, invite: {id, email, role, expiresAt}, emailed, link?}`, where `id` is the hash.
4. Cancel (`DELETE /api/team/invite {id}`). Needs `team.invite.cancel` (admin+; an admin cancels `member` invites only; not a founder impersonating). The id must name an invite of this account (else 404); under `lock:team:{owner}` the invite is read again and, if still there, it and its index entry are deleted (404 when an accept holding the lock used it first).
5. Join page (`/{lang}/app/join`, public, listed in the app layout's public paths). `JoinForm` reads the token from `location.hash` (`readInviteToken`: 64 hex or nothing), clears the fragment with `history.replaceState`, and never puts the token in a query string. It keeps the token in `sessionStorage` for the tab (`rememberInviteToken`), so switching the page language, which reloads without the fragment, still finds it; it is forgotten after a successful accept and whenever the server calls it invalid, and the page works without storage. A signed-in visitor is shown who they are signed in as and must log out first; nobody is joined into an existing session. Signed out, the form posts `{token}` to `POST /api/team/accept` for a preview.
6. Preview (`POST /api/team/accept {token}`). Rate limit `team:peek:ip:{ip}` 30 per 15 min. `peekInvite` returns `{team, inviter, email, role, expiresAt}` for a live invite whose owner exists and is not suspended and whose inviter still passes the accept's check (the owner, or an enabled admin of this team inviting a plain member); anything else is 400 `invalid`. Nothing is consumed.
7. Accept (`POST /api/team/accept {token, name, password, lang?}`). Rate limit `team:accept:ip:{ip}` 10 per 15 min. `acceptInvite`: a live invite (400 `invalid`); a name, control characters removed and cut to 80 (400 `invalid_name`); `strongPassword` (400 `weak_password`); bcrypt runs before any lock. Then single use: `inviteuse:{hash}` is taken with SET NX (30 s; a concurrent accept gets 400 `invalid`). Under `lock:team:{owner}` everything that decides the answer is read again, so a cancel, a plan change, a demotion or an account deletion that finished while the accept waited is seen: the invite must still be stored AND in `invites:{owner}` (a cancelled one is 400 `invalid`, never counted as a new seat); the owner exists, is not suspended and is not newer than the invite (an address registered again); an invite sent by a member needs that member to be still an enabled admin of this team and the role to be `member`; and the seats are counted against the owner's limit as it is now, the invite's own seat counted once (409 `seats`). Under `lock:login:{email}` the address must still be free across `user:` and `member:` (409 `unavailable`). The member is written with `acceptedAt = sessionsAfter = now` and the language from the request, else the invite's; the invite and its index entry are deleted. The route then destroys any session on the device, creates one for the member and puts a bell item on the owner. The new login lands in the owner's workspace (section 5).
8. Member login, forgot, reset and password change act on the member record only (sections 2 and 4): the member's own hash and its own `sessionsAfter`; the owner's hash, sessions, MCP token and grants are never touched. A seat-paused member cannot sign in (403 `disabled`).
9. Remove (`DELETE /api/team/member {email}`). Needs `team.remove.member` (admin+); removing an admin needs the owner; a founder impersonating cannot. The member must belong to this account (404). Under `lock:team:{owner}` and then `lock:member:{email}` (the lock every member-record writer holds), the record is read again and, while it still belongs to this account, `member:{email}`, `activebrand:{email}`, the roster entry and every pending invite that member sent are deleted. A profile, password or reset save in flight therefore finishes first or finds nothing: it can never restore a removed login. The member's sessions stop at their next request, because `currentUser` finds no member record (and would refuse one off the roster anyway).
10. Leave (`POST /api/team/leave`). Member logins only (`team.leave`; the owner, a token and a founder get 403). The same deletion as a removal, then `destroySession()`.
11. Role change (`PATCH /api/team/member {email, role}`). Owner only (`team.role`). `admin` or `member` only; the owner role cannot be assigned, removed or transferred. Written under `lock:team:{owner}` and `lock:member:{email}`; the new role applies at the member's next request. Demoting an admin deletes the invites that admin sent, which could never be accepted afterwards yet would each hold a seat for up to 7 days.
12. Seats. The limit is `seatLimit(owner)`: `User.seats` when it is a positive integer, else `PLAN_SEATS[plan]` (trial 3, starter 1, pro 3, agency 7, enterprise 25), the owner included. Seats used = 1 + members not disabled + unexpired invites. The billing page shows used of the limit to every role.
13. Seats after a plan change. `POST /api/admin/plan` (founder console) runs `enforceSeats(owner)` after any plan or `seats` change, up or down, under `lock:team:{owner}`, relative to who is active now: over the limit, the newest ENABLED members get `disabled: "seats"` (kept, never deleted) and every pending invite beyond the room left is cancelled, the newest first; under it, paused members come back oldest first, but only into seats no pending invite holds. Re-applying the same limit changes nothing (the team is never re-ranked as a whole, so a member the owner brought in after a downgrade is not swapped for one paused earlier). Removing a member does not bring a paused one back by itself; the next limit change does. A disabled member's login answers 403 `disabled` and its sessions stop at their next request. The response and the `admin:log` entry list who was paused and restored and how many invites were cancelled. Trial to Starter therefore pauses up to two members. No other code changes a plan today (`permissions.md` 5.32).
14. Account deletion (`DELETE /api/account`, owner only, or the console's `delete`). `wipeAccount` deletes the account's keys, `user:{owner}` included, and then runs `wipeTeam(owner)` under `lock:team:{owner}`: every member record of this account (each under its own `lock:member`), each member's `activebrand:`, every invite, `members:{owner}` and `invites:{owner}`. An accept that held the team lock first has its member deleted here; one that takes it afterwards finds no owner. A member login never survives to point at an address someone registers again, and a member record older than a re-registered owner is refused anyway (section 5).
15. Owner reset and founder reset both stamp `teamSessionsAfter` on the owner record, in the same locked save as the password, which signs every member out; each signs back in with its own password. A member's own reset or password change stamps only its own `sessionsAfter`. The owner's password change from Settings does not sign members out.
16. Shared and per login. Credits and the plan are the account's, so a member's generations spend the owner's balance under the same per-agent caps. The bell (`notifs:{owner}`) and its read state, the chat ceiling and analytics are per account. The active brand is per login: a member switching or adding a brand moves only `activebrand:{member}`, and a member's stored brand is used only while it is one of the owner's active brands; an admin archiving the brand the owner has open resets the owner's key too.
17. Pages by role. Owner-only and admin+ screens render read-only for lower roles with a one-line note: billing (no pay links or WhatsApp activation; seats for all), governance, the scheduled tasks page ("Run now" stays), the brand file, brands (switching stays), integrations (requesting stays), MCP (no token or grant controls), refer (nothing read). The sidebar shows the acting person's name, email and role and a Members link for everyone; the trial banner and the limit dialog tell other roles to ask the owner. The working screens offer a plain member only what the server lets a member do: the inbox has no Approve or Publish for a member (an edit is saved without approving, and an approved item goes back to pending), and a chat card says an admin approves; the files page has no catalog import and no edit or delete on core memory; reports offer no CSV import or removal of imported results; the start page tells a member who sets the brand up (and the chat's first-run thread sends them there); the chat's WhatsApp card is shown only to the owner, whose phone it saves. A refused call says the role does not allow it, never "check your connection". The profile page hides the password and delete forms from a founder viewing the account (`GET /api/profile` returns `may`), and the MCP page tells a founder why there is no token.

## Revocation (2026-09-18)

- Password change (`PATCH /api/account`): new hash and `sessionsAfter = now` saved inside the user lock, the caller's session is destroyed and a new one issued. Every other session of the account fails at its next request. This is the owner's change; it does not sign members out. A member's change is its own (section 4).
- Password reset (`POST /api/auth/reset`) and founder `resetPassword`: the same, plus `revokeAllMcp` (personal MCP token and every OAuth grant).
- Connected apps: `GET /api/mcp/grants` lists OAuth grants of the signed-in account; `DELETE /api/mcp/grants?id=` revokes one, `?all=1` all. A grant id of another account is a 404. Refreshing a token keeps the grant and deletes the previous access token.
- Teams (2026-09-29): a member's password change or reset stamps that member's own `sessionsAfter` (its other devices only); an owner reset and a founder `resetPassword` also stamp `teamSessionsAfter` on the owner record, which signs every member out; a removal, a member leaving and a seat pause end that member's sessions at their next request, because `currentUser` re-reads the member record; `createUser` stamps `sessionsAfter` at creation, so a session from an earlier account at the same address never revives. Listing and revoking grants is owner only (`oauth.grants`).
