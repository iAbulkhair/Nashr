## 1. Signup (email first, then name and password)

Files: `src/app/[lang]/app/signup/page.tsx`, `src/components/app/AuthForm.tsx:16-71`, `src/app/api/auth/signup/route.ts`, `src/lib/auth.ts`, `src/lib/referral.ts`, `src/lib/track.ts`.

1. Page redirects an already signed-in user to `/{lang}/app` (`signup/page.tsx:11`).
2. Client step 1: email is validated with `^[^\s@]+@[^\s@]+\.[^\s@]+$` (`AuthForm.tsx:33`). Step 2 asks for name and password; the client requires length >= 8, one letter, one digit (`AuthForm.tsx:29`). Query params read: `ref` (referral code), `url` (site for onboarding), `next` (must start with `/` and not `//`, `AuthForm.tsx:23`).
3. `POST /api/auth/signup` with `{email, name, password, lang, ref, phone?}`.
4. Server: normalizes email (trim, lowercase); same email regex; password length >= 8 only (no letter/digit rule server-side, `signup/route.ts:10`); optional phone needs >= 9 digits; 409 `exists` if `user:{email}` exists.
5. `createUser` (`auth.ts:63`): bcrypt cost 10, plan `trial`, 50 credits, `trialEnds` = now + 3 days, name clipped to 80 chars. Writes `user:{email}`, adds to `users:all`.
6. `registerCode` writes `ref:{CODE}`. If `ref` matches `^[A-Za-z0-9]{6,10}$`, `applyReferral` runs (section 15).
7. `createSession(email)` sets cookie `nashr_session`. `track(email,"signup")`.
8. Client navigates to `next`, or `/{lang}/app/start?url={url}` when a site URL was carried (the owner reviews and confirms it there before anything is read, section 6), else `/{lang}/app/start`. A carried URL never starts onboarding by itself: until 2026-09-28 it went straight to `/{lang}/app/chat?onboard={url}`, so a link like `/en/app/signup?url=attacker.example` chose the new workspace's brand.
9. No rate limit, no email verification, no CAPTCHA on this route.

## 2. Login

Files: `login/page.tsx`, `AuthForm.tsx:73-111`, `src/app/api/auth/login/route.ts`.

1. `POST /api/auth/login {email, password}`.
2. `getUser(normalizeEmail(email))`; bcrypt compare. Unknown user or bad password: 401 `invalid` (same response for both). Suspended: 403 `suspended` (only after a correct password).
3. `createSession`, `track("login")`, `{ok:true}`. Client goes to `next` (same `/` and not `//` rule) or `/{lang}/app`.
4. No rate limit or lockout on this route.

## 3. Logout

`src/components/app/LogoutButton.tsx` posts to `POST /api/auth/logout` (`src/app/api/auth/logout/route.ts`), which calls `destroySession()` (`auth.ts:92`): deletes `session:{token}` and the `nashr_session` cookie. It does not touch `nashr_admin`, `nashr_return` or `nashr_impersonate`.

## 4. Password reset

### Forgot
Files: `forgot/page.tsx`, `AuthForm.tsx` (`ForgotForm`), `src/app/api/auth/forgot/route.ts`, `src/lib/notify.ts`, `src/lib/rate.ts`.

1. `POST /api/auth/forgot {email, lang}`. Bad email format: 400.
2. Rate limits: 8 per 15 min per IP and 3 per 15 min per email. When exceeded the route still answers `{ok:true, mail}` (`forgot/route.ts:23`).
3. If the account exists and `RESEND_API_KEY` is set: a 32-byte hex token is generated, its SHA-256 is stored as `pwreset:{hash}` with `{email}` for 3600 s, and a link `${APP_ORIGIN}/{lang}/app/reset?token=...` is emailed.
4. Response is always `{ok:true, mail:boolean}`; `mail` says whether email delivery is configured, not whether the account exists. The forgot page shows a WhatsApp link when `SUPPORT_WHATSAPP` is set.

### Reset
Files: `reset/page.tsx`, `AuthForm.tsx:151-167`, `src/app/api/auth/reset/route.ts`.

1. `POST /api/auth/reset {token, password}`. Rate limit 10 per 15 min per IP (429).
2. Password rule server-side: length >= 8, one Unicode letter, one digit. Token must match `^[a-f0-9]{64}$`.
3. Looks up `pwreset:{sha256(token)}` and the user. Missing: 400 `bad_token`. The key is deleted before the suspended check (token is single use even when the account is suspended, 403).
4. New bcrypt hash saved with `saveUser` (not under the user lock), `createSession`, `{ok:true}`. Existing sessions for the account are not revoked.

### Change password while signed in
`PATCH /api/account {currentPassword, newPassword}` (`src/app/api/account/route.ts:8`): requires session, new password length >= 8, verifies the current password, saves. Other sessions are not revoked.

## 5. Session handling and cookie names

| Cookie | Set by | Value | Attributes | Lifetime |
|---|---|---|---|---|
| `nashr_session` | `auth.ts:89` (`createSession`), `api/admin/impersonate/route.ts:11` | 32-byte hex token; server side `session:{token}` holds the email | httpOnly, sameSite lax, secure in production, path `/` | 30 days (cookie and Redis TTL) |
| `nashr_admin` | `api/admin/login/route.ts:18` | The raw `WAITLIST_ADMIN_KEY` value | httpOnly, lax, secure in production | 30 days |
| `nashr_return` | `api/admin/users/[email]/route.ts:90` | The founder's own session token, saved while impersonating | httpOnly, lax, secure in production | 2 hours |
| `nashr_impersonate` | `api/admin/users/[email]/route.ts:91` | Email of the impersonated user (display and audit only; `byOf` records the founder only when `nashr_return` or the admin key cookie backs it) | httpOnly, lax, secure in production | 2 hours |
| `nashr_lang` | `src/components/LangToggle.tsx:8` (client JS) | `ar` or `en` | not httpOnly, lax | 1 year |

`currentUser()` (`auth.ts:99`): cookie, `session:{token}`, `user:{email}`; returns `null` when the user is missing or `suspended`; otherwise sets runtime-only `brandId` and `scope`. Sessions are not rotated, not bound to IP or user agent, and are not deleted on password change, password reset, suspension (suspension is enforced at read time) or account wipe (the user record disappears, so `currentUser` returns `null`).

## 6. First-run onboarding inside the chat

Files: `start/page.tsx`, `src/components/app/StartWizard.tsx`, `src/app/api/onboard/confirm/route.ts`, `src/lib/onboard-confirm.ts`, `chat/page.tsx:28-41`, `src/components/app/ChatPanel.tsx:112`, `src/app/api/onboard/route.ts`, `src/lib/crawl.ts`, `src/lib/onboard.ts`, `src/app/api/onboard/plan/route.ts`, `src/components/app/OnboardCards.tsx`.

1. A user without `brand:{scope}` is redirected from the inbox, chat and reports pages to `/{lang}/app/start`. The wizard collects a site URL; a manual alternative links to `/{lang}/app/onboarding` (brand form, `PUT /api/brand`). A URL carried in from a link (signup `?url=`, start `?url=`, chat `?onboard=`) only pre-fills the field and shows a review note ("Check this link before Noor starts"); nothing is read until the owner presses Go.
2. Go posts `{url}` to `POST /api/onboard/confirm`: session required, URL trimmed and clipped to 300 characters (`onboardUrl`), length >= 4 else 400 `bad_url`, 409 `already_onboarded` when the workspace has a brand. It writes `onboardok:{scope}` = the URL (1 day) and nothing else: no crawl, no model call. The session cookie is SameSite=Lax, so another site cannot submit it for a signed-in owner. The wizard then routes to `/{lang}/app/chat?onboard={url}` (also on 409, where the chat opens as usual).
3. The chat page without a brand reads `onboardok:{scope}` and hands that URL to `ChatPanel`. The `?onboard=` value itself is never used to build: without a confirmation the page redirects to `/{lang}/app/start?url={value}` so the owner reviews it.
4. `ChatPanel` posts `{url}` to `POST /api/onboard`. Server requires a session and a URL of length >= 4, then, in this order: 409 `already_onboarded` when `brand:{scope}` exists; 403 `unconfirmed` unless the URL equals `onboardok:{scope}` (checked in code, before the paused check, the daily allowance, the lock and the crawl, so an unconfirmed URL costs nothing); 503 `paused`; 429 after three runs a day per account; lock `onboardlock:{scope}` (240 s), a second concurrent run gets 409 `busy`.
5. SSE stream (10 s ping). Steps: intro message, `crawl(url)` of the confirmed URL (server-side fetch of the user URL, 9 s timeout, follows redirects, `crawl.ts:44`), then `buildFromSite`: three parallel `claude-opus-5` calls from the same snapshot (core: brand, brand.md, plan, goal, summary; identity: guidelines, opportunities; market: research, strategy), one retry per part; the status line advances as each part lands.
6. Writes: `saveBrand(scope)`, each returned file via `writeFile(scope, ...)`, `preferences.md` if absent, `onboardplan:{scope}`, and deletes `onboardok:{scope}`: one confirmation, one build. Every assistant message is persisted to `chat:{scope}` via `push`. A failed or paused run keeps the confirmation, so "refresh to try again" works for a day.
7. Onboarding charges no credits (`onboard/route.ts:25`) and runs once per workspace (409 once `brand:{scope}` exists) and at most three times a day per account.
8. `GET /api/onboard/plan` returns the stored plan; `POST {index, added}` flips the `added` flag. Phone is requested in-thread and saved through `PUT /api/profile` (`OnboardCards.tsx:75`).
9. While the stream runs, `OnboardProgress` (`ChatPanel.tsx`) shows each `status` event as a completed step with a bar that never reaches 100% before `done`. After it, the launch journey (section 19) celebrates its first milestone.

## 7. Chat turn with `generate_content` and `draft_items`

Files: `src/app/api/chat/route.ts`, `src/lib/chat.ts`, `src/lib/noor.ts`, `src/lib/credits.ts`, `src/lib/judge.ts`, `src/lib/governance.ts`.

It works out who is talking once (`opts.by`, which the MCP route sets to `tokenBy(user)`, else `byOf(user)`) and passes each tool its turn (`ToolCtx`: the talking agent and `by`), which the tools put on their activity rows (section 27).

8. `POST /api/chat/feedback {agent, value: 1|-1, reason?, at?}` records the thumb in `fblog:{scope}`, keyed by the ACTIVE BRAND's scope (chat history is per brand, so its feedback is too). The old `fb:{email}:{agent}:up|down` lifetime counters are no longer written (2026-09-21).
9. Without `ANTHROPIC_API_KEY` the chat returns a `[DEV MOCK]` message before any tool runs (`chat.ts:208`), and `generate` returns mock items (`noor.ts:171`). The batches that reach `generate` through `generateBatch` (`/api/generate`, MCP `generate_content`, `runWeekly`) still charge credits for the mock items; a routine answers `skip:mock` before its lock and charges nothing.

Cart-recovery drafts (`cart_recovery`, Noor, 5 items for 3 credits; `src/lib/cart-recovery.ts`): `generateBatch` calls `missingData` before `charge` on every batch (`/api/generate`, chat `generate_content` and `draft_items`, MCP `generate_content`, and the routines, whose cart gate has read it already); without a `storesales:{scope}` snapshot that names products left in carts they return `no_cart_data` (409 on the route) and charge nothing. `statsFor` hands the model a `CART DATA` block built from the snapshot (store, sync date, open carts, products most often left, best sellers) as escaped JSON inside `<cart_data>`, with no shopper data. The drafts are a 3-message WhatsApp sequence (1 h, 24 h, 72 h, with `{{1}}` name and `{{2}}` cart-link placeholders) and 2 posts; Nashr never sends them, the owner pastes them into the store's own abandoned-cart automation. 12. Goal, reviewer and judge (2026-09-29). Every generation and chat turn reads `memoryBlock(scope)` (`files.ts`), which opens with the owner's onboarding goal from `onboardplan:{scope}` when there is one: one line of at most 140 characters, flattened by `goalLine` so it cannot open a fake file section. The static prompt block of every agent (generation and chat) says to steer toward it and never to promise it as a result. The reviewer (`critique` in `noor.ts`) runs with `reviewerPrompt(type)`: named for the agent who owns the type, with that agent's own fit checks (`REVIEW_FOCUS`), one cached copy per agent. The reviewer and the judge both receive what the agent had, through `groundingBlocks` in `json.ts`: the batch notes as `<owner_notes>`, the memory block (goal included) as `<workspace_files>` and the WORKSPACE / STORE / CART DATA block as `<workspace_data>`, all escaped with `asData` and placed before `<items>`. ## 8. Credits: charge and refund

Files: `src/lib/credits.ts`, `src/lib/generate-batch.ts` (the one text pipeline, step 13; its callers are `api/generate/route.ts:18`, `chat.ts:294,308` (`generate_content`, `draft_items`), `api/mcp/route.ts:75`, `schedule.ts:96` and `routines.ts:241` (`routineFor`)), and `startMedia` in `src/lib/media/jobs.ts`, which the image and video routes and the chat tool `generate_image` reach through `renderImage` / `renderVideo` in `src/lib/media/start.ts`.

1. `withUserLock(email)`: spin on `lock:user:{email}` (SET NX, 10 s TTL), 60 tries at 50 ms (3 s) then throws `user_lock_timeout`. Re-reads the user inside the lock. A release that fails after the change was saved is logged, not thrown (`credits.ts:27`; the TTL frees the lock), so a throw from `charge` or `refund` always means the balance did not change there.
2. `charge(email, cost, meta?)`: fails without change when `credits < cost` (`reason: "no_credits"`, with `need`) or, with `meta`, when the agent's monthly cap would be passed (`reason: "agent_cap"`, step 9); else subtracts and saves, with `meta` also adding to the agent's counter in the same save.
3. `refund(email, n, spend?)` adds `n` back; balance is floored at 0 and deltas are truncated to integers. With the charge's result as `spend` it also lowers that agent's counter (step 9); without it, it is `adjust(email, +n)`.
4. Pattern: charge before the model call, refund in `catch` (for text batches in one place, `generateBatch`, step 13). Credits belong to the account, not the brand: every scope of one account draws from `user:{email}.credits`.
5. The lock guards only the read-modify-write of the user record and expires after 10 s. `unlock` is an unconditional `DEL` (`db.ts:87`), so a holder whose lock already expired would delete the next holder's lock.
6. Other balance writers: `renewIfDue` (monthly reset to plan allowance for non-trial plans, `credits.ts:145`), `POST /api/admin/plan` (under lock), `applyReferral` (+50 both sides), `POST /api/referral/share` (+20 per platform).
7. Writers that save the whole user record outside the lock: `PUT /api/profile` (`profile/route.ts:39`), `PATCH /api/account` (`account/route.ts:15`), `POST /api/auth/reset` (`reset/route.ts:22`). These persist the `credits` value read at request start.
8. Trial expiry (`trialOver`) is checked in `generateBatch` (`generate-batch.ts:125`) for `/api/generate`, the chat tools `generate_content` and `draft_items`, MCP `generate_content`, the weekly plan and the routines (`runWeekly` and `routineFor` also check it first, before their weekly-cap reads, `schedule.ts:87`, `routines.ts:219`), and every media path: the image and video routes and the chat tool `generate_image` all go through `renderImage` / `renderVideo` (`src/lib/media/start.ts`), which answer 402 `trial_over` before anything else. It is not checked in onboarding, catalog import or the free tools, none of which charges credits.
9. Per-agent spend and caps (2026-09-29). Attribution: a charge belongs to the agent that owns the task type (`agentForTask(type)`, computed in code, never taken from the request); an image or a video belongs to the owner of the item it illustrates; the weekly plan is Noor's; a routine's batch belongs to the owner of its type (Dana, Noor, Razan or Majed). Chat turns are never charged credits (only metered), so a cap bounds batches, drafts, images and videos, not chat. Every charging path (`/api/generate`, MCP `generate_content`, chat `generate_content` and `draft_items`, `runWeekly`, `runRoutine`, and `startMedia`, which the image and video routes and chat `generate_image` reach, step 12) reads governance BEFORE charging and calls `charge(email, cost, {scope, agent, cap: gov.agentCaps[agent]})`. Inside the same lock, `charge` refuses with `{reason: "agent_cap", spent, cap, agent}` when `spent + cost > cap`, without touching the balance; otherwise it debits and adds the cost to `User.agentSpend.by[scope][agent]` in the same `saveUser`, so parallel charges can never pass the cap. A record from an earlier month counts as empty: the month is the UTC calendar month and rolls at 00:00 UTC on the 1st, while `renewIfDue` resets the balance later, at the 05:00 UTC daily cron. Every refund after a metered charge passes the charge's result, and the counter goes down by the refund (never below 0) only while the record is still in the charge's month. `adjust` (referral and share bonuses), `POST /api/admin/plan` and `renewIfDue` never touch the counters.
10. At 100%: `/api/generate` and the image and video routes answer 402 `{ok:false, error:"agent_cap", agent, spent, cap}` before any model call; MCP `generate_content` returns a tool error (`isError`) with the same facts in a sentence, like its insufficient-credits answer; chat tools return a sentence for the model to relay and push `limit:agent_cap`, which `/api/chat` returns as `limit: "agent_cap"`; `runWeekly` and `runRoutine` return `agent_cap` (not a retry). The app's limit dialog (`LimitModal`, `limitFromError("agent_cap")`) explains the cap and links to Governance instead of billing. At 80%: the charge that crosses 80% of the cap returns `warn80`, and `warnAgentCap` (`notifications.ts`, called by every charging path) pushes one `credits` notification per brand scope, agent and month (fingerprint `agentcap80:{scope}:{agent}:{YYYY-MM}`, 35 days) naming the agent, the brand the cap belongs to (the name given to the brand, else its brand file's; the bell is per account and Governance shows the open brand, so the body says to switch to that brand) and "X of Y credits this month".
11. The owner sets the caps on the Governance page ("Monthly credit cap per agent"): one text field with a numeric keyboard per agent, empty for no cap (a field that is not a whole number blocks the save with an error instead of being dropped), with this brand's credits used this month rendered on the server from `User.agentSpend` (no request on mount), a "near the cap" badge at 80% and a "cap reached" badge at 100%. Caps and counters are per brand scope; the balance stays account-level.
12. Media credits (`startMedia` in `src/lib/media/jobs.ts`, spec A24 and A32):
    - Order: the owning agent's monthly cap against this month's count as the session read it (402 `agent_cap {agent, spent, cap}`, step 10) and the balance pre-check against the session's balance (402 `no_credits {need, have}`), flight lock `mflight:{scope}:{taskId}:{kind}` (409 `in_progress`), account limits (429 `too_many`), the trial video marker (402 `trial_video_used`), the kie create throttle or Higgsfield admission (429 `busy` / `one_open`), and only then `charge` with the owning agent and its cap (step 9), which checks both again inside the ledger lock. A request refused before the provider throttle moves none of it (one refused at the charge has already counted one kie create), and through `try/finally` no refused request keeps the flight lock. A `charge` that throws (the ledger lock timed out) answers 429 `busy` with nothing charged; a refused `charge` answers 402 `agent_cap` or `no_credits`. The 80% warning of the agent's cap (`warnAgentCap`) goes out beside the submit and never stands in its way.
    - The charge comes before the submit: the credit buys the render. The job is then saved `queued` with its open-set member and `task.mediaJob[kind]` (through `updateTask`, section 9 step 9), and all three writes settle before anything is decided. If one failed, `refundUnsaved` (`jobs.ts:228`) refunds at once through `refundOnce`, removes the member and the task pointer (restoring the `mediaLast` the start had cleared), and the route answers 502 `media_failed` with the restored balance. If that refund fails too, the charge stands and only the job can return it: the queued record, its member and the task pointer are written again, the flight lock stays held, the 502 carries no balance (`mediaResponse` sends it as `media_pending`, so the inbox never says credits were returned), and the next poll or sweep ends the job `submit_lost` with the refund three minutes on.
    - A job ends only under `mjoblock:{jobId}`, after a re-read, and never changes again. Refund once (`refundOnce`, `jobs.ts:496`) is the one path every refund takes (`failLocked` and `refundUnsaved`), so duplicate webhooks, two tabs and the sweeps refund once, a job is `refunded` only after a refund that happened, and a pass that died holding the claim delays the refund by at most a minute instead of losing it:
      1. Read `mrefund:{jobId}`. `"done"`: the refund was made, the job is recorded `refunded: true` and nothing is paid again. `"none"`: nothing is owed, `refunded: false`.
      2. Otherwise take the claim: `db.lock(mrefund:{jobId}, 60)` (`REFUND_CLAIM_S`, far past the ledger lock's worst wait). A claim another pass holds makes this one throw `refund_pending`; the caller writes nothing and the job stays open for the next poll or sweep.
      3. Holding the claim: when the account that paid still exists with the same `createdAt` (`sameAccount`), `refund(email, credits, spend)`, with the charge's agent, scope and month stored on the job (`job.spend`), so the agent's monthly counter comes down with the balance (step 9). A ledger error (not `user_not_found`) releases the claim and is rethrown, so the job stays open and a later pass retries.
      4. Replace the claim with `"done"` once `refund` has returned, or `"none"` when the account is gone or was registered again (7 days, `JOB_TTL_S`). If that write fails, the claim expires in 60 s and the job record, saved next with `refunded`, is what stops a second refund.
      5. In `failLocked` the task is written next (`updateTask`: `mediaJob[kind]` cleared and `mediaLast[kind]` set, only while the task still points at this job), and only after that the job is saved `failed`; a task write that throws leaves the job open, and the next pass finds the refund already recorded in the marker.
      6. `finalizeLocked` reads the marker before delivering (`jobs.ts:416`): any value means a fail is under way, so it finishes that fail (or throws `refund_pending` while the claim stands) and a refunded render is never delivered.
    - Same-account refunds: the job stores the account's `createdAt` (`accountSince`). When the account is gone (`user_not_found` after `wipeAccount`) or was registered again since, the job ends `failed` with `refunded: false`, the marker is set to `"none"` and no notification is sent. The same check guards the owner's analytics (`track(email, "image")`) when a render finishes: a render that finishes after the account was deleted rebuilds none of the `uev:`, `ulast:` and `ufirst0:` records `wipeAccount` removed.
    - Trial accounts keep one video, from the 12-credit models only (`TRIAL_VIDEO_MODELS`: Quick clip, Clip with sound, Photo to motion; other video models are 402 `plan_required`). `mtrialvid:{email}` (14 days) is taken at the start and deleted again if that video is refunded.
    - A finished render adds its credits to `task.mediaCredits` (`withResult` in `jobs.ts`; on a task that predates the field, an existing generated image first counts as `IMAGE_COST`), even when a newer render already replaced it on the card; reports and the founder overview read `t.mediaCredits ?? (t.image ? IMAGE_COST : 0)`. The task records the job in `mediaApplied` (the last 8) in the same write, so a finalize retried after a failed write never counts a render twice.
    - The placeholder card (no `FAL_KEY`, or `img-fast` switched off) is not charged at all; before 2026-09-29 it was charged and refunded. It never replaces artwork: `placeholder` (`src/lib/media/start.ts:47`) writes the card through `updateTask` only while the task as stored has no generated image; otherwise nothing is written and the answer is 409 `model_unavailable` (`:66`), on the route and in the chat tool ("keeps its current image. No credit was used"). The card writes `mediaCredits: 0` when the task had none, and `liteOf` does not count it as an image, so neither the reports nor the founder overview count a credit or an image for it.
13. One text pipeline (2026-09-29, `src/lib/generate-batch.ts`). `/api/generate`, the chat tools `generate_content` and `draft_items`, MCP `generate_content`, the weekly plan and the routines all call `generateBatch(user, scope, {type, notes, count?, source, via, gov?, brand?, brief?, forcePending?, settle?, by?})` with the caller's own scope (`sc(u)`, or `user.scope ?? user.email` where the scope is already on the user), and keep only their own response shapes, messages, tracking and limits. ## 9. Approval and rejection of a task

Files: `src/app/api/tasks/[id]/route.ts`, `src/components/app/Inbox.tsx:147`, `ChatPanel.tsx:31`.

1. `PATCH /api/tasks/{id} {status?, editedBody?, note?, scheduledFor?}`; session required; the change is applied with `updateTask(sc(u), id, ...)` (`tasks/[id]/route.ts:31`, step 9), so only tasks under the caller's active scope resolve (404 otherwise, `:60`). Preference notes, `approve`/`reject` tracking and the decision records (step 8) are collected inside the change and run after the response (`after()`).
2. `scheduledFor`: `null` clears, `YYYY-MM-DD` sets.
3. `editedBody` different from `body`: stored (max 20000 chars). When `gov.learning` is on, a preference note is pushed to `prefs:{scope}` and appended to `preferences.md`.
4. `status` in `approved|rejected|pending`: sets `decidedAt` on change, tracks `approve`/`reject`, and on reject with a note records a preference.
5. Any status may be moved to any other status, including after publishing. There is no separate approver role: the account owner is the only actor. Who decided is still recorded on each decision (step 8): the owner, or the founder through support access (`byOf`, section 25).
6. Brand gate (`src/lib/brand-rules.ts`): when the resulting status is `approved` and the item is customer-facing (`CUSTOMER_FACING`: social, article, whatsapp, ads, gbp, followup_seq, cart_recovery), the final text (`title` plus `editedBody ?? body`) is checked against the brand file's banned words. A hit returns 409 `{error: "brand_violation", violations}` and nothing is saved. Saving an edit as `pending` is allowed. Matching folds Arabic diacritics, tatweel and letter variants, accepts the Arabic prefixes و ف ب ل ك ال and suffixes for Arabic terms of three letters or more, and requires whole words for Latin and shorter terms. The inbox runs the same function in the browser to label cards and to check the editor as the owner types.
7. Auto-approval goes through `initialStatus(autoApprove, brand, item)` at every creation site (`api/generate`, `api/mcp` `generate_content`, chat `generate_content` and `draft_items`, the weekly schedule): an item that breaks a rule is created `pending` even when its type is auto-approved, and the chat tool reports how many were held.
8. Decision records (2026-09-29, `src/lib/decisions.ts`). The route works out the request's human decisions inside its `updateTask` change, from the task as stored (step 9), and after the task is saved appends them to `decisions:{scope}` (scope from `sc(u)`, never from the body): `edit` when the stored text changes (re-saving the same edit adds nothing; `editPct` uses `editPctOf`, the light index's measure), then `approve`, `reject` or `reopen` (back to `pending`) when the status changes. The owner's typed `note` goes on the rejection, or on the edit when nothing was rejected, cut to 300 characters. Each record carries `by`, who decided (`byOf(u)`, `src/lib/actor.ts`, worked out from the session in the route's first `Promise.all`, before the response and before `after()`, never from the body; section 25 step 1), the owning agent from `agentForTask(type)`, the title (80) and the judge's score and automatic-fail code at that moment. Records are written whatever `gov.learning` says, and read back into the owning agent's prompts only while it is on (section 7 step 13); a request stopped by the brand gate records nothing; items created approved by `initialStatus` never appear. Tracking, decision records and preference notes go out in one `Promise.all` inside `after()`; `preferences.md` is then read and rewritten as before. `recordDecisions` also writes one `decision` activity row per record in the same round (section 27; not for `publish`).
9. Whole-task writes (`updateTask`, `src/lib/brand.ts:283`): `saveTask` replaces the whole task, so a writer that saves a copy it read before slow work erases whatever landed meanwhile, a render that finished by poll, webhook or sweep included. Every writer of an existing task goes through `updateTask` instead: the approve and edit route (`tasks/[id]/route.ts:31`), the publish route (`publish/[id]/route.ts:38`), the chat tool `publish_item` (`chat.ts:374`), the judge's scores (`judge.ts:140`), the placeholder card (`src/lib/media/start.ts:63`) and every task write of the media engine (the start's pointer `jobs.ts:182`, the start's cleanup `:234,244`, finalize `:457`, fail `:541`). Each one:
   1. takes `tasklock:{scope}:{id}` (SET NX, 10 s TTL), trying 60 times 50 ms apart, else throws `task_lock_timeout`;
   2. re-reads the task; a task deleted meanwhile returns null and is not recreated;
   3. runs the writer's `mutate` once on a copy of the stored task, which applies only that writer's fields (or returns null to save nothing, as the brand gate does on a 409, the placeholder does over artwork, and the engine does when the task no longer points at its job or, at finalize, already took it in `mediaApplied`);
   4. saves through `saveTask` (pending set and light index follow) and releases the lock; a release that fails is logged, not thrown, and the TTL frees the lock.

   Creation sites (`/api/generate`, MCP `generate_content`, the chat tools, the weekly schedule and the routines, all through `generateBatch`, section 8 step 13; MCP `save_draft`) still call `saveTask(..., true)` for new tasks; the decision records (step 8) are an append-only list, not a task write. The scope is always the caller's `sc(u)` or the one stored on the media job. So a clip that finishes during a publish, an approval, an edit or a judge run keeps its media and credits, and an approval landing during a finalize keeps its status.

### OAuth 2.1
1. Discovery: `/.well-known/oauth-authorization-server` and `/.well-known/oauth-protected-resource` (rewrites). Issuer and endpoints derive from `APP_ORIGIN`.
2. Client registration: `POST /api/oauth/register` is open to anyone. Keeps up to 10 `http(s)` redirect URIs, issues `client_id`, and a `client_secret` only when `token_endpoint_auth_method = client_secret_post`. Rate limited to 30 per IP per hour (429 `slow_down`); no expiry.
3. Authorize: `/oauth/authorize?client_id&redirect_uri&response_type=code&code_challenge&code_challenge_method&state&scope`. Anonymous users are redirected to `/ar/app/login?next=...`. The page checks client, exact `redirect_uri` membership, `response_type=code`, presence of `code_challenge`; shows Allow/Deny with the client name supplied at registration.
4. Approve: `POST /api/oauth/approve` (form post, session required) re-validates client and redirect URI, requires `code_challenge_method=S256`, issues a 10 min single-use code bound to client, redirect URI, challenge, email and `scope` (free text from the request, default `noor`). Deny redirects with `error=access_denied`.
5. Token: `POST /api/oauth/token` (JSON or form; client auth via Basic, body secret, or none for public clients; a secret is compared with `sameSecret`; 60 requests per IP per 15 minutes, checked first, 429 `slow_down`). `authorization_code`: code is deleted on first read, then client id, redirect URI and PKCE S256 are verified. Issues access token `nashr_...` stored in `mcptoken:{access}` for 30 days and refresh token `nashr_r_...` in `oauthrefresh:` for 90 days.
6. Refresh: `grant_type=refresh_token` rotates: the old refresh token is deleted and a new pair is issued; client id must match. The previous access token stays valid until its own TTL.
7. There is no revocation endpoint and no listing of granted clients. `revokeMcpToken` only removes the personal token.

### MCP calls
`POST /api/mcp` JSON-RPC. `initialize`, `ping`, `notifications/initialized`, `tools/list` answer without authentication (`mcp/route.ts:64-66`). Everything else needs `Authorization: Bearer nashr_...` resolved by `userFromBearer` (`mcp.ts:25`), which refuses a suspended account and sets `scope` from the active brand like a browser session. Tools: `ask_noor` (full chat loop with all nine chat tools, including `publish_item`), `generate_content` (charges credits, no trial-expiry check), `list_inbox`, `read_file`, `list_files`, `get_brand_rules` (the active brand's tone, dialect, audience, products, offers, preferred words, channels and the enforced banned words as JSON; free), `check_brand` (`{text, type?}`, up to 20,000 characters, checked with the same `gateTask` as the approve button; returns `pass`, `violations` and a summary; internal types are not held; free, no model call), `save_draft` (below).

### MCP `save_draft` (2026-09-29): drafts from the owner's own assistant
Lets an owner write with their own Claude or ChatGPT subscription and still review in Nashr. `{type, body, title?, channel?, notes?, lang?}`, one item per call (`src/lib/external-drafts.ts`):
1. `parseDraft` validates before anything is read or written: `type` must be in `TASK_TYPES` (`isTaskType`, so `constructor` and friends fail); `body` is required, at most 20,000 characters; `title` at most 200 (defaults to the body's first line, 80 characters); `notes` at most 500 (kept as `brief`); `channel` a lowercase `[a-z0-9_-]{1,30}` name (defaults to the type); `lang` `ar` or `en` (defaults to the brand's first language). Control and bidi-override characters are stripped. A field over its limit is refused with a tool error, never truncated. Any other argument (`scope`, `email`, `id`) is ignored.
2. `draftAllowed(user.email)` (`rate.ts`): 30 an hour and 150 a day per account, across its brands. Over the limit: tool error, nothing saved.
3. The brand of `sc(u)` (the bearer's active brand, set by `userFromBearer`) is read; without one: tool error, nothing saved.
4. The brand gate runs in code (`gateTask`, the approve and publish routes' check). Status is `initialStatus(false, ...)`, i.e. always `pending`: the owner's auto-approval does not apply to text the owner has not seen in Nashr. A draft that breaks a rule is saved anyway, held like an agent's draft (the inbox names the rule, `PATCH /api/tasks/{id}` refuses to approve it with 409, publish refuses it), and the tool answer returns `brandCheck.violations` so the assistant can fix and save again. This matches every other creation path, which keeps a violating item pending rather than dropping it.
5. `saveTask(sc(u), task, true)` with `source:"external"` (ad and social types get an ad code there, as on every path). No credits, no model call, no judge, no trial-expiry check (like `check_brand`, it spends nothing).
6. Answer: JSON with `saved`, `id`, `status`, `type`, `channel`, `title`, `brandCheck` and `credits: 0`. 401 responses carry `WWW-Authenticate` pointing at the resource metadata. CORS is `*`.

## 16. Scheduled jobs

See `architecture.md` 2.6 and 4(d). Details:

- Daily (`src/app/api/cron/daily/route.ts`): per (user, active brand): `renewIfDue`; if no brand and account older than 10 min and email configured, a one-time nudge email (`notified:{email}:nudge1`); else `runLifecycle` (day 1, 2, 3, 10 emails, once each), `runDaily` (brief stored at `brief:{scope}`, no model call), `followUps` (notifications with fingerprints), and an email according to `profile:{email}.emails` (`all|important|none`). Links in the nudge and brief emails use a hard-coded production origin (`:29`, `:46`).
- Weekly (`src/app/api/cron/weekly/route.ts`, `schedule.ts` `runWeekly`): skips when no brand, `weeklyPlan` off, trial over, weekly cap reached (`gov.weeklyCap`, counts `source:"scheduled"` tasks in 7 days, the routines' included), Noor's monthly credit cap reached in that brand (`agent_cap`) or insufficient credits (`no_credits`); the batch itself goes through `generateBatch` (section 8 step 13, `via:"weekly"`), which reads Noor's preferences, memory, data block and feedback inside the refunding try. Response body maps account email to result string.
- Golden (`cron/golden/route.ts`, `golden.ts`): fixed fictional brands, meters usage under `golden@nashr.internal`, notifies founder accounts on regressions. Each run records its prompt versions and tags a regression line "(prompt changed)" when that agent's prompts changed since the previous run (section 26).
- Media (`cron/media/route.ts`, `20 5 * * *`, `maxDuration = 300`): `sweepMedia(mediaDeps(), {deadline})` with no job limit; section 23 step 9. Not a step of the daily cron, whose per-workspace budget cannot hold an advance that may take most of a minute.
- Opportunistic media sweep: the image, video and poll routes schedule `maybeSweep` in `after()`; it runs `sweepMedia` with at most 6 jobs, only when it wins `msweep` (300 s) and at least 30 s of the request's deadline are left.
- Routines (`src/app/api/cron/routines/route.ts`, `src/lib/routines.ts`, 2026-09-29), daily at 06:00 UTC, after the 05:00 daily job has renewed credits. Four routines, each for an agent with real input data: `dana_weekly_report` (Dana, `weekly_report`, weekly), `noor_cart_recovery` (Noor, `cart_recovery`, weekly), `razan_cash_forecast` (Razan, `cash_forecast`, monthly) and `majed_monthly_review` (Majed, `strategy_review`, monthly). The other agents have none until they have a data source. All are off by default; the owner turns each on per brand on the Scheduled tasks page (`PUT /api/schedule {routines: {id: boolean}}`, only known ids with boolean values, merged per id into `schedule:{scope}.routines`). There is no "Run now" for a routine.
  1. Items: `dueRoutines(allUsers())` reads every (user, active brand) schedule in parallel, then the last runs of the routines that are on, and keeps those that are on and have not run in their period (the UTC week from Sunday, `weekStartUtc`, or the UTC month, `monthKey`). `runCronBatch` with job `routines`, period = today's UTC date, id `{scope}:{routineId}`, four at a time, no new item after 160 s, markers for 2 days. One item is one generation. A missed day needs no catch-up route: the next day's run asks again and the period check decides. The batch's attempt count is per day, so charges left by killed runs are bounded by the runner's own count per routine and period (step 4).
  2. `runRoutine(user, id)` in this order: brand (`no_brand`); switched on (`off`); not yet run in its period (`routinelast:{scope}:{id}`, `already_this_period`); model state (`retry:paused` while paused, `skip:mock` without a key, since placeholders must never be charged); lock `routinelock:{scope}:{id}` (300 s, `retry:locked`); trial (`trial_over`); the last run read again under the lock; the gate; the weekly cap and the batch's hold; the attempt count (`attempts_exhausted`); the charge. The hold is deleted and the lock released in a `finally`, after the batch is saved.
  3. Gates, checked in code; a gate that fails answers `idle` or `no_data`, charges nothing and is final for the day (the next day's run asks again). Only Noor's gate asks for data newer than the routine's last run; Razan's and Majed's look at a fixed window, so they can run again in the next month on the same sync or decisions. Dana: an item the owner created or any decision in the last 7 days (light index `createdAt`/`decidedAt`, newest decision record), or a store sync (`storesales:{scope}.at`) or an ad-account read (`adsync:{scope}:{provider}`) in the last 7 days; items the weekly plan or a routine created on their own do not count, or the routines would keep each other busy for an absent owner. Noor: abandoned-cart data (`missingData` is null, else `no_data`) synced after the routine last ran (else `idle`). Razan: a store sales snapshot from the last 35 days (else `no_data`). Majed: decisions on at least 3 different items in the last 30 days, from the decision records or the light index's `decidedAt` (else `idle`).
  4. Weekly cap: the `source:"scheduled"` items of the last 7 days, plus the batches the brand's other routines hold right now (`routinehold:{scope}:{id}` = their `TASK_COUNT`), plus this batch's `TASK_COUNT` must not pass `gov.weeklyCap` (`cap_reached`); the weekly plan and the routines share it. The cron runs a brand's routines side by side, so this check and setting the routine's own hold (360 s) happen under a short lock per brand (`routinecap:{scope}`, waited for up to about 2 s, else `retry:locked`); holds are read before the items, and a run deletes its hold only after its batch is saved (in `runRoutine`'s `finally`), so every batch is counted once in one of the two. Then the attempt count `routinetry:{scope}:{id}:{period}` (8 or 35 days) is raised before the charge and lowered again when the charge is refused or refunded; a platform kill leaves it raised, and once two such charges are left in the period the routine answers `attempts_exhausted` (final for the day, nothing charged) until its next period. Then `charge(email, TASK_COST[type], {scope, agent, cap: gov.agentCaps[agent]})` (`agent_cap`, `no_credits`) and `warnAgentCap`.
  5. The charge, the refund and the save go through `generateBatch` (section 8 step 13, `via:"routine"`, with the routine's attempt as `settle`). Inside the refunding try, one round: `listPreferencesFor`, `memoryBlock`, `statsFor(type)` (Dana and Majed: WORKSPACE DATA, plus STORE DATA when a store was synced; Noor: CART DATA; Razan: STORE DATA) and `feedbackFor`; then `generate` with the routine's note. A throw refunds with the charge's receipt, lowers the attempt count and is rethrown (the cron counts a failed attempt).
  6. The batch is saved in one parallel round with `source:"scheduled"` and `brief` = the routine id, judged with the same grounding (`judgeLater`), `routinelast:{scope}:{id}` is set, and one `pending` notification goes to the account (fingerprint `routine:{scope}:{id}:{period}`, 8 or 35 days). The answer is `ok:N`.
  7. The outcome of every run that took the lock is recorded in the activity log (`recordRun`, section 27 step 3); the Sunday plan's the same way, `via:"weekly"`.
- Users can trigger their own runs: `POST /api/schedule {run:"weekly"|"daily"}`. A weekly Run now passes the owner's `byOf(u)`, so its rows name the owner; the cron's are the system's.

## 20. Campaign results import (CSV)

Files: `src/lib/perf-import.ts`, `src/lib/perf-store.ts`, `src/app/api/performance/route.ts`, `src/components/app/PerformanceImport.tsx` (on the reports page).

1. The owner exports an ad-level report (Meta, Snapchat, TikTok, Google Ads, or an email tool) and drops the CSV on the reports page. The browser reads the text (2 MB at most) and posts `{csv, file, metric?}` to `POST /api/performance`.
2. `readRows`: RFC 4180 parse with the delimiter detected from the header; the header is the first of the first twelve rows naming two known columns (English or Arabic synonyms, most specific first: "link clicks" before "clicks"); totals lines are skipped; at most 5,000 rows. Names and text are stripped to one plain line (`clean`). Missing name column or metrics: 422 with a reason code.
3. `analyze`: the metric defaults to what the file supports (ROAS, then cost per result, CTR, open rate, conversion rate) and can be switched. A row is ranked only above the metric's sample minimum (500 impressions for CTR, 30 clicks for cost per result, 50 spend for ROAS, 30 clicks for conversion rate, 100 sends for open rate). Findings: top and bottom three, best against the median, wording patterns (offer, number, question, Arabic, short) compared by pooled metric when both groups have three or more ads and differ by 20% or more, best and weakest placement, and spend with no result when it is 10% or more of spend. Confidence is "medium" at ten times the sample minimum with five or more ads, otherwise "low"; never "high".
4. `savePerf` stores the snapshot in `perfimport:{scope}` and writes `performance-learnings.md`, which `memoryBlock` includes, so every later generation, the weekly plan included, reads it. The file states that quoted names are data, not instructions, and that findings are comparisons, not promises. The reports card links to chat with prompts to write variants of the winners or plan next week.
5. No model call and no credits. `DELETE` removes the snapshot and the file.

Images for `IMAGE_TYPES` (social, ads, gbp, whatsapp, cart_recovery), video for `VIDEO_TYPES` (social, ads), both checked on the server. Aspect: 9:16 for video and for the TikTok and Snapchat channels, 1:1 otherwise (`aspectFor`).
2. What is offered (`modelAvailable` in `src/lib/media/config.ts`): the provider's keys (`FAL_KEY`; `KIE_API_KEY`; both Higgsfield keys); the Blob store for kie and Higgsfield, whose results are deleted after 1 to 14 days while posts are published by URL later (fal works without it and hot-links); the model listed in `MEDIA_MODELS_ON` (`img-fast` is always on; unset means `img-fast` only); and not switched off in `media:off`. The inbox page reads `availableModels(undefined, await offModels())` per request and passes it to the inbox with the balance, the plan and `paused`; the start routes check the same things again. When the default image model is unavailable, the image route and the chat tool fall back to the placeholder card, uncharged, and only onto an item without artwork: the card is written through `updateTask` on the task as stored, and an item that already has a generated image (or gets one from another image style while the placeholder waits for the task lock) keeps it, with 409 `model_unavailable` and nothing written (`placeholder`, `src/lib/media/start.ts:47-69`; section 8 step 12); an image of another style that finishes after the card was written replaces the card, because the card leaves `task.mediaJob` as it was. The inbox follows the same rule (`MediaControls.tsx`): with no image model offered, an item with artwork keeps its image button closed with the `keepsImage` note, and a 409 `model_unavailable` to a request sent without a model shows that note too.
3. Start (spec 4.4 A): `architecture.md` section 4(e) steps 1-4, and section 8 step 12 here for the credits. Deadline: `deadlineFor(maxDuration)` = start + `maxDuration` × 1000 − 15 s. Each step takes `min(its maximum, time left)`: prompt 20 s; submit 45 s for fal (keeping 25 s for the copy) and 20 s for kie and Higgsfield; status 15 s; download 15 s (image) or 45 s (video); put 20 s or 30 s. No step starts below its minimum (a submit with less than 5 s left is not sent, and the credit comes back). The chat tool works to the chat request's own deadline: `deadlineFor(300)` counted from the start of `chat()` (`CHAT_MAX_DURATION_S`, the `maxDuration` of `/api/chat` and `/api/mcp`, pinned by a test), or `opts.deadline` when the route passes one; with less than 60 s of it left (`CHAT_RENDER_MIN_MS`) it starts no render and charges nothing.
4. Reference image (spec A9, A26, `mediaImageFor`): only our Blob copy of a real generated image (`hasArtwork` and `isOurBlobUrl`) is ever sent to a provider, and only to the models that build on it. Video takes it as a first frame only when it is portrait (TikTok and Snapchat posts); with a square image the clip is text-to-video at 9:16, except Photo to motion, which needs the image whatever its shape (the inbox says the clip keeps the photo's square shape, `squareClip`).
5. Prompts (spec 4.5, `src/lib/media/prompts.ts`). With Claude on: one Sonnet call (`claude-sonnet-5`, `max_tokens` 400, effort low, `{timeout: min(20 s, time left), maxRetries: 0}`), metered as `image_prompt` for images and video alike; the text style asks for one English headline of at most 6 words and no Arabic lettering, and video prompts forbid speech, dialogue and voice-over. On a failure, an empty reply, less than 3 s left, or while paused: the fixed template (section 7 step 11). The `img-text` template quotes the brand name only when it is plain Latin text, else it is the design template; the task title never reaches it. The prompt is shown under the image or the clip.
6. Poll (spec 4.4 E). `pollJob` in `MediaControls.tsx` asks `GET /api/media/{jobId}` every 3 s (image) or 6 s (video) for the first 2 minutes, then every 15 s; a failed request (a 429, any other error answer, or a network error) doubles the gap up to 30 s. Past the model's max age plus 2 minutes (`GRACE`) the card shows the `stillRendering` note once and keeps asking once a minute (`LATE_GAP`) until the server settles the job: only `done`, `failed`, a 404 or a 401 ends the loop. The running job is found through `task.mediaJob[kind]` as well as the click, so a reload resumes polling; after a 409 `in_progress` that named no job, the card re-reads the task at 4, 12 and 30 s (`RECHECK_GAPS`) and then stops. The route answers `{ok, job}` plus `task` when done and the account's `credits` when failed; `publicJob` carries no email, scope or prompt, and `queued` reads as `running`.
7. `advance` (`jobs.ts`): a terminal job returns as it is. A `queued` job belongs to its start request for 3 minutes (longer than any route deadline); after that, with the job lock free, it fails `submit_lost` and is refunded. Otherwise a status call needs the `mpoll:{jobId}` throttle (4 s; skipped only by the sweeps' `force`) and the job lock `mjoblock:{jobId}` (120 s), held through finalize or fail, so two tabs, webhooks and sweeps cannot multiply provider calls and a job being copied gets none. A job holding `resultUrls` is copied without a status call. `pending` past the max age (image 10 minutes, video 30) is cancelled (Higgsfield, best effort) and fails `timeout`; `done` is finalized when the deadline leaves room (25 s for an image, 60 s for a clip), else kept for the next poll; `failed` ends `nsfw` or `provider_failed`. Every fail goes through `failLocked`, which refunds through `refundOnce` (section 8 step 12) before it writes the task and then the job; while another pass holds the refund claim it throws `refund_pending` and the job stays open.
8. Finalize and storage (spec 4.6, A25). `copyToBlob` downloads the result through `safeFetch`, caps it (image 25 MB, video 100 MB), checks the magic bytes, re-encodes images with `sharp` (rotated upright, transparency on white, fitted inside 1440×1920, JPEG quality 88) and stores MP4 unchanged under `media/{32 hex}`. A failed copy keeps the result on the job (`resultUrls`) and is retried by later polls or sweeps without another status call, at least 30 s apart, 3 tries in all; then `store_failed`, refunded, with the provider's cost recorded. The engine checks the 30 s itself (`copyWaits`): the `mpoll` lock holds polls back, and a sweep's `force`, which skips that lock, still waits. On delivery the task is written first (`updateTask`, `jobs.ts:457`) and only then the job is saved `done`; a failed task write leaves the job `running` with its `resultUrls`, so the next poll or sweep copies and delivers it instead of a done job the task never received. `withResult` (`jobs.ts:400`) adds the job's credits to `mediaCredits` and appends the job id to `mediaApplied` (the last 8, `APPLIED_KEEP`) in the same write, and returns null (nothing saved) for a job already in that list, so a retry after a write whose index half was lost never counts the render twice. fal keeps its own URL when the copy fails (the hot-link used before Blob). The task gets the media fields only while `task.mediaJob[kind]` still points at this job, so a late, older job never overwrites a newer render.
9. Webhook (spec 4.4 D, A30): `architecture.md` section 4(e) step 6. Sweeps (spec 4.4 F, A3): `sweepMedia` reads the three open sets with one `Promise.all`, loads the jobs with `pmap` (8 at a time), removes members that are gone, terminal or unparseable, and force-advances jobs older than 2 minutes or holding `resultUrls`, oldest first, 4 at a time, starting none with less than 20 s left (section 16 for the two callers).
10. Higgsfield admission (spec A10, `hfAdmission`): every tenant shares one Higgsfield account, so only live jobs count (not terminal, inside their max age, no result waiting to be copied). At the cap the start first force-advances stale open jobs (at most 4, behind `mhfclean`, 60 s, status calls only). Then at most 1 live Higgsfield job per account (429 `one_open`) and 2 in all (`HF_MAX_OPEN`), of which at most 1 a video (429 `busy`). The check is not atomic; Higgsfield's own concurrency refusal is `busy` too, refunded at once.
11. Breaker (spec A22, `trip` and `setOff`): 3 `store_failed`, `timeout` or defect-class `submit_failed` (`rejected`, `bad_response`) of one model within an hour switch it off for 6 hours; a kie render whose `creditsConsumed` exceeds 110 % of `EXPECTED_KIE_CREDITS` switches its model off for 6 hours (the owner keeps that render); a `no_balance` answer switches every model of that provider off for 1 hour. A switched-off model is refused (409 `model_unavailable`, or the placeholder for `img-fast`) before any charge and left out of the inbox. Entries clear themselves at `until`, or when `media:off` is deleted.
12. Notifications (spec A28): a job that ends through a webhook or a sweep (`via` `hook` or `sweep`) tells the owner with `pushNotif` (kind `info`), in the language stored on the job: ready, or did not finish with the credits returned. Only the account that was charged, and only while it exists with the same `createdAt`. A failure also leaves `task.mediaLast[kind] = {error, credits, refunded, at}` on the card until the next render of that kind starts.
13. Chat tool `generate_image`: the default model only (spec A2), through `renderImage`, with the deadline of step 3. Its answers name the outcome: not started because the reply has run too long (no credit used), a placeholder with no credit used ("not available right now", since the breaker may have switched the default model off), no image model while the item already has artwork ("keeps its current image. No credit was used"), trial ended, insufficient credits, wrong item type, already being drawn, busy ("try again in a minute. No credit was used."), the account limit (30 an hour, 150 a day), a content refusal or any other failure, saying the credit was returned only when the engine's answer carries the refunded balance (otherwise that a credit taken is returned on its own within a few minutes), still being drawn ("will appear in the inbox shortly"), or generated with the balance. `list_inbox` marks items with `(has image)` and `(has video)`. MCP has no media tool of its own, but its `ask_noor` runs this chat loop, so it reaches `generate_image` under the same rules and deadline.
14. Video in the inbox: a preview with a poster frame (`#t=0.1`), save or share (`navigator.share` with files, else a `?download=1` link on our Blob host), and `videoNoPublish` under every clip.
15. Retention. Blob files and images hot-linked at fal.ai survive account deletion: `wipeAccount` does not touch them (a follow-up in the spec, section 9). The job records (`mjob:`, 7 days from the last save), the webhook pointers (`mjobref:`, 7 days), the trial marker (`mtrialvid:`, 14 days), the flight locks and the per-account render counters expire by TTL, so the render records of a deleted account are gone within 14 days. The privacy policy and the help centre say this.

On main there is no teams actor: the owner is `{kind: "owner", email}`, and while the founder's support access is on it is `{kind: "founder", email, imp: "founder"}`. Support access needs two things: the `nashr_impersonate` cookie equals the account's email (section 14 step 5), and something the owner cannot forge backs it, the founder's own session saved in `nashr_return` (a 64-hex token whose `session:` record is live and belongs to a founder account, `isFounder`) or the admin key cookie (`nashr_admin`, `sameSecret`). 4. 5. Retention: `wipeAccount` deletes `govhist:{s}` and `govlock:{s}` for every brand. Until then a revision keeps the email in its `by` (a member's, once teams exist).

## Revocation (2026-09-18)

- Password change (`PATCH /api/account`): new hash and `sessionsAfter = now` saved inside the user lock, the caller's session is destroyed and a new one issued. Every other session of the account fails at its next request.
- Password reset (`POST /api/auth/reset`) and founder `resetPassword`: the same, plus `revokeAllMcp` (personal MCP token and every OAuth grant).
- Connected apps: `GET /api/mcp/grants` lists OAuth grants of the signed-in account; `DELETE /api/mcp/grants?id=` revokes one, `?all=1` all. A grant id of another account is a 404. Refreshing a token keeps the grant and deletes the previous access token.
