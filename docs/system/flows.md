## 1. Signup (email first, then name and password)

Files: `src/app/[lang]/app/signup/page.tsx`, `src/components/app/AuthForm.tsx:17-72`, `src/app/api/auth/signup/route.ts`, `src/lib/auth.ts`, `src/lib/referral.ts`, `src/lib/track.ts`.

1. Page redirects an already signed-in user to `/{lang}/app` (`signup/page.tsx:11`).
2. Client step 1: email is validated with `^[^\s@]+@[^\s@]+\.[^\s@]+$` (`AuthForm.tsx:34`). Step 2 asks for name and password; the client requires length >= 8, one letter, one digit (`AuthForm.tsx:30`). Query params read: `ref` (referral code), `url` (site for onboarding), `next` (must start with `/` and not `//`, `AuthForm.tsx:24`).
3. `POST /api/auth/signup` with `{email, name, password, lang, ref, phone?}`.
4. Server: rate limit 5 per IP per hour (429 `slow_down`); normalizes email (trim, lowercase); `validEmail` (the address regex, and no `:` or `#`); `strongPassword` (8+, a letter, a digit); optional phone needs >= 9 digits. Then, inside `withLoginLock(email)` (`lock:login:{email}`, the lock invite acceptance takes too), `getLogin(email)`: an owner account or a member login at the address gets 409 `exists`, the same answer for both (2026-09-29); otherwise `createUser`.
5. `createUser` (`auth.ts:155`): bcrypt cost 10, plan `trial`, 50 credits, `trialEnds` = now + 3 days, name clipped to 80 chars. Writes `user:{email}`, adds to `users:all`. It also stamps `sessionsAfter` = `createdAt`, so a session issued for an earlier account at the same address never works again. Member logins are never created here (section 26).
6. `registerCode` writes `ref:{CODE}`. If `ref` matches `^[A-Za-z0-9]{6,10}$`, `applyReferral` runs (section 15).
7. `createSession(email)` sets cookie `nashr_session`. `track(email,"signup")`.
8. Client navigates to `next`, or `/{lang}/app/start?url={url}` when a site URL was carried (the owner reviews and confirms it there before anything is read, section 6), else `/{lang}/app/start`. A carried URL never starts onboarding by itself: until 2026-09-28 it went straight to `/{lang}/app/chat?onboard={url}`, so a link like `/en/app/signup?url=attacker.example` chose the new workspace's brand.
9. Rate limit 5 per IP per hour; no email verification, no CAPTCHA on this route.

## 2. Login

Files: `login/page.tsx`, `AuthForm.tsx:74-107`, `src/app/api/auth/login/route.ts`.

1. `POST /api/auth/login {email, password}`.
2. Rate limits 20 per IP and 8 per login per 15 min (429 `slow_down`). `getLogin(email)` finds the login: the owner record `user:{email}` or a member record `member:{email}` (the owner record wins should both exist). bcrypt compares against THAT login's own hash, so the owner's password never opens a member login and a member's never opens the owner's. Unknown login or bad password: 401 `invalid` (same response for both).
3. Owner: 403 `suspended` (only after a correct password). Member (2026-09-29): 401 `invalid` when the owner record is missing, `memberOf` does not name it, or the member was accepted before the owner record was created; 403 `suspended` when the owner is suspended; 403 `disabled` when the member is paused by the seat limit (section 26 step 13).
4. `createSession(login email)`, `track(owner email, "login")` (analytics count accounts), `{ok:true}`. Client goes to `next` (same `/` and not `//` rule) or `/{lang}/app`. Every later request resolves a member session to the owner's account again (section 5).
5. No lockout beyond the rate limits.

## 3. Logout

`src/components/app/LogoutButton.tsx` posts to `POST /api/auth/logout` (`src/app/api/auth/logout/route.ts`), which calls `destroySession()` (`auth.ts:241`): deletes `session:{token}` and the `nashr_session` cookie. It does not touch `nashr_admin`, `nashr_return` or `nashr_impersonate`.

## 4. Password reset

### Forgot
Files: `forgot/page.tsx`, `AuthForm.tsx` (`ForgotForm`), `src/app/api/auth/forgot/route.ts`, `src/lib/notify.ts`, `src/lib/rate.ts`.

1. `POST /api/auth/forgot {email, lang}`. Bad email format: 400.
2. Rate limits: 8 per 15 min per IP and 3 per 15 min per email. When exceeded the route still answers `{ok:true, mail}` (`forgot/route.ts:29`).
3. `getLogin(email)`. When the login exists and mail can reach a customer (`mailReady()`: `RESEND_API_KEY` and `MAIL_FROM` both set): a 32-byte hex token is generated, its SHA-256 is stored as `pwreset:{hash}` with `{email, kind}` (`kind` is `owner` or `member`) for 3600 s, and a link `${ORIGIN()}/{lang}/app/reset?token=...` is emailed to the login's own address. A member whose owner record is gone gets no link and the same answer.
4. Response is always `{ok:true, mail:boolean}`; `mail` says whether email delivery is configured, not whether the account exists. The forgot page shows a WhatsApp link when `SUPPORT_WHATSAPP` is set.

### Reset
Files: `reset/page.tsx`, `AuthForm.tsx:148-178`, `src/app/api/auth/reset/route.ts`.

1. `POST /api/auth/reset {token, password}`. Rate limit 10 per 15 min per IP (429).
2. Password rule server-side: length >= 8, one Unicode letter, one digit. Token must match `^[a-f0-9]{64}$`.
3. Looks up `pwreset:{sha256(token)}`. Missing: 400 `bad_token`. Single use: `pwresetuse:{hash}` is taken with SET NX (1 h) before the record is deleted, so two requests racing on one link cannot both pass (the second gets 400 `bad_token`).
4. `getLogin(record.email)`: the login must still be of the kind the record names (a record without `kind`, written before teams, is an owner's), else 400 `bad_token`, so a member removed since, or an address that changed sides, gets nothing. A suspended owner (for either kind) gets 403 `suspended`; the token is spent either way.
5. Owner: the new hash, `revokeSessions` and `revokeTeamSessions` in one save inside `withUserLock`, then `revokeAllMcp` and `createSession(owner)`. Every owner session, every member session and every MCP token dies with the old password; each member signs back in with its own.
6. Member (2026-09-29): under `withMemberLock` the member record alone gets the new hash and `sessionsAfter = now`, which signs out that member's other devices; the owner's hash, sessions and tokens are untouched. Then `createSession(member)`, unless the member is seat-paused: the password is set but the answer is 403 `disabled` with no session.

### Change password while signed in
`PATCH /api/account {currentPassword, newPassword}` (`src/app/api/account/route.ts`): session and `forbid(u, "password.change")` (every login; refused to a founder impersonating); `strongPassword`; the current password is checked against the ACTING login's own hash, never the account's for a member (401 `wrong_password`). Owner: new hash and `revokeSessions` inside the user lock, then `revokeAllMcp`. Member (2026-09-29): the member record only, under `withMemberLock`, with its own `sessionsAfter = now`; the owner's hash, sessions, MCP token and connected apps are untouched. Either way this device's session is destroyed and a new one issued for the same login, so only the other devices are signed out.

## 5. Session handling and cookie names

| Cookie | Set by | Value | Attributes | Lifetime |
|---|---|---|---|---|
| `nashr_session` | `createSession` (`src/lib/auth.ts:233`), `api/admin/impersonate/route.ts` (restores the founder's saved token) | 32-byte hex token; server side `session:{token}` holds `{email, at, imp?}`: the LOGIN email (owner or member), the issue time, and on an impersonation session the founder behind it (`imp`) | httpOnly, sameSite lax, `Secure` unless plain http to the loopback interface, path `/` | 30 days (cookie and Redis TTL); 2 hours for an impersonation session |
| `nashr_admin` | `api/admin/login/route.ts:19` | The raw `WAITLIST_ADMIN_KEY` value | httpOnly, lax, secure in production | 30 days |
| `nashr_return` | `api/admin/users/[email]/route.ts:116` | The founder's own session token, saved while impersonating | httpOnly, lax, secure in production | 2 hours |
| `nashr_impersonate` | `api/admin/users/[email]/route.ts:117` | Email of the impersonated user (display and audit only; `byOf` never reads it: who acted comes from the session record's `imp`) | httpOnly, lax, secure in production | 2 hours |
| `nashr_lang` | `src/components/LangToggle.tsx:8` (client JS) | `ar` or `en` | not httpOnly, lax | 1 year |

`currentUser()` (`src/lib/auth.ts:248`, `resolveSession`; rewritten 2026-09-29): cookie, `session:{token}`, then in one parallel round `user:{login}`, `member:{login}` and `activebrand:{login}`.

- Owner login (`user:` exists; it wins should both exist): `null` when suspended or when the session predates `sessionsAfter`. Otherwise the record with `brandId`, `scope` and actor `{kind:"owner", role:"owner"}`, or `{kind:"founder", role:"owner", impersonating: imp}` when the session carries `imp`.
- Member login: `null` when the member is disabled, its role or `memberOf` is malformed, the session carries `imp`, or the session predates `member.sessionsAfter`. Then the owner record and the owner's brand list are read in one round, and `null` again when the owner is missing or suspended, the session predates `owner.teamSessionsAfter`, or the member's `acceptedAt` is earlier than the owner's `createdAt`. Otherwise the OWNER's record with actor `{kind:"member", email, name, lang, role}` and scope `scopeFor(owner, brandId)`, where `brandId` is the member's own active brand when it is one of the owner's active brands, else `default`.

Membership is re-read on every request; a session never caches the owner. `saveUser` strips `actor`, `scope` and `brandId`. Sessions are not rotated and not bound to IP or user agent; they stop working through the revocation stamps (Revocation, below), suspension (read time), the login being removed, or the account being wiped (the record is gone).

## 7. Chat turn with `generate_content` and `draft_items`

Files: `src/app/api/chat/route.ts`, `src/lib/chat.ts`, `src/lib/chat-budget.ts`, `src/lib/chat-allowance.ts`, `src/lib/noor.ts`, `src/lib/credits.ts`, `src/lib/judge.ts`, `src/lib/governance.ts`.

1. `POST /api/chat {text, conv?, agent?, stream?}`; session required; text clipped to 4000 (400 `empty` when nothing is left); `agent` falls back to `noor`; reply language from header `x-lang` else `u.lang`. `conv` is not validated against `convs:{scope}`; any string yields the key `chat:{scope}:{conv}`. Before anything is saved (step 14): the burst limit (429 `slow_down`) and, since 2026-10-01, the plan's monthly chat allowance (402 `chat_allowance` or `chat_credits`, section 37).
2. `chat()` pushes the user message, builds context (brand, this agent's 30 preferences from `listPreferencesFor`, five memory files up to 6000 chars each, file names, connected providers, the thread, and the agent's recent feedback with its chat thumbs, step 13), and loops up to 5 model calls (`CHAT_MAX_CALLS`, `chat.ts:345`). Since 2026-10-01 the thread goes through the history guard (`trimHistory` in `src/lib/chat-budget.ts`): the newest 16 messages that fit 24,000 characters together, each cut to 6,000, the owner's newest always kept, and a thread that starts with the assistant (the first-run onboarding writes its messages before the owner says anything) sent as it is, so a long thread cannot make every message dearer. Then `fitFirstCall` drops the oldest messages until the first call has room for at least 4,000 output tokens (`CHAT_FIRST_MIN_OUT`), or only the newest is left: a full workspace shortens the thread's memory, not the answer. Each call's `max_tokens` is what is left of the per-message ceiling (`CHAT_TURN_MAX_USD`, $0.35 in model calls, `src/lib/pricing.ts`) after what the turn has cost so far and an upper estimate of the call's input, at most 8,000 (`nextMaxTokens`). The estimate counts 3 characters a token (`CHARS_PER_TOKEN_EST`, below the measured 3.3); the first call prices the cached prefix (the tools and system blocks 1-2) as a cache write and the rest as input, and every later call prices the previous call's cache read and cache write tokens as a cache read, and the rest of its input, its output and the tool results added since as input. When less than 2,048 tokens would be left (`CHAT_MIN_OUT`), no further call is made (step 7). It works out who is talking once (`opts.by`, which the MCP route sets to `tokenBy(user)`, else `byOf(user)`) and passes each tool its turn (`ToolCtx`: the talking agent and `by`), which the tools put on their activity rows (section 32).
3. All three are owner only (`mcp.token`, 2026-09-29): a member and a founder impersonating get 403. The slot is keyed by the acting login, which past the gate is the owner.

### OAuth 2.1
1. Discovery: `/.well-known/oauth-authorization-server` and `/.well-known/oauth-protected-resource` (rewrites). Issuer and endpoints derive from `APP_ORIGIN`.
2. Client registration: `POST /api/oauth/register` is open to anyone. Keeps up to 10 `http(s)` redirect URIs, issues `client_id`, and a `client_secret` only when `token_endpoint_auth_method = client_secret_post`. Rate limited to 30 per IP per hour (429 `slow_down`); no expiry.
3. Authorize: `/oauth/authorize?client_id&redirect_uri&response_type=code&code_challenge&code_challenge_method&state&scope`. Anonymous users are redirected to `/ar/app/login?next=...`. The page checks client, exact `redirect_uri` membership, `response_type=code`, presence of `code_challenge`; shows Allow/Deny with the client name supplied at registration.
4. Approve: `POST /api/oauth/approve` (form post, session required) re-validates client and redirect URI, requires `code_challenge_method=S256`, issues a 10 min single-use code bound to client, redirect URI, challenge, email and `scope` (free text from the request, default `noor`). Deny redirects with `error=access_denied`. Owner only (`oauth.approve`, 2026-09-29): a member and a founder impersonating get 403, and the consent page shows them no form, only who is signed in.
5. Token: `POST /api/oauth/token` (JSON or form; client auth via Basic, body secret, or none for public clients; a secret is compared with `sameSecret`; 60 requests per IP per 15 minutes, checked first, 429 `slow_down`). `authorization_code`: code is deleted on first read, then client id, redirect URI and PKCE S256 are verified. Issues access token `nashr_...` stored in `mcptoken:{access}` for 30 days and refresh token `nashr_r_...` in `oauthrefresh:` for 90 days.
6. Refresh: `grant_type=refresh_token` rotates: the old refresh token is deleted and a new pair is issued; client id must match. The previous access token stays valid until its own TTL.
7. `GET /api/mcp/grants` lists the account's grants and `DELETE ?id=` or `?all=1` revokes (Revocation, below); both are owner only (`oauth.grants`) since 2026-09-29.

### MCP `save_draft` (2026-09-29): drafts from the owner's own assistant
Lets an owner write with their own Claude or ChatGPT subscription and still review in Nashr. `{type, body, title?, channel?, notes?, lang?}`, one item per call (`src/lib/external-drafts.ts`; action `drafts`, any role, and an MCP bearer is always the owner):
1. `parseDraft` validates before anything is read or written: `type` must be in `TASK_TYPES` (`isTaskType`, so `constructor` and friends fail); `body` is required, at most 20,000 characters; `title` at most 200 (defaults to the body's first line, 80 characters); `notes` at most 500 (kept as `brief`); `channel` a lowercase `[a-z0-9_-]{1,30}` name (defaults to the type); `lang` `ar` or `en` (defaults to the brand's first language). Control and bidi-override characters are stripped. A field over its limit is refused with a tool error, never truncated. Any other argument (`scope`, `email`, `id`) is ignored.
2. `draftAllowed(user.email)` (`rate.ts`): 30 an hour and 150 a day per account, across its brands. Over the limit: tool error, nothing saved.
3. The brand of `sc(u)` (the bearer's active brand, set by `userFromBearer`) is read; without one: tool error, nothing saved.
4. The brand gate runs in code (`gateTask`, the approve and publish routes' check). Status is `initialStatus(false, ...)`, i.e. always `pending`: the owner's auto-approval does not apply to text the owner has not seen in Nashr. A draft that breaks a rule is saved anyway, held like an agent's draft (the inbox names the rule, `PATCH /api/tasks/{id}` refuses to approve it with 409, publish refuses it), and the tool answer returns `brandCheck.violations` so the assistant can fix and save again. This matches every other creation path, which keeps a violating item pending rather than dropping it.
5. `saveTask(sc(u), task, true)` with `source:"external"` (ad and social types get an ad code there, as on every path). No credits, no model call, no judge, no cross-agent review (section 33; the inbox card says "unreviewed · written outside Thakeen"), no trial-expiry check (like `check_brand`, it spends nothing).
6. Answer: JSON with `saved`, `id`, `status`, `type`, `channel`, `title`, `brandCheck` and `credits: 0`. 401 responses carry `WWW-Authenticate` pointing at the resource metadata. CORS is `*`.

## 20. Campaign results import (CSV)

1. Reem is the eighth agent (`AGENTS`, id `reem`, "Secretary"), with a playbook and no task types, so `agentForTask` never names her and the generate page, reviewer and golden set skip her. Her chat intro: she keeps the list, repeats every saved date back, never marks anything done, never promises a reminder at a set time (there is no alert at the due time in phase 1), and treats quoted customer, supplier, connector or file text as data. Every agent's uncached prompt block starts with `nowLine`: `NOW (Riyadh, UTC+3): …; today is …. The work week starts on Sunday.` in the brand's zone (Dubai: `UTC+4`, Monday), so relative dates are worked out from the real calendar. The chat page accepts `?agent=reem` (any id in the registry).
2. Capture. The owner writes in chat ("add: call the supplier Thursday 10am"); Reem (or any agent: the tools are offered to all) calls `todo_create` with a title and a due time in local wall time (`YYYY-MM-DDTHH:mm`, or `YYYY-MM-DD` for the end of that day). `runSecretaryTool` checks `sec:write` and `sec:create` allowances and reads the zone once, `createItem` validates and saves `sec:item:{scope}:{id}` with its `sec:open` score, `sec:all` member and one audit line, and the answer carries the stored date formatted in the owner's language and the zone's city (`formatWhen`: «الجمعة 2 أكتوبر 10:00 ص», "(Dubai time)"), which the prompt tells Reem to read back exactly; when that date has already passed the answer says so, so the agent checks it with the owner. A link to an inbox item (`task_id`) is accepted from chat or MCP only here, at creation, and only to an item still `pending` (400 `link_not_pending` otherwise). From the page: the add form posts `{title, dueAt, direction, owedBy|owedTo}` to `POST /api/secretary`; from the owner's own assistant: MCP `todo_create`, `source:"mcp"`.
3. Who owes what: `direction` `i_owe` (the owner acts; `owedTo` is who it is for) or `they_owe` (`owedBy` names who owes the owner; required; `owedTo` becomes `owner`). A `waiting_on` item is always `they_owe`. A party is `owner`, an exact agent id, or a contact label; Arabic names stay labels. A they-owe item without a due date gets `expectBy`: the owner's date (`expect_by` in the tools, `expectBy` on the route) or, by default, two working days after creation (`addWorkingDays`, skipping the zone's weekend); an item that becomes they-owe or loses its date later gets it from then.
4. The agenda (`agendaFor`, `computeAgenda`), computed at every read and never stored: a proposed "done" goes to "needs your confirmation", even if the item was snoozed; other snoozed items are only counted until `snoozeUntil`. Someone else's item follows the chase clock (`chaseAt`): its due time, else `expectBy` (default as above), and after a recorded follow-up two working days after `lastChasedAt`, never before the due time. Past the clock it is the owner's move: "overdue" (next step chase) when the due time passed, else "time to follow up" (`chase`); before it, "waiting on others" (reason `chased` when a follow-up holds an overdue item back). The owner's own items: past due goes to "overdue"; then "today" (the same local calendar day), "next 7 days", "later", "no due date", and "untouched for 14 days" (`cold`: undated, `updatedAt` 14 days back; next step: do it, date it or delete it). Order: critical, earliest due, priority, oldest, id. The approvals inbox count (`pendingCount`) is one line of the agenda. Reads: the open set, one MGET of items, the pending count, the brand file (its zone) and, when any item is linked, one MGET of the linked tasks, which also gives `facts` (step 6).
5. Updates: `todo_update` (title, details, due, clear due, expected date, snooze, priority, party, direction, critical, a note, `chased`; never a link: `toolFields` reads `task_id` for `todo_create` only, and `mutateItem` refuses a link change from anyone but the owner on the web, `owner_only`) and `PATCH /api/secretary/{id}` (the same fields; actions `snooze {preset: 2h|tonight|tomorrow | until}`, `reschedule {dueAt}`, `add_note {text, private}`, `chased`) go through `changeItem`: the item lock `sec:lock:{scope}:{id}`, the `rev` check when the caller sent one (409 `conflict` with the current item), the change applied to the stored copy in the brand's zone, `rev` bumped, item, index moves and audit line saved in one round. A follow-up (`chased`, the page's "Followed up" / «تابعت», or `todo_update {chased: true}` when the owner says they followed up) sets `lastChasedAt`, adds a note of kind `chased` («تمت المتابعة»; never "sent") and restarts the clock; it never closes the item, and on the owner's own item it is 409 `not_theirs`. The audit line's action is `chased`.
6. Closing. Chat and MCP can only propose: `todo_propose_done {id, evidence}` sets `proposedDone`, ends any snooze, and the item waits under "needs your confirmation". The evidence is the agent's own words: the page shows it as that agent's claim («ريم تقول: …», «سامي يقول: …», «مساعدك يقول: …», "Reem says: …", marked as not checked) and next to it, under "Checked by the app" / «تحقّق التطبيق», what code read from the stored linked task (`linkFactText` over `facts`: still waiting for approval, rejected on a date, approved by the owner on a date or by a rule, and where it was published), or "Nothing in the app confirms this" when the item has no link; `agenda_get` writes the same as "claimed done by … (a claim, not checked); checked by the app: …". The owner completes from the page with a written result (`complete {result}`; the Done button opens a required field), or confirms a proposal (`confirm_done`, the evidence becomes the result) or sends it back (`reject_done`, a note of kind `not_yet` records the evidence; `noteText` words it in the reader's language). These, `delete` and `restore` are refused for any actor other than the owner on the web route (`owner_only`).
7. The one automatic close: an item whose `links.taskId` names an inbox task of the same scope (set by the owner, or by chat or MCP at creation to a pending task, so an approval the owner makes after the link) closes with the result "linked item approved" when that task is `approved` (publishing approves too), found when the agenda is read (page, route, `agenda_get`, brief) or by the daily job, and re-checked under the item lock (`closeLinked`, audit actor `rule` or `cron`). The page lists it under "done" with the checked fact (when the owner approved it and where it was published).
8. Delete and restore: `delete` sets `deletedAt` and `expiresAt` (30 days) and moves the id from `sec:open` to `sec:deleted`; the page shows "Deleted. Undo" and a restorable list; `restore` puts it back where it was (open or done) until `expiresAt`, then answers 410; a restore that reopens an item counts against the 500 open items like a new one (409 `open_limit`). The daily cron's `purgeExpired` removes at most 200 expired items per scope per day with their `sec:deleted`, `sec:all`, `sec:done` and `sec:open` entries, for every brand scope: the active ones through `secretaryDaily`, archived brands and suspended accounts through `purgeIdle` (`dailyRoster().idle`).
9. Brief: `runDaily` adds «مهامك (ريم): N متأخرة، N لليوم، N بانتظار غيرك» (and the numbers to follow up and to confirm) with the first three overdue or due-today titles, stored as `Brief.agenda`; the brief email carries it, and the "important" preference sends when a to-do is overdue or due today.
10. Overdue alerts (`followUps` → `overdueTodoAlerts` in `src/lib/notifications.ts`): one `todo` notification from Reem per overdue item, linking to `/{lang}/app/todo`, on the local day it fell behind and on the 1st, 3rd and 7th day after (`overdueAlerts`, `alertStep`: day 0 → step 0, days 1-2 → 1, 3-6 → 3, day 7 → 7, later → none; a missed day inside a window is caught up once). Each step is claimed once with SET NX on `notifseen:{email}:todo-due:{scope}:{id}:{dueAt ms}:{step}` (5 days), so a new due date starts afresh and two overlapping runs send it once. At most `SEC_ALERTS_PER_DAY` (5) a brand a local day, critical and earliest first, counted in `sec:alerts:{scope}:{day}` (2 days); a claim beyond the allowance is handed back (its marker deleted) so the item can still go on another day of its window. The seventh day's alert says it is the last; after it the item is only in the morning brief. Every other follow-up keeps its own fingerprint, now claimed the same atomic way (`pushNotif`).
11. The page `/{lang}/app/todo` ("مهامي" / "My to-dos", in the sidebar under Approvals) is rendered on the server from `todoPage(sc(u))`: sections per bucket, each row with its title, due date formatted in the brand's zone, who owes it, when it is expected and the last follow-up, badges, its last three notes (private ones included: this is the owner's page) and the next step, and Done (result required), Snooze (2 hours, tonight 8 PM while it is still ahead, tomorrow 9 AM, local), Reschedule (a datetime-local input read as local time), "Followed up" on someone else's item, and Delete (with Undo, a toast pinned to the bottom of the screen for 8 seconds; restoring from the Deleted list clears it); "needs your confirmation" rows show the claim and the checked fact and get Confirm / Not yet; then the add form, the last 10 done (with the checked fact of a linked item) and the restorable deleted items. The subtitle and the date labels name the zone («بتوقيت دبي»). Every action is one request followed by a refresh of the server render. There is no alert at the due time, and reminders on WhatsApp or Telegram are not available; the page says both.
12. Account deletion: `wipeAccount` deletes every key `secretaryKeys(scope)` names for every brand scope: each id in `sec:all`, the open, done, deleted and id sets, the audit log and the alert counters of the last days. The `notifseen:` alert markers expire within five days.

## 26. Teams: members, invites and seats (2026-09-29)

Files: `src/lib/team.ts`, `src/lib/roles.ts`, `src/lib/auth.ts` (`resolveSession`, `getLogin`, `PLAN_SEATS`, `seatLimit`), `src/app/api/team/*`, `src/app/[lang]/app/team/page.tsx` (`TeamPanel`, `teamPerms`), `src/app/[lang]/app/join/page.tsx` (`JoinForm`, `inviteToken.ts`), `src/app/api/admin/plan/route.ts`, `src/lib/account.ts`. Design: `docs/superpowers/specs/2026-09-29-teams-design.md`. Roles and gates: `permissions.md` 0.1.

1. Model. The account stays the owner's `User` at `user:{owner}`: plan, credits, brands, scopes, governance, usage and cron are unchanged. A member is a separate login at `member:{email}` (`{email, name, lang, passHash, memberOf, role, invitedBy, acceptedAt, sessionsAfter, disabled?}`), listed in `members:{owner}`. It never passes through `saveUser` or `createUser`, never enters `users:all`, and gets no trial credits, referral code or signup tracking. An email is one login across `user:` and `member:`: signup and accept both create logins under `lock:login:{email}`.
2. Members page (`/{lang}/app/team`, every role; "Members" / "الأعضاء"). Server-rendered from `teamView(u)`, the same body `GET /api/team` returns: the acting person, seats used of the limit, the roster (owner first; each member's role, `acceptedAt` and `disabled`) and, for admin and owner, the pending invites. The controls come from `teamPerms(u)`, which is `can()`; after every change the panel reloads `GET /api/team`.
3. Invite (`POST /api/team/invite {email, role, lang?}`). Needs `team.invite.member` (admin+); `role: "admin"` needs the owner; a founder impersonating cannot invite. Rate limits `team:invite:acct:{owner}` 20 a day (5 on a trial, which anyone can open with one signup), `team:invite:ip:{ip}` 30 an hour and `team:invite:to:{sha256(address)}` 5 a day across all accounts, counted on every attempt, because each answer says whether an address is free and each emailed invite is mail from the product's own domain to a stranger. `createInvite`: the role must be `admin` or `member` (400 `invalid_role`); the email is normalised and must pass `validEmail` (400 `invalid_email`); the acting member's record must still hold its role (403). The owner's or the inviter's own address is 409 `unavailable`; then, under `lock:team:{owner}`, an existing owner or member login anywhere, or a pending invite for the address in this team, gets the same 409 `unavailable`, and seats used + 1 over the limit gets 409 `{error:"seats", used, limit}`. The token is 32 random bytes (64 hex); only its SHA-256 is stored, as `invite:{hash}` (`{email, role, owner, invitedBy, createdAt, expiresAt, lang}`, TTL 7 days) plus an entry in `invites:{owner}`. The link is `${ORIGIN()}/{lang}/app/join#t={token}`: the token is in the fragment, so it never reaches a server or an edge log. When `mailReady()` the link is emailed in the invite's language from a fixed template that names only the inviting login's address (never a display name or brand name, which are free text the sender chose), and the link goes to the invited address or nowhere: when that send fails the invite is withdrawn under `lock:team` (`discardInvite`) and the answer is 502 `{error:"send_failed"}` with no link, so an inviter cannot take an address they do not control by making the send fail. Only when mail is not set up at all does the response carry `link` once for the inviter to pass on (the Members page then says a link is created, not that an email is sent). It can never be shown again (only the hash exists); to resend, cancel and invite again. The account's bell gets an item that names neither the invited address nor the role (the bell is shared by every login, and pending invites are admin+) and says whether an email went out. Response: `{ok, invite: {id, email, role, expiresAt}, emailed, link?}`, where `id` is the hash.
4. Cancel (`DELETE /api/team/invite {id}`). Needs `team.invite.cancel` (admin+; an admin cancels `member` invites only; not a founder impersonating). The id must name an invite of this account (else 404); under `lock:team:{owner}` the invite is read again and, if still there, it and its index entry are deleted (404 when an accept holding the lock used it first).
5. Join page (`/{lang}/app/join`, public, listed in the app layout's public paths). `JoinForm` reads the token from `location.hash` (`readInviteToken`: 64 hex or nothing), clears the fragment with `history.replaceState`, and never puts the token in a query string. It keeps the token in `sessionStorage` for the tab (`rememberInviteToken`), so switching the page language, which reloads without the fragment, still finds it; it is forgotten after a successful accept and whenever the server calls it invalid, and the page works without storage. A signed-in visitor is shown who they are signed in as and must log out first; nobody is joined into an existing session. Signed out, the form posts `{token}` to `POST /api/team/accept` for a preview.
6. Preview (`POST /api/team/accept {token}`). Rate limit `team:peek:ip:{ip}` 30 per 15 min. `peekInvite` returns `{team, inviter, email, role, expiresAt}` for a live invite whose owner exists and is not suspended and whose inviter still passes the accept's check (the owner, or an enabled admin of this team inviting a plain member); anything else is 400 `invalid`. Nothing is consumed.
7. Accept (`POST /api/team/accept {token, name, password, lang?}`). Rate limit `team:accept:ip:{ip}` 10 per 15 min. `acceptInvite`: a live invite (400 `invalid`); a name, control characters removed and cut to 80 (400 `invalid_name`); `strongPassword` (400 `weak_password`); bcrypt runs before any lock. Then single use: `inviteuse:{hash}` is taken with SET NX (30 s; a concurrent accept gets 400 `invalid`). Under `lock:team:{owner}` everything that decides the answer is read again, so a cancel, a plan change, a demotion or an account deletion that finished while the accept waited is seen: the invite must still be stored AND in `invites:{owner}` (a cancelled one is 400 `invalid`, never counted as a new seat); the owner exists, is not suspended and is not newer than the invite (an address registered again); an invite sent by a member needs that member to be still an enabled admin of this team and the role to be `member`; and the seats are counted against the owner's limit as it is now, the invite's own seat counted once (409 `seats`). Under `lock:login:{email}` the address must still be free across `user:` and `member:` (409 `unavailable`). The member is written with `acceptedAt = sessionsAfter = now` and the language from the request, else the invite's; the invite and its index entry are deleted. The route then destroys any session on the device, creates one for the member and puts a bell item on the owner. The new login lands in the owner's workspace (section 5).
8. Member login, forgot, reset and password change act on the member record only (sections 2 and 4): the member's own hash and its own `sessionsAfter`; the owner's hash, sessions, MCP token and grants are never touched. A seat-paused member cannot sign in (403 `disabled`).
9. Remove (`DELETE /api/team/member {email}`). Needs `team.remove.member` (admin+); removing an admin needs the owner; a founder impersonating cannot. The member must belong to this account (404). Under `lock:team:{owner}` and then `lock:member:{email}` (the lock every member-record writer holds), the record is read again and, while it still belongs to this account, `member:{email}`, `activebrand:{email}`, the roster entry and every pending invite that member sent are deleted. A profile, password or reset save in flight therefore finishes first or finds nothing: it can never restore a removed login. The member's sessions stop at their next request, because `currentUser` finds no member record (and would refuse one off the roster anyway).
10. Leave (`POST /api/team/leave`). Member logins only (`team.leave`; the owner, a token and a founder get 403). The same deletion as a removal, then `destroySession()`.
11. Role change (`PATCH /api/team/member {email, role}`). Owner only (`team.role`). `admin` or `member` only; the owner role cannot be assigned, removed or transferred. Written under `lock:team:{owner}` and `lock:member:{email}`; the new role applies at the member's next request. Demoting an admin deletes the invites that admin sent, which could never be accepted afterwards yet would each hold a seat for up to 7 days.
12. Seats. The limit is `seatLimit(owner)` (`src/lib/pricing.ts` since 2026-09-30): `User.seats` when it is a positive number (floored), else `PLAN_SEATS[plan]` (trial 3, starter 1, pro 3, business 7), and Agency Business's 7 unless the founder sets `seats` for its contract; the owner included. A retired `enterprise` record (25 seats) reads as agency, so without a seat override it falls to 7: members above that stay enabled until the next plan or seat change runs `enforceSeats`, while new invites and accepts are refused. Seats used = 1 + members not disabled + unexpired invites. The billing page shows used of the limit to every role.
13. Seats after a plan change. `POST /api/admin/plan` (founder console) runs `enforceSeats(owner)` after any plan or `seats` change, up or down, under `lock:team:{owner}`, relative to who is active now: over the limit, the newest ENABLED members get `disabled: "seats"` (kept, never deleted) and every pending invite beyond the room left is cancelled, the newest first; under it, paused members come back oldest first, but only into seats no pending invite holds. Re-applying the same limit changes nothing (the team is never re-ranked as a whole, so a member the owner brought in after a downgrade is not swapped for one paused earlier). Removing a member does not bring a paused one back by itself; the next limit change does. A disabled member's login answers 403 `disabled` and its sessions stop at their next request. The response and the `admin:log` entry list who was paused and restored and how many invites were cancelled. Trial to Starter therefore pauses up to two members. No other code changes a plan today (`permissions.md` 5.32).
14. Account deletion (`DELETE /api/account`, owner only, or the console's `delete`). `wipeAccount` deletes the account's keys, `user:{owner}` included, and then runs `wipeTeam(owner)` under `lock:team:{owner}`: every member record of this account (each under its own `lock:member`), each member's `activebrand:`, every invite, `members:{owner}` and `invites:{owner}`. An accept that held the team lock first has its member deleted here; one that takes it afterwards finds no owner. A member login never survives to point at an address someone registers again, and a member record older than a re-registered owner is refused anyway (section 5).
15. Owner reset and founder reset both stamp `teamSessionsAfter` on the owner record, in the same locked save as the password, which signs every member out; each signs back in with its own password. A member's own reset or password change stamps only its own `sessionsAfter`. The owner's password change from Settings does not sign members out.
16. Shared and per login. Credits and the plan are the account's, so a member's generations spend the owner's balance under the same per-agent caps. The bell (`notifs:{owner}`) and its read state, the chat ceiling and analytics are per account. The active brand is per login: a member switching or adding a brand moves only `activebrand:{member}`, and a member's stored brand is used only while it is one of the owner's active brands; an admin archiving the brand the owner has open resets the owner's key too.
17. Pages by role. Owner-only and admin+ screens render read-only for lower roles with a one-line note: billing (no pay links, WhatsApp activation or Agency contact link; plan, credits, seats and the four plan cards for all), governance (its change history stays listed, without Restore; section 30), the scheduled tasks page ("Run now" stays), the brand file, brands (switching stays), integrations (requesting stays), MCP (no token or grant controls), refer (nothing read). The sidebar shows the acting person's name, email and role and a Members link for everyone; the trial banner and the limit dialog tell other roles to ask the owner. The working screens offer a plain member only what the server lets a member do: the inbox has no Approve or Publish for a member (an edit is saved without approving, and an approved item goes back to pending), and a chat card says an admin approves; the files page has no catalog import and no edit or delete on core memory; reports offer no CSV import or removal of imported results; the start page tells a member who sets the brand up (and the chat's first-run thread sends them there); the chat's WhatsApp card is shown only to the owner, whose phone it saves. A refused call says the role does not allow it, never "check your connection". The profile page hides the password and delete forms from a founder viewing the account (`GET /api/profile` returns `may`), and the MCP page tells a founder why there is no token.

### 36.1 Timed reminders
1. Setting. `remindAt` is one instant on an item: from the owner in the app (the add form's "Reminder" field and a row's "Reminder" panel, `remindAt` in the POST or PATCH body; null clears it) or from an agent (`remind_at` on `todo_create` / `todo_update`, `clear_remind: true`). Read in the brand's zone like a due date; a date alone is 08:00 local that day (`REMIND_DAY_AT`: at or before the 05:00 UTC daily run in every Gulf zone, so even the fallback fires it that morning); it must be in the future (`remind_past`, 400).
2. Index. `indexWrites` (every write path: create, change, the linked close, the fire) calls `dueWrites`: an open item with a reminder is in `sec:due:{scope}` at `remindAt` ms, and then its scope in `sec:duescopes` at that score with ZADD LT (a later reminder never raises the scope's score); any other item that had or has a reminder (done, deleted, cleared) is removed. The purge also removes it. A sweep never removes an id: it leaves when the item's own write clears `remindAt`.
3. The tick. An Upstash QStash schedule (created by the founder in the Upstash console, every 15 minutes) calls `POST /api/cron/secretary`. The route first refuses oversized input unread (a body over 64 KB, by its declared length or while reading: 413; an `Upstash-Signature` header over 4096 characters: 401), then accepts either the CRON_SECRET bearer (`sameSecret`) or a valid `Upstash-Signature` (`verifyQstash`: HS256 with the current or next signing key, `iss`, `sub`, `nbf`/`exp`, the body hash). Anything else is 401 and nothing runs; only those failed calls count against the per-IP limit (`allow`, 60 a minute, then 429), so callers sharing QStash's egress addresses can never make the real tick answer 429.
4. The sweep (`sweepReminders(now, {fromQstash, deadline})`): up to 200 scopes from `sec:duescopes` with score <= now, grouped by account, 8 accounts at a time. Per account the user and the brand list are read once: a missing account's scopes leave the index; a suspended account's scopes, and the scopes of a brand that is not active (archived), are looked at again 6 hours later with their reminders still due. Per scope (all of an account's at once, each isolated: `Promise.allSettled`, the zone read falls back to Riyadh) up to 50 due ids are read, and each is leased with `SET NX sec:firing:{scope}:{id}` for 330 s (longer than the longest caller, the daily cron's 300 s): one run at a time works on it, and the lease is released when the attempt ends (a killed run's expires). `fireReminder` re-reads the item under its lock (30 s) and fires only when it is open with a `remindAt` at or before now and still the instant the sweep read. Delivery comes first: one `todo` notification (href `/{lang}/app/todo`, fingerprint `todo-remind:{scope}:{id}:{remindAt ms}`), then, only when that push was new, one email when `RESEND_API_KEY` is set and the scope's email preference is not `none`; then the item: a `reminded` note («طلبت تذكيرك اليوم» / "You asked to be reminded"), `remindAt` cleared, `rev` bumped, then its index moves and the audit `remind` by `cron`. An item with no reminder due (closed, deleted, gone, cleared) leaves `sec:due`; one whose reminder moved is re-indexed at its new time; a busy lock leaves the id due. The scope is then rescored to its earliest remaining reminder (or removed), and read once more so a reminder added meanwhile is never dropped; a failed rescore is logged, not thrown.
5. Late, never lost. A failure anywhere (a store error, the bell write, the item write, a kill) leaves the id due and the next sweep retries it: a bell write that fails releases the fingerprints it claimed before the error goes on, and a retry after a run stopped between the delivery and the item's write finds the fingerprint claimed, so there is no second bell entry and no second email, and the item is written. Nothing is sent on WhatsApp or Telegram. The bell's list is written under the account's bell lock (section 36.7). A deadline bounds each run: no account starts and no lease is taken after it (the tick: 40 s after it started, of its 60 s; the daily route: 60 s after it started), and what is left stays due. `sendEmail` gives up after 10 s (false, logged as refused), so a hung send never holds a lease or a slot.
6. Honesty. A QStash call writes `sec:tick:last` (TTL 2 h); `timedReminders()` is true while it is under an hour old. Only then do tool answers say the reminder "comes at {time}" and the page show «تذكير: …» / "Reminder: …"; otherwise they say it arrives with the next morning brief after that time, at the brief's local time in the brand's zone (`briefClock`: 05:00 UTC plus the zone's offset, 08:00 in Riyadh, Kuwait, Doha and Manama, 09:00 in Dubai and Muscat; never a fixed "08:00"), and the page fills the same time into `remindBrief`, `timedOff` and its note. Fallback: the daily cron's first hop runs the sweep (not on chained hops, and without writing the tick), again while a sweep read a full 200 scopes (at most 4 more times, within its 60 s), and its time comes out of the batch's 240 s start budget; so without QStash a reminder is late, never lost.

A card is `{key, kind, id, title, line, actions}`, plus, on a confirm card, the agent's `claim` (who says it, marked as a claim the app has not checked) and the app's `fact` about the linked inbox item, as the list shows them; and on an approval card the draft's first 500 characters (`excerpt`) and, when the brand guard holds it (`gateTask`, as the inbox's PATCH checks), why (`held`, `explain`). `actions` come from `WALK_TABLE` (confirm: confirm, not yet; do: done, snooze; chase: follow-up, snooze; approval: approve, open; held: open) cut to what the viewer may do (`todo.close` for done, confirm and not yet, `todo.write` for snooze and follow-up, `publish` for approve, `read` for open).
2. `GET /api/secretary/walk` (any member, `read`) answers `{card, left}`; `POST {action: "next", key}` (any member, `todo.write`; the key must be `todo:{item id}` or `task:{inbox id}`) skips that card for 3 hours in `sec:walk:{scope}` and answers the next. The page's "Walk me through" shows one card at a time, the claim, fact, excerpt and hold as plain text; its buttons call `/api/secretary/{id}` or `/api/tasks/{id}`, so every gate stays where it is (Done asks for the result first; a brand-guard refusal reads "Held by the brand rules").
3. Chat and MCP: `agenda_next {skip_id?}` (MCP action `read`) answers the card as a tool line with its claim, fact, hold and excerpt as JSON-quoted data: done, confirm, not yet, approve and open are the owner's, on the page or in the inbox, and the agent cannot do them; on a to-do card, snooze and the follow-up the agent may do with `todo_update` (`snooze_until`, `chased: true`) when the owner asks. `skip_id` skips that card first.

### 36.5 Evening wrap
1. `buildWrap` first runs the agenda as the cron (`agendaFor`), which closes the items whose linked inbox item was approved, then reads stored facts only: items completed today in the brand's local day with their result (from the newest 50 done), the approvals (approve, and publish, which approves) and rejections the owner decided today (the newest 100 records of `decisions:{scope}`), items that fell overdue since the previous evening's wrap time (`previousEveningAt`: yesterday's 18:00, or 21:30 when yesterday was in Ramadan; an all-day item due yesterday included), and the first three items of tomorrow 09:00's overdue, today, confirm and chase buckets. No model, no motivational line.
2. `eveningWrap(user)`: "off" when follow-ups are off in Scheduled tasks (the switch's text says it silences the wrap); silent when all four parts are empty; otherwise `sec:wrap:{scope}:{day}` is claimed with SET NX (TTL 2 days) and one `todo` notification («ملخص المساء من ريم» / "Reem's evening wrap"; with more than one active brand, «ملخص المساء من ريم — «{brand}»» / "Reem's evening wrap — “{brand}”", and the email's subject names it too) is pushed; when that notification cannot be written the claim is released and the error goes on, so the batch's retry sends it (never after it was written). Then one email when `RESEND_API_KEY` is set and the preference is `all`.
3. When: 18:00 local, 21:30 local in Ramadan (`activeSeasons()` has `ramadan`), after Taraweeh. The Vercel cron `GET /api/cron/evening` at `0 15 * * *` (18:00 Riyadh, 19:00 Dubai) runs it for every active workspace through `runCronBatch`, and does nothing in Ramadan. The QStash tick starts `/api/cron/evening?zones=…` (with the cron bearer, only when CRON_SECRET is set) for the zones whose wrap time fell within its last 16 minutes, in and out of Ramadan; that call serves only the workspaces kept in those zones, and a list naming any zone off the allow-list is refused whole (400). Without QStash there is no wrap in Ramadan.

### 36.6 A blocked agent opens a waiting-on item
1. `handoff_note {to: agent id | "owner", kind: "blocked" | "ready" | "note", body}` is a chat tool for every agent (body up to 500 characters; `to` never the sender; the sender is the turn's agent). It leaves one of the agents' handoff notes («ملاحظات التسليم»), which cost no credits; they are not Majed's handoffs (section 34, `propose_handoff`: work for other agents, charged when it runs). Over MCP it is neither listed nor run (`runTool` refuses it when `via` is `mcp`). Each note costs one change of the `sec:write` allowance.
2. Notes go to the capped list `notes:{scope}` (30). The receiving agent sees its last 5 from the past 7 days in its uncached prompt block (`handoffNotesFor`, `handoffBlock`: an `asData` JSON value inside `<handoff_notes>`, labelled as data); Reem also sees the notes addressed to the owner.
3. `kind: "blocked"` (at most 20 a day per account) opens a Reem item in code (source `agent`, `handoffFrom` the sender): to the owner, the owner owes the agent input (i_owe, `owedTo` the agent, `follow_up`), due all day today in the brand's zone, so it is in today's agenda, the morning brief, the evening wrap and the walk, and overdue after; to another agent, that agent owes it (they_owe, `owedBy` that agent, `waiting_on`, with the usual two-working-day chase date). Title «توقّف عمل {agent}: {body}» / "{agent} is blocked: {body}" (cleaned, 200 characters), description the full body. Under one lock per scope, an open item the same agent opened for the same party that says the same thing (`sameBlock`: equal after normalising; otherwise both at least 3 words, `similarity` >= 0.6 AND at most 2 words in one and not the other) gets the new body as a note instead, and the answer says no second item was opened. The answer is built from the stored item: it names the due date and says the item is in the morning brief (at the brief's local time) only when it is.

### 36.7 The bell's lock
1. Every read-then-write of `notifs:{email}` (`pushNotifs`' list write and `markAllRead`) runs under `withBellLock`: `notiflock:{email}`, SET NX for 10 s, 60 tries 50 ms apart, released in `finally`. Two writers landing together (the tick's reminders, the daily follow-ups, an evening wrap, the owner opening the bell) therefore never overwrite each other's entries. Past about 3 s without the lock the write goes ahead anyway, as before the lock. The fingerprint claims stay outside it.

## 37. The chat allowance and the "continue on credits" switch (2026-10-01)

Pricing phase 2 (spec `docs/superpowers/specs/2026-09-29-pricing-design.md` section 6 rules 1 and 2, as amended on 2026-10-01; plan `docs/superpowers/plans/2026-09-29-pricing.md` phase 2). Files: `src/lib/pricing.ts` (`CHAT_ALLOWANCE`, `chatAllowanceOf`, `CHAT_TURN_MAX_USD`, `chatOverflowHold`), `src/lib/chat-allowance.ts`, `src/lib/chat-budget.ts`, `src/lib/credits.ts` (`settleChatOverflow`), `src/lib/usage.ts` (the counters), `src/app/api/chat/route.ts`, `src/app/api/mcp/route.ts`, `src/app/api/billing/chat-overflow/route.ts`, `src/app/api/profile/route.ts`, the chat, billing and profile pages (`ChatPanel.tsx`, `LimitModal.tsx`, `ChatAllowanceCard.tsx`, `ProfilePanel.tsx`, `src/lib/usage-view.ts`), and the founder console (section 14). Tests: rules 308-316 of `tests.md`.

1. The allowance. A message is one turn the owner (or any login of the account, or a connected app through MCP `ask_noor`) sends, however many model calls and tools it takes. `chatAllowanceOf(u)`: the founder's override (`User.chatAllowance`, a whole number 0..100,000; 0 stops chat for the account, "continue on credits" included: `reserveChatTurn` refuses every message) when set, else Agency gets Business's, else the plan's `CHAT_ALLOWANCE`: trial 30 for the whole trial, starter 250, pro 650, business 1,300 per UTC calendar month.
2. Counting. Per ACCOUNT: `u.email` is the owner's for every seat, so the owner, admins and members, every brand and every connected app share one counter: `usage:{email}:{YYYY-MM}:chat_msgs` on a paid plan (it renews at 00:00 UTC on the 1st, before the 05:00 credit renewal), `chatm:{email}:trial` on a trial (never renewed). `reserveChatTurn` counts the message with INCRBY before the turn, so parallel messages can never pass the allowance, and before `chat()` saves it, so a refused message is in no thread. After the turn `settleChatTurn` (through `runChatTurn`, on every path) gives it back when the turn threw, made no model call or cost nothing (Claude paused, the dev mock, a workspace too large for one message), so only answered messages count. `ChatStatus.used` is the count clamped to the allowance (what the owner is shown); `counted` is the raw count, which can pass the allowance after the founder lowered it mid-period (the founder console's figure).
3. Used up, owner's switch off (the default): 402 `{error: "chat_allowance", chat, credits}`. Chat is paused until the 1st (UTC) on a paid plan, and on a trial until the owner subscribes. Nothing was saved, sent to the model or charged.
4. The switch. `POST /api/billing/chat-overflow {on: boolean}` (owner only, `billing`; 30 calls an hour, `rate:chatovf:{email}`, 429 `slow_down`; anything but a real boolean 400 `bad_request`; a trial 409 `trial`) writes `User.chatOverflow` under the user lock (on sets it, off deletes it) and answers `{ok, chat}`. Admins and members see it read-only; a trial has no switch: its chat is its 30 messages.
5. Used up, switch on (paid plans only). Nothing is held or taken before the turn: the gate only checks that the balance is at least `chatOverflowHold()` = `ceil(CHAT_TURN_MAX_USD / maxCostPerCreditUsd())` = ceil($0.35 / $0.07104) = 5 credits, the most one message can cost, so the turn's own tools (a batch asked for in that message) can spend the whole balance; below that the answer is 402 `chat_credits` and nothing is charged or sent. The message is counted in `usage:{email}:{YYYY-MM}:chat_over`. After the reply `settleChatOverflow` (one save under the user lock, `src/lib/credits.ts`; not `charge`, so no agent's cap counts it: chat is no agent's work) adds the turn's metered model cost to `User.chatCarryMicro` and bills every whole credit of it at the floor rate (`maxCostPerCreditUsd()`, the 60% margin on the cheapest credit), at most 5 and at most what the balance still holds; the carry keeps the remainder (always under one credit) for the next message, so a run of cheap messages is billed what they cost, not a credit each. Cost past either bound is never billed. The credits billed are added to `usage:{email}:{YYYY-MM}:chat_cred` (`ChatStatus.overflow.credits`). A failed turn is neither billed nor counted. What a typical message costs on Opus is not measured, so no copy guesses below the 5-credit bound.
6. Per-message guards, the same for every message (section 7 steps 2 and 7): the history guard with `fitFirstCall`, and the $0.35 ceiling on the turn's chat model calls, checked in code before each call; a call cut off at `max_tokens` is never acted on. Generation asked for in chat (`generate_content`, `draft_items`, `generate_image`) is not inside the ceiling: it charges credits as before, under the agents' caps.
7. What the owner sees (rule 315). The chat page reads `chatStatus(u)` on the server and every answer carries `chat` (`GET /api/chat` too, for the recovery after a dropped stream): under the box «تبقّى لك {left} من {allowance} رسالة هذا الشهر» / "{left} of {allowance} messages left this month" ("in your trial" on a trial), in the warning colour at 10% or less, used up, or continuing on credits; used up it says when chat resumes, or, with the switch on, that each extra message needs at least {hold} credits in the balance and is billed what it actually cost, at most {hold}; with the switch on and the balance below {hold}, that chat is paused for the low balance (`chatPausedCredits`); and with an allowance of 0 (whatever the switch says), that chat is not available on this account and to contact support (`chatOff`), with no promise of the 1st. A refused message is taken out of the thread and its text put back in the box (unless something new was typed), with a line saying it was not sent and not counted; on 402 the limit dialog opens (`LimitModal` kinds `chat` and `chat_credits`): the owner is sent to the Subscription page, any other login is told to ask the owner, and a trial gets the subscribe wording; `chat` with an allowance of 0 gets its own dialog (`chatOffTitle`: not available, contact support) with only the OK button; on 429 its own sentence and no dialog. The billing page's chat card (`ChatAllowanceCard`): used of the allowance with a bar, when it renews (or the trial's end), how long it lasts at this pace (`runway` in `usage-view.ts`, worked out on the server; none once the reset or trial end is at or before now), what counts as a message, the messages continued on credits this month with the credits they were billed, paused for a low balance or off for the account when so, and the switch with its terms for the owner. The profile (`GET /api/profile` now returns `chat`, the same for every seat) shows the used of the allowance, the messages continued on credits this month with the credits billed, counts those credits in the credits used, its bar and its runway, and gives a runway line for the credits and for the messages that follows the owner's choice, a low balance (`shortOf`) and chat off (`chatOff`). Every number comes from the status and `src/lib/pricing.ts`, never typed into the copy (rule 248).
8. MCP `ask_noor` passes the same gates on the same counter (section 13). The founder sees and overrides each account's chat (section 14, rule 316). Deleting the account deletes the counters (`usageMonthKeys` and `chatTrialKey`, rule 314).

## 38. Credit top-ups, activated by hand (2026-10-01)

Pricing spec `docs/superpowers/specs/2026-09-29-pricing-design.md` section 6 rule 5, with the founder decisions of 2026-10-01 (manual activation while there is no payment gateway; sold to paid plans only). Files: `src/lib/pricing.ts` (`TOPUP_PACKS`, `TOPUP_SAR_PER_CREDIT`, `TOPUP_VALID_DAYS`, `isTopupPack`, `topupPriceSar`, `topupsSold`), `src/lib/topups.ts` (the packs' arithmetic, `parseTopup`, `topupRevenueSar`, `NO_CREDITS_HINT`), `src/lib/credits.ts` (`addTopup`, `voidTopup`, `saveSettledTopups`, and every debit and refund), `src/lib/auth.ts` (`getUser` settles the packs), `src/app/api/admin/topups/route.ts`, `src/components/app/TopupCard.tsx` and the billing page, `src/components/app/AdminConsole.tsx`, `src/lib/admin-stats.ts`, `src/app/api/cron/daily/route.ts`, `src/components/app/LimitModal.tsx`. Tests: rules 440-452 of `tests.md` (`tests/topups.test.ts`).

1. Packs: 100, 300 or 1,000 credits at 1 SAR a credit plus VAT, valid 90 days from the founder's activation, spent after the month's plan credits. Sold to every paid plan, Agency included; a trial sees them as available after subscribing (the spec says nothing about trials; founder decision). A top-up credit brings in more than the cheapest plan credit, so the 60% margin floor holds for it (rule 440).
2. The balance: `User.credits` stays the whole balance that every page shows and every charge checks. Each pack is a lot on the account record, `User.topups: [{id, credits, left, at, expiresAt, paidSar, paidOn, ref, by}]`; the month's plan credits are the rest (`monthlyCredits` = credits − what is left in live packs). Every change happens under the per-user ledger lock.
3. Spending (rule 441): every debit takes the month's plan credits first, then packs by earliest expiry: `charge` (batches, media, an added brand's setup, through `debit`) and `settleChatOverflow`. A charge that touched a pack carries a receipt on its result, `from: {monthly, lots: [{id, n}]}`; a media job keeps it in `job.spend`, an added brand's hold in `OnboardHold.from`.
4. Refunds (rule 442): a refund with the receipt undoes the charge from its last credit backwards: each pack gets back what it gave, then the month's plan credits. A pack voided or expired since drops its share; it is never moved into the plan credits, so a credit never outlives its pack and a voided pack never comes back. A refund with no receipt, or beyond it, goes to the plan credits as before top-ups. Every caller refunds a charge in one call; a second refund against the same receipt never fills a pack past its size.
5. Renewal and plan changes (rule 443): `renewIfDue` and a plan change in the console set the month's plan credits to `allowanceOf(u)` and keep every credit left in live packs (`setMonthly`); unused plan credits never roll over. `adjust` (referral and share bonuses) and the console's "+ credits" add to or take from the plan credits only, never a pack's (`addMonthly`).
6. Expiry (rule 444): `getUser` settles every read (`settleTopups`): a pack at or past `expiresAt` leaves the balance with its unspent credits at once, malformed values are repaired, and the record is marked `topupsDirty` (runtime only, never stored) so the next locked save writes it; the daily cron saves it for an account nobody opens (`saveSettledTopups` on the default brand's entry, one account per item of `runCronBatch`, no awaited loop).
7. Buying (rule 449): the billing page's "Top up credits" section (`#topup`) shows the three packs with their price ("100 SAR + VAT" / «100 ريال + الضريبة») and validity from `pricing.ts`, says they are used after the monthly credits, and lists the account's live packs with the credits left and the expiry date (to everyone in the account, without what was paid). The owner of a paid plan gets one button per pack: a WhatsApp link to `SUPPORT_WHATSAPP` whose message names the pack, its price and the account email, or an email to support when the number is not set. Nothing is charged in the app; the summary card shows the balance's share from packs.
8. Activation (rules 446-447): after the payment the founder opens the account's card in the console. "Add top-up" sends `POST /api/admin/topups {email, action:"add", credits, paidSar, paidOn, ref?, reason?}`: founder only (`adminActor`, else 401 before the body is read); `parseTopup` checks the pack (one of `TOPUP_PACKS`, 400 `bad_pack`), the amount paid excluding VAT (0..100,000, kept to the halala, 400 `bad_paid`), the payment date (a real YYYY-MM-DD, at most a year back and a day ahead, 400 `bad_date`) and the reference (at most 80 characters, control characters stripped, 400 `bad_ref`); then 404 `not_found`, and under the ledger lock 409 `topup_needs_paid_plan` on a trial or `too_many_topups` past 50 live packs. The pack's credits join the balance at once, valid 90 days from now. "Void" sends `{action:"void", id}` (400 `bad_id` unless 16 hex characters, 404 `topup_not_found`): the pack and its unspent credits leave the balance; credits already spent from it stay spent. Both write `admin:log` (`topup:+N` or `topup_void:N removed:M`, the actor, the balance before and after, the pack's id, credits, amount paid, payment date and expiry, the reason); the payment reference stays on the pack.
9. Revenue (rule 448): `overview().revenue.topupSarMonth` (`topupRevenueSar`) is what packs whose payment date falls in this UTC month brought in, excluding VAT, summed in halalas; the console shows it next to MRR on the Overview and Billing tabs and never adds it to MRR or the gross margin. A voided pack leaves the figure, and so does a deleted account's (admin:log keeps the record of the payment).
10. Out of credits (rule 450): on a paid plan the limit dialog's `credits` kind offers "Top up credits" (to `/billing#topup`) before an upgrade, and tells a member to ask the owner for a top-up; on a trial it offers a plan and says packs come with one. The "continue on credits" refusal (`chat_credits`), the chat tools' and MCP `generate_content`'s insufficient-credit answers (`NO_CREDITS_HINT`) and MCP's chat refusal (`refusalText`) name the top-up. An agent's cap is not a lack of credits (it counts every credit the agent spends, from a pack or not): its dialog still leads to Governance.

## Revocation (2026-09-18)

- Password change (`PATCH /api/account`): new hash and `sessionsAfter = now` saved inside the user lock, the caller's session is destroyed and a new one issued. Every other session of the account fails at its next request. This is the owner's change; it does not sign members out. A member's change is its own (section 4).
- Password reset (`POST /api/auth/reset`) and founder `resetPassword`: the same, plus `revokeAllMcp` (personal MCP token and every OAuth grant).
- Connected apps: `GET /api/mcp/grants` lists OAuth grants of the signed-in account; `DELETE /api/mcp/grants?id=` revokes one, `?all=1` all. A grant id of another account is a 404. Refreshing a token keeps the grant and deletes the previous access token.
- Teams (2026-09-29): a member's password change or reset stamps that member's own `sessionsAfter` (its other devices only); an owner reset and a founder `resetPassword` also stamp `teamSessionsAfter` on the owner record, which signs every member out; a removal, a member leaving and a seat pause end that member's sessions at their next request, because `currentUser` re-reads the member record; `createUser` stamps `sessionsAfter` at creation, so a session from an earlier account at the same address never revives. Listing and revoking grants is owner only (`oauth.grants`).
