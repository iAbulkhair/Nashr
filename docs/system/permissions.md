# Nashr: permissions (as implemented)

What the code enforces, written at HEAD `4959f7e` and updated since; the teams and roles model (sections 0.1 and 1.1a, and the role notes in every table) was added on 2026-09-29. Paths are relative to the repository root; API route files are under `src/app/api/` and are written without that prefix in the tables. `file:line` points at the line where the check happens; rows changed on 2026-09-29 name the function or the `src/lib/roles.ts` action instead, because line numbers drift.

## 0. Actors and the functions that identify them

| Actor | How the code identifies it | Function |
|---|---|---|
| Anonymous | No check | none |
| Signed-in login | Cookie `nashr_session` to `session:{token}` (`{email, at, imp?}`) to the LOGIN it names: an owner record `user:{email}` or a member record `member:{email}` (the owner record wins should both exist). It always returns the OWNER's `User`, which is the account, with a runtime-only `actor` saying who is acting, plus `brandId` and `scope`. The refusals are in 0.1. | `currentUser()` and `resolveSession` in `src/lib/auth.ts` |
| Account owner | The login whose `user:{email}` record is the account: actor `{kind:"owner", role:"owner"}`. Created by signup. The only role that can pay, delete the account, write governance, mint the MCP token, approve OAuth apps or manage admins (0.1). | `currentUser()` |
| Member of an account (role `admin` or `member`) | A login at `member:{email}` whose `memberOf` names the owner, created only by accepting an invite. Resolves to the OWNER's account: every read and write uses the owner's workspace. Actor `{kind:"member", email: the member's own address, role}`. Never in `users:all`, never given credits, a referral code or signup tracking. | `currentUser()`; records in `src/lib/team.ts` |
| Account of the resource | Every workspace reader and writer takes the caller's scope `sc(u)` (`src/lib/auth.ts`), built from the OWNER email and the acting login's active brand, so ids from the request only resolve inside the account's own workspace. The owner and the account's members share that workspace; nobody outside the account can be given access to it. | `sc(u)` plus the scoped getters in `src/lib/brand.ts`, `files.ts`, `conversations.ts`, `connectors/store.ts` |
| Founder impersonating an account | A session written by the console's `impersonate` action carries `imp` (the founder's email, or `"key"` for the console key): actor `{kind:"founder", role:"owner", impersonating}`. Refused every action in `IMPERSONATION_BLOCKED` (0.1) and the founder console itself. | `currentUser()`, `can()` |
| Founder admin | `WAITLIST_ADMIN_KEY` in header `x-admin-key` (30 tries per IP per 15 min, bucket `adminhdr:{ip}`) or cookie `nashr_admin`, never in the URL; or a session whose actor is the owner login itself (`kind:"owner"`, actor email equal to the account email) with that email in `ADMIN_EMAILS`. A member of a founder's account and a founder impersonating never pass. | `adminActor(req)` and `isAdmin(req)` (APIs), `isAdminCookie()` (pages), `isFounderActor(u)`, all in `src/lib/auth.ts` |
| Cron | Header `Authorization: Bearer ${CRON_SECRET}`; denied when the variable is unset | inline in each cron route |
| MCP bearer | Header `Authorization: Bearer nashr_...` to `mcptoken:{token}` to `user:{email}`; refuses a `suspended` account and a token whose email is a member login (even should an owner record exist at the same address); sets `scope` from the owner's active brand like a session; actor `{kind:"token", role:"owner"}` | `userFromBearer(req)` `src/lib/mcp.ts` |

There is no global guard. `src/proxy.ts` does not authenticate (`src/proxy.ts:15-30`); every handler enforces its own rule, and a handler without a check is public.

### 0.1 Roles, members and seats (2026-09-29)

Files: `src/lib/roles.ts` (the table), `src/lib/team.ts` (member logins, invites, seats), `src/lib/auth.ts` (resolution, `PLAN_SEATS`, `seatLimit`). Design: `docs/superpowers/specs/2026-09-29-teams-design.md`.

1. Three roles. `owner` belongs to the `user:` record only and can never be assigned, removed or transferred. `admin` and `member` belong to member logins (`Member.role`): chosen at invite, changed only by the owner.
2. One table, `MIN_ROLE` in `src/lib/roles.ts`, names the minimum role of each action. `can(u, action)` answers; `forbid(u, action)` returns a 403 `{error:"forbidden"}` or `null`. Routes call it right after `currentUser()`; the chat tools (`TOOL_ACTION` in `src/lib/chat.ts`), MCP dispatch (`MCP_TOOL_ACTION` in `src/lib/mcp.ts`) and the pages use the same function. A control hidden on a page is display only; the route refuses regardless.
3. `can` fails closed. It answers false without a user or an actor, for an unknown action (an own-property test, so `__proto__` is unknown), for a role that is not one of the three, and when kind and role disagree (a member holding `owner`; an owner, token or founder not holding `owner`). `team.leave` is true only for kind `member`. Otherwise the actor's rank (member 1, admin 2, owner 3) must reach `MIN_ROLE[action]`. Users built by the cron (`allUsers()`) carry no actor, so a `can()` check on a cron path refuses.

| Needs | Actions (`MIN_ROLE`) | Covers |
|---|---|---|
| owner | `billing`, `account.delete`, `governance.write`, `mcp.token`, `oauth.approve`, `oauth.grants`, `referral`, `profile.account`, `team.invite.admin`, `team.role`, `team.remove.admin` | Pay links and activation; account deletion; governance writes; the personal MCP token (status, mint, revoke); OAuth consent and connected apps; referral data; the account's phone, language and email preferences; inviting or promoting an admin; any role change; removing an admin |
| admin or owner ("admin+") | `brand.write`, `brands.manage`, `onboard`, `catalog.import`, `connectors`, `schedule.write`, `publish`, `files.core.delete`, `files.core.write`, `performance.delete`, `performance.import`, `team.invite.member`, `team.remove.member`, `team.invites.view`, `team.invite.cancel` | Brand file writes (route, profile brand fields, chat `update_brand`); brands add, rename, archive; onboarding; catalog import; connectors (start, callback, key, disconnect, page and ad-account choice, product import); schedule and routine switches; approving and publishing (route, inbox approval, chat `publish_item`); deleting a core memory file, and writing one (route and chat `write_file`: writing one empty is deleting it); importing campaign results from a CSV and deleting them (an import replaces the last); inviting and removing plain members; seeing and cancelling pending invites (an admin cancels member invites only) |
| member (every login of the account) | `chat`, `generate`, `images`, `drafts`, `conversations`, `feedback`, `notifications`, `tools`, `support`, `integrations.request`, `brands.switch`, `read`, `team.view`, `team.leave`, `password.change`, `profile.self` | Chat, generation and images (charged to the account); editing, rejecting, reopening and rescheduling drafts; conversations; thumbs; notifications; free tools; support and integration requests; switching one's own active brand; reading everything in the workspace, the store and ad syncs included; the roster; leaving (members only); one's own password, name and interface language |

4. Founder impersonation. `IMPERSONATION_BLOCKED` is `account.delete`, `password.change`, `team.invite.member`, `team.invite.admin`, `team.invite.cancel`, `team.role`, `team.remove.member`, `team.remove.admin`, `mcp.token` and `oauth.approve`. Actor kind `founder` is refused all of them whatever its role, so nothing that outlives the two-hour session can be created. Everything else the owner may do, a founder impersonating may do.
5. Member refusals (`resolveSession`, on every request). `currentUser()` returns `null` for a member session when the member record is missing (removed, or left), is `disabled` (seat-paused), holds a role other than `admin` or `member`, or has an empty `memberOf` or one equal to its own address; when the session carries `imp`; when the session predates `member.sessionsAfter` (the member's own password change or reset; set to `acceptedAt` on creation); when the owner record is missing or suspended; when the member is not on the owner's roster (`members:{owner}`, `onRoster`); when the session predates `owner.teamSessionsAfter` (owner reset, founder reset); or when the member was accepted before the owner record was created, so a re-registered owner address inherits nothing. Membership is never cached in the session: a removal, a role change or a seat pause applies at the member's next request. Owner sessions keep their checks (`suspended`, `sessionsAfter`), and `createUser` now stamps `sessionsAfter` at creation.
6. Scope. Always `scopeFor(owner email, brandId)`. `brandId` comes from `activebrand:{login}`, the acting login's own key; a member's value must be one of the owner's active brands, else `default`. A member's address never becomes part of a workspace key, and `tests/scope-usage.test.ts` fails when a page or customer route passes an actor, member, owner or login email to a workspace reader.
7. Shared by everyone in the account: the credits and the plan (`charge(u.email, ...)`), the per-agent caps and counters, the chat ceiling (`chat:h:{owner}`, `chat:d:{owner}`), the notification bell and its read state (`notifs:{owner}`), model usage, and product analytics (a member's login is tracked on the owner email). Not recorded: which login approved, published, edited or chatted; tasks, decision records and publishes carry no actor. Support tickets and integration requests record both the acting login (`user` / `email`) and the account (`account`).
8. Seats. `PLAN_SEATS`: trial 3, starter 1, pro 3, agency 7, enterprise 25, the owner included; `User.seats`, set in the founder console, overrides when it is a positive integer (`seatLimit`). Seats used = 1 + members not disabled + unexpired invites, counted under `lock:team:{owner}` at invite and again at accept. `enforceSeats` runs after every plan or seat change in `POST /api/admin/plan`, today the only code that changes either.
9. The founder console follows the actor, not the account: `isFounderActor(u)` is true only for the owner login itself with its own email in `ADMIN_EMAILS` (section 4).

## 1. API routes (66 route files, 104 exported handlers on 2026-09-29)

Legend for "Who": A = anonymous, U = signed-in login (the owner or a member), O = a login of the account that owns the addressed resource (U plus scope binding), F = founder admin, C = cron secret, M = MCP bearer token.

Roles (since 2026-09-29): a row names the `src/lib/roles.ts` action its handler checks with `forbid` or `can`, and that action's minimum role: owner; admin+ (admin or owner); member (every login of the account). A U or O row that names no role accepts every login of the account, members included. `tests/role-gates.test.ts` holds the same map (`ROUTE_ROLES`, `GATED_GETS`) and fails when a POST, PUT, PATCH or DELETE handler is missing from it or does not check what it declares.

## 3. Cross-tenant isolation

### 3.1 How a scope is derived
1. `currentUser()` resolves the session's login (section 0.1): an owner login loads its own record; a member login loads the owner's. In both cases `activeBrandId(login)` reads `activebrand:{login}` (default `"default"`), a member's value must be one of the owner's active brands, and `scopeFor(ownerEmail, brandId)` returns the owner email for the default brand or `` `${ownerEmail}#${brandId}` `` otherwise (`src/lib/auth.ts`, `src/lib/brands.ts`). A member's own address is never a scope.
2. `sc(u) = u.scope ?? u.email` (`src/lib/auth.ts:26`). `scope` and `brandId` are runtime only and stripped by `saveUser` (`auth.ts:51`).
3. The active brand can only be set to an id found in the account's own `brands:{owner}` list (`brands/route.ts`), or to a brand just created by `addBrand`. Both move only the acting login's `activebrand:{login}`. Archiving the brand the caller has open resets the caller's key to `default`, and an admin archiving the brand the owner has open resets the owner's key too. `activeBrandId` does not re-validate the owner's own stored id; a member's is re-validated on every request.
4. Brand ids are 8 base36 characters from `Math.random()` (`brands.ts:34`).
5. Every brand-scoped key embeds the scope string (see `architecture.md` section 3). Isolation between tenants therefore depends on (a) the session to email mapping and (b) scope strings of different accounts never being equal.
6. Account-level (not brand-level) records: user, credits, sessions, notifications, MCP tokens, referral data, usage, analytics. The per-agent monthly counters live on the account's user record but are keyed by brand scope (`agentSpend.by[scope]`), and the caps they are checked against are per brand (`gov:{scope}.agentCaps`), so one brand's spend and caps never apply to another. Chat thumbs are per brand scope since 2026-09-21 (`fblog:{scope}`), and so is the feedback built from them, the decision records and the judge's notes for an agent's prompts (`feedbackFor`, 2026-09-29). Since 2026-09-29 the account also holds its team: `members:{owner}`, `invites:{owner}`, the `member:{email}` records and each member's `activebrand:{member}`; all of them are keyed by the owner email or the member's own login, never used as a scope.
7. Cron and admin code construct scopes with the same `scopeFor` (`allUsers()` in `schedule.ts:157-167`, `admin/users/[email]/route.ts:24`, `account.ts:26`). The routines cron keys every read and write by the `scope` `allUsers()` set (`routinelast:{scope}:{id}`, `routinelock:{scope}:{id}`, `routinecap:{scope}`, `routinehold:{scope}:{id}`, `routinetry:{scope}:{id}:{period}`, `schedule:{scope}`, `gov:{scope}`, the tasks).
8. MCP callers resolve the active brand the same way a browser session does (`userFromBearer`, `src/lib/mcp.ts`), so a bearer token works in the brand the owner has active. Fixed 2026-09-20; it used to always mean the default brand. Tokens resolve to owner accounts only: a token naming a member login is refused.
9. Members (2026-09-29). A member session resolves to the owner's `User`, so `sc(u)`, `charge(u.email)`, plan checks and every scoped getter work unchanged and never see the member's address; only `u.actor` differs. The routes that act on a member or an invite take the email or invite id from the request but act only on a record whose `memberOf` or `owner` is the caller's account (3.2).

## 4. Admin model

1. `adminEmails()` (`src/lib/auth.ts:108-110`): `ADMIN_EMAILS` split on commas, normalized. When the variable is unset the list defaults to one hard-coded address in the source.
2. `isFounder(email)`: membership test. Used by `isFounderActor(u)` (sidebar link, `adminActor`, `isAdminCookie`) and as the recipient list for golden-set alerts (`golden.ts`, `adminEmails()`). `isFounderActor(u)` requires `u.actor.kind === "owner"` and `u.actor.email === u.email` besides the list: a member of the founder's own account (whose `u.email` is the founder's) and a founder impersonating never pass (2026-09-29).
3. `adminActor(req)` (`src/lib/auth.ts`) and `isAdmin(req)` (= `adminActor(req) !== null`), used by every `/api/admin/*` data and action route plus the admin branches of `/api/support`, `/api/affiliates`, `/api/integrations`: `"key"` when `WAITLIST_ADMIN_KEY` is set and equals header `x-admin-key` (throttled 30 per IP per 15 min) or cookie `nashr_admin` (`sameSecret`), otherwise the founder's email when `isFounderActor(currentUser())`, otherwise `null`. The key is never read from the URL.
4. `isAdminCookie()`, used by `admin/page.tsx`: the `nashr_admin` cookie or `isFounderActor(currentUser())`.
5. `nashr_admin` cookie: set by `POST /api/admin/login` after a rate-limited, constant-time comparison; the cookie value is the key itself; 30 days; httpOnly; lax (`admin/login/route.ts:9-19`).
6. Founder accounts are ordinary users: they sign up through the public signup route. Whoever registers an address listed in `ADMIN_EMAILS` (or the default address) becomes a founder, because signup has no email verification (`auth/signup/route.ts`).
7. A suspended founder loses the session path (`currentUser` returns `null`) but the key path still works.
8. Impersonation (`admin/users/[email]/route.ts`): requires `adminActor`. Saves the caller's current `nashr_session` value in `nashr_return` (2 h), sets `nashr_impersonate` to the target email (2 h), then `createSession(target, 2 h, {imp: who})`: the session record carries the founder (or `"key"`) and resolves to actor kind `founder`, role `owner`. While impersonating, the founder console is closed through the session path (`isFounderActor` is false) and the `IMPERSONATION_BLOCKED` actions are refused; everything else acts as the owner.
9. Return (`admin/impersonate/route.ts`): no admin check; deletes the impersonation session record, restores `nashr_return` into `nashr_session` when that token is still a live session, clears the helper cookies, and logs `impersonate:stop` with `actor` = the `imp` the burned session carried and the `nashr_impersonate` value as the subject.
10. Audit: `admin:log` entries written by `POST /api/admin/users/{email}` and `POST /api/admin/plan` carry `actor` = the founder's email or `"key"` (`adminActor`), the target email, action, optional before/after (plan, credits, seats, the team members paused or restored) and reason. `POST /api/admin/golden` still writes the literal `"founder"`. Actions taken while impersonating are marked only in the session record (`imp`), not in the task, decision or publish records. `setLang` is not logged.
11. `WAITLIST_ADMIN_KEY` has two further roles: it gates `GET /api/waitlist` (query string only) and it is the fallback encryption secret for connector credentials when `CONNECT_SECRET` is unset (`src/lib/connectors/store.ts:14`).

## 5. Unclear or missing rules

Each item states what the code does and why the intended rule cannot be read from it. None of these is guessed as intended or unintended.

1. **Email characters versus scope strings.** Signup accepts any address matching `^[^\s@]+@[^\s@]+\.[^\s@]+$` (`auth/signup/route.ts:9`), which allows `#` and `:`. Extra-brand scopes are `email#brandId` (`brands.ts:28`) and keys are `prefix:{scope}[:{id}]`. An account registered as `victim@x.com#<brandId>` has a default scope equal to the victim's brand scope, and an account registered as `victim@x.com:<convId>` has a default thread key equal to the victim's `chat:{scope}:{convId}`. Both require knowing a random id. No rule forbids these characters and nothing states that scope strings must be unique across accounts.
2. **No email verification at signup.** Accounts become active immediately. Combined with `ADMIN_EMAILS` (and its hard-coded default), founder status is granted to whoever first registers a listed address. No rule says founder addresses must be pre-registered.
3. **No rate limit on OAuth client registration or `/api/oauth/token`.** Login and signup are throttled per IP and per email; support, affiliates and waitlist were given a per-IP limit on 2026-09-20; chat is bounded per account (`CHAT_PER_HOUR`, `CHAT_PER_DAY` in `src/lib/rate.ts`) because a turn costs no credits and can run up to five model calls. `clientIp` prefers the platform headers and falls back to the last `x-forwarded-for` hop (`rate.ts`).
4. **Password policy differs by route.** Reset requires 8 chars plus a letter and a digit (`auth/reset/route.ts:13`); signup and change-password require only 8 chars server-side (`auth/signup/route.ts:10`, `account/route.ts:12`); the signup form enforces the stricter rule client-side only. Update: signup, change and reset, and invite acceptance, all use `strongPassword` server-side now.
5. **Sessions end when the password changes.** Fixed 2026-09-18. A session record is `{email, at}`; the user record carries `sessionsAfter`, set on password change, password reset and founder `resetPassword`; `currentUser` refuses any session issued before it, including the older bare-email records (treated as issued at 0). The device that changed the password gets a new session. Password writes now happen inside the user lock on the fresh record. Suspension is still enforced on read. Since 2026-09-29 a session record may also carry `imp` (impersonation), `createUser` stamps `sessionsAfter` at creation so a re-registered address never revives an old session, each member has its own `sessionsAfter` (its own password change or reset), and the owner record's `teamSessionsAfter` (owner reset, founder reset) signs every member out without touching the owner's sessions.
6. **Suspension.** Fixed: `userFromBearer` (`mcp.ts:31-32`) refuses a suspended account, so its MCP personal and OAuth tokens stop working, and `allUsers()` (`schedule.ts:163`) skips suspended accounts, so no cron (weekly plan, routines, daily emails) charges or emails them. The `User.suspended` comment says "login and all API access blocked" (`auth.ts:21`).
7. **MCP token revocation.** Fixed 2026-09-18. Every OAuth token pair belongs to a grant (`mcpgrant:{email}:{id}`, index `mcpgrants:{email}`). `GET /api/mcp/grants` lists connected apps without tokens, `DELETE ?id=` or `?all=1` revokes; the MCP page shows the list. Refresh rotation deletes the previous access token. Password reset, founder reset and `wipeAccount` revoke the personal token and every grant. Tokens issued before this change have no grant and cannot be listed; they expire on their own (30 d access, 90 d refresh) or die at the next password reset only if they were the personal token.
8. **MCP scope.** Partly fixed 2026-09-18: the approve route only writes scopes this server defines (`SCOPES`, today `noor`), and MCP `generate_content` applies the same trial-expiry check as `/api/generate`. On 2026-09-20 a token started resolving the active brand like a session, and `ask_noor` was put under the same per-account chat ceiling as the web route. Still open: there is one OAuth scope, so every token grants every MCP tool including `ask_noor` (which reaches `write_file`, `update_brand` and credit-spending tools; `publish_item` still needs an approved item).
9. **`POST /api/admin/impersonate` has no admin check.** It acts only on the caller's own cookies and requires `nashr_return` to be a live session token, so it cannot mint access, but the rule "founder only" is not enforced there.
10. **Impersonation lifetime and audit.** The log says `expiresInMin:120` and the banner says "2 hours max", but the impersonated session is a normal 30-day session and is not deleted on return (`admin/users/[email]/route.ts:87-90`, `admin/impersonate/route.ts:11-14`). Actions performed while impersonating are attributed to the target user; `admin:log` never records which founder acted. Update 2026-09-29: the impersonation session now lasts 2 hours, is burned on return, carries the founder in `imp`, is refused the `IMPERSONATION_BLOCKED` actions, and `admin:log` records which founder acted (section 4).
11. **Admin key handling.** `isAdmin` accepts the key in the URL query (`auth.ts:118`), where it can end up in logs and browser history, and every comparison now goes through `sameSecret` (`isAdminCookie` used `===` until 2026-09-20). The `nashr_admin` cookie stores the key itself rather than a derived session. Rate limiting applies to `/api/admin/login` only, not to guesses sent as `?key=` or `x-admin-key` to other admin routes. The same key doubles as the connector encryption fallback (`connectors/store.ts:14`), with a fixed development string as the last fallback. Update 2026-09-29: `adminActor` reads the key from the `x-admin-key` header (throttled) or the cookie only, never the query string.
12. **`GET /api/waitlist` uses its own check** (query key only, `waitlist/route.ts:55`) instead of `isAdmin`. Whether founders without the key should reach it is not stated.
13. **Publishing does not require approval.** `POST /api/publish/{id}` and the chat tool `publish_item` publish a task in any status and then set it to `approved` (`publish/[id]/route.ts:18-20`, `chat.ts:307-309`). The HTTP route also skips `targetsFor`, so any task type can be sent to any connected provider. The product copy describes an approval inbox; the code does not gate publishing on it. For the model-driven path, "only when the owner explicitly asks" is a prompt instruction (`chat.ts:82`), not a code check. Since 2026-09-29 approving and publishing need admin or owner (`publish`) on the route, the inbox approval and the chat tool; a plain member can draft, edit and reject only.
14. **Model-controlled writes are not re-validated.** `update_brand` writes `brand[field] = value` using the model's `field` (`chat.ts:283-286`); the enum is enforced only by the strict tool schema. Text crawled from user-supplied sites and imported catalogs is placed into prompts and `products.md` without marking it as untrusted.
15. **Server-side fetches of user-supplied URLs** (`crawl.ts:50`, `catalog.ts:12,26`, WordPress/WooCommerce/Odoo/PrestaShop base URLs in `connect/[provider]/key`) have no allow-list, no private-address or metadata-address block, and follow redirects. Verify errors and publish errors return fragments of the remote response to the caller (`key/route.ts:27`, `publish/[id]/route.ts:25`). No rule is written for acceptable targets.
16. **Connector OAuth callback is sessionless.** The connection is saved to the scope stored in `state`, whoever completes the redirect (`callback/route.ts:28`); the path provider is not checked against the state's provider; Shopify callbacks are not HMAC-verified. OAuth tokens are never refreshed although `expiresAt` is stored.
17. **Account deletion leaves data behind.** `wipeAccount` (`account.ts:8-21`) deletes the `conns:{scope}` set but not the `conn:{scope}:{provider}` records holding encrypted third-party credentials; (fixed 2026-09-18: connector records, every task and conversation, the task index, the pending set, the personal MCP token and all OAuth grants are deleted); it still leaves `session:*` (harmless: the user record is gone),  `notifs:`, `notified:`, `notifseen:`, `usage:`, `uev:`/`ulast:`/`ufirst0:`, `fb:`/`fblog:` (fixed 2026-09-21: `fblog:{scope}` for every brand and the legacy `fb:` counters are now deleted — the log holds the free-text reason the owner typed; `decisions:{scope}`, added 2026-09-29, is deleted for every brand for the same reason; the `usage:` counters of the last 36 months are deleted from the list `usageMonthKeys` builds from `KINDS` and `AGENT_IDS`, so the per-agent counters added 2026-09-29 go too), `ref:`, `referrals:`, `referredBy:`, `shared:`, OAuth tokens, membership in `users:all` and `active:*` sets, tickets, and for non-default brands the `profile:{scope}` key. A `deleted-accounts` entry keeps the email. No retention rule is documented in code. Since 2026-09-29 `wipeAccount` also deletes the team (`wipeTeam`): every member login and its `activebrand:`, every invite, `members:{owner}` and `invites:{owner}`, so a member login never survives to join a new account registered at the owner's address.
18. **Whole-record user saves outside the credit lock.** `PUT /api/profile`, `PATCH /api/account` and `POST /api/auth/reset` call `saveUser` with the record read at request start (`profile/route.ts:39`, `account/route.ts:15`, `reset/route.ts:22`), so a concurrent `charge` or `refund` can be overwritten, and since 2026-09-29 that includes the per-agent counters (`agentSpend`) the charge wrote. `POST /api/referral/share` checks and sets its once-only flag in two steps (`share/route.ts:16-18`), as do `once()` and `pushNotif` fingerprints. Update 2026-09-29: `PUT /api/profile`, `PATCH /api/account` and `POST /api/auth/reset` now write the owner record inside `withUserLock` on the fresh record, and a member's fields go to its own record under `withMemberLock`.
19. **Brand-scope inconsistencies inside one account.** Pages fixed 2026-09-18: files, governance, tasks, generate, onboarding, and `listConnections` in chat and reports now read `sc(u)`; `tests/scope-usage.test.ts` fails when a page or customer API route passes the bare account email to a workspace reader. Still open: email preferences are written to `profile:{sc(u)}` and cron reads the scope first and the account second; the founder overview counts credits from the default brand only.
20. **Credits and plan limits not tied to a payment event.** Plans and credits change only through the founder console. Free tools are unlimited and free for signed-in users (`tools/[tool]/route.ts:15`), onboarding and catalog import are uncharged and repeatable, and trial expiry is not checked for image generation. `BRAND_LIMIT` is checked only when adding a brand, not after a downgrade. Whether these are intended is not stated.
21. **Layout guard depends on a header.** The layout redirect runs only when `x-pathname` is non-empty (`layout.tsx:24`) and public paths are matched with `endsWith`. Every current page has its own guard except `reset` (public by design), so this is defence in depth only; the rule for future pages is unwritten.
22. **`next` redirect parameter.** Login and signup accept `next` when it starts with `/` and not `//` (`AuthForm.tsx:23,75`). A value beginning with `/\` passes this test; browsers may treat it as protocol-relative. No server-side rule exists for post-login destinations.
23. **No CSRF token.** State-changing routes rely on `sameSite=lax` cookies and JSON bodies. `POST /api/oauth/approve` and `POST /api/admin/impersonate` accept form posts. MCP and OAuth endpoints send `Access-Control-Allow-Origin: *` (bearer or public by design).
24. **Anonymous counters without expiry.** Fixed 2026-09-18 for the free tools: the limiter is `allow("tool:{ip}")` with a 24 h window and the platform IP. The in-memory store honours TTL since 2026-09-18.
25. **Email normalisation on founder actions.** `POST /api/admin/users/{email}` looks the user up with a normalized email but passes the raw decoded path value to `withUserLock` and `wipeAccount` (`admin/users/[email]/route.ts:47-48,94`). With a mixed-case path value the lookup succeeds while the wipe targets different keys and the log still records `delete`.
26. **Pages that still offer what the route refuses (teams, 2026-09-29).** Fixed 2026-09-29: the inbox and chat cards offer a plain member no Approve or Publish (an edit is saved without approving) and say who approves; the WhatsApp card is the owner's only; the files page hides catalog import and core-file edit and delete from members; reports hide the CSV import and removal; the start page tells a member who sets the brand up; every refused call on these screens says the role does not allow it, and none is shown as a success. The profile page hides the password and delete forms from a founder viewing the account.
27. **Core files can be overwritten by any member.** Fixed 2026-09-29: writing a core file needs admin+ (`files.core.write`) in `PUT /api/files` and in the chat's `write_file`, as deleting one does, and replacing imported performance data needs admin+ (`performance.import`) as deleting it does. A member still writes any other file, and a rejection's reason is still appended to `preferences.md` by the tasks route (a system write in a fixed shape, not the member's text as a file).
28. **Signup does not see a pending invite.** No invite-by-email index exists, so an address with only a pending invite can sign up as an owner; the later accept then answers 409 `unavailable` under `lock:login:{email}`.
29. **An owner reset does not remove invited logins.** An owner reset signs every member out (`teamSessionsAfter`), but a member login invited by someone who held the old password stays, and can sign back in with its own password. Nothing prompts the owner to review the Members page after a reset.
30. **No attribution to the acting login.** Tasks, decision records, publishes, brand edits and chat history carry no actor; the account's notification bell and its read state are shared by everyone in it; the chat ceiling is per account. The design lists per-actor attribution as later work.
31. **Cron paths carry no actor.** `allUsers()` returns users without `actor`, so any `can()` check added to a cron-driven path refuses (fail closed). Routines and the weekly plan call `generate` directly and have no role check today.
32. **Plan changes outside the console.** Only `POST /api/admin/plan` changes a plan or seat count and it runs `enforceSeats`; any future billing webhook or checkout must call it too, or members above the new limit keep working until the next console change.
33. **The chat still offers refused tools.** A plain member's chat shows the model `update_brand`, `publish_item` and `import_catalog`; `runTool` refuses them in code and the model relays the sentence. Filtering the tool list by role would change the cached prompt prefix per role.
34. **Hand-passed invite links prove nothing about the address.** When mail is not set up (`mailReady()` false, the case in production until `MAIL_FROM` is set), the invite link is returned to the inviter, who can accept it themselves and hold a member login at an address they do not control; signup at that address then answers `exists`. With mail set up the link reaches only the invited address (a failed send withdraws the invite). Signup itself does not verify an address either, so an unregistered address can be taken either way; the founder console can now look a member login up by address and remove it (`removeMember`), as it can delete an owner account.
35. **A paused member comes back only on a limit change.** `enforceSeats` brings paused members back oldest first when the limit grows; removing someone frees a seat for a new invite but does not resume a paused member, and the owner has no resume action. Removing the paused member and inviting the address again works.

## Brand rules (2026-09-28)

The owner's banned words are enforced in code, not only in prompts (`src/lib/brand-rules.ts`). A customer-facing item whose text contains one cannot become `approved` through `PATCH /api/tasks/{id}` (409 `brand_violation`), cannot be published through `POST /api/publish/{id}` (409) or the chat tool `publish_item` (refused), and is created `pending` even when its type is auto-approved. Any login of the account can still edit it or save it as pending (`drafts`), and the owner or an admin can remove the word from the brand file (`brand.write`); nothing else lifts the rule.
