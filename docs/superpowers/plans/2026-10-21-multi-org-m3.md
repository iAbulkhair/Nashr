## Global constraints

- Tenant isolation: no route reads an account id or a person id from the request. The transfer accept names a workspace handle, matched only among the signed-in person's own held accounts (`heldAccounts` + `matchHandle`, rule 2112); the console names an address, resolved through `getLogin`.
- Lock order (rule 2139): `lock:team:{aid}` → `lock:login:{email}` → `lock:person:{pid}` → `lock:member:{email}` → `lock:user:{aid}`. Locks are not reentrant.
- No `await db.*` in a loop: `Promise.all` / `pmap`.
- Secrets: the transfer token is 32 random bytes, mailed once, stored only as its SHA-256, compared with `sameSecret`, carried in the link's fragment (never a query string), never logged and never in a team-log row.
- Mail sends happen outside every lock.
- Every new route authenticates first; the people view is behind `isAdmin` + `staffMay("workspace.view")`; the offer and the delete are rate-limited per person (`src/lib/rate.ts`).
- Expand only: `xfer:` and `invitesfor:` are new keys that M2 code never reads; the account record's fields that a transfer changes (`ownerPid`, `email`, `name`, `phone`, `emailVerifiedAt`, `billing`) already exist and M2 reads them as today.

## Spec reconciliation (rulings, fail-closed where the spec is silent)

1. **Transfer scope.** A transfer runs only when the account is not its owner's legacy account (`acct(u) !== ownerOf(u)`, an M2 `a_` account or one transferred before) and both the old and the new owner have a `person:` row (`source === "person"`). Otherwise 409 `transfer_unavailable`. Reason: until M4/S2 a legacy account record is also its owner's credential record (`resolveIds`' `same` path and `resolveLegacy` treat `acct === pid` as ownership), and a legacy member's `member:` record is their credential record. Moving ownership of such an account would either strand the old owner's credentials or delete the new owner's. Cost: legacy accounts cannot transfer until M4 (open risk, named in the report).
2. **Fresh proof from the owner.** The offer needs the owner's own password (the 2fa route's `passwordRefusal` pattern, `mfapw:` bucket) and, when two-step sign-in is on, a fresh authenticator code (recovery codes are refused for a transfer). A Google-only owner without a password is refused `password_required`. An impersonation (`IMPERSONATION_BLOCKED`) and an MCP token cannot offer.
3. **The receiving person's explicit accept.** The mailed link opens `/{lang}/app/workspaces#xfer=<handle>.<token>`; the page shows the offer and the person presses "Accept". The accept route needs the signed-in person whose pid is the offer's `toPid`, with a verified address, a held membership of that account (the handle match), and the token (`sameSecret` on its hash). Single use: the offer is deleted under the locks before anything changes; a wrong token deletes nothing.
4. **What changes at accept** (under `lock:team:{aid}` → `lock:login:{new}` → `lock:person:{new}` → `lock:user:{aid}`): re-read the offer, the account and the new owner's membership; the new owner must still be an enabled, live admin and the old owner must still own the account and be the offer's `byPid`. Then: MCP token and OAuth grants revoked (before the account write, and once more after it, so a token minted in between dies too); `ownerPid`, `email`, `name`, `emailVerifiedAt` from the new person, `phone` cleared (the old owner's number is theirs); the saved card cleared (`billing.card` and `paymob:card:{aid}`) and `billing.autoRenew` false, so the plan runs to `paidThrough` and nothing is charged (decision 8); the old owner gets an `admin` membership (`writeMembership`, accepted now, invited by the new owner); the new owner's `mbr:` row and roster entry go (an owner holds no membership); one `ownership_transferred` row. The new owner's owned-account cap is checked (`ownedCap ?? OWNED_CAP`): over it answers 409 `workspace_cap` with nothing changed.
5. **Sessions after a transfer.** The old owner's sessions are kept: `resolveIds` re-reads `ownerOf` and the membership on every request, so the next request resolves them as the admin they now are. The new owner's sessions likewise resolve as owner. No session is rewritten.
6. **Offer lifecycle.** One pending offer per account (`xfer:{aid}`, TTL 7 days); a new offer replaces it; the owner can cancel (DELETE). An offer is void at accept if anything in ruling 4 changed. `ownership_offered` is logged at offer.
7. **Delete person.** `DELETE /api/workspaces/person {password, code?}` behind `currentPerson()` and `MULTI_ORG`. Only a `person:`-source person (the others are legacy-shaped; their records go with M4/S2). Fresh proof as ruling 2 (recovery codes accepted here, as for disabling two-step). Refused 409 `owns_workspace` while `heldAccounts` lists an owned account. Otherwise each held membership is deleted under its own team lock (`pmap`, `deleteMembership`), then under `lock:login` → `lock:person` the person is read again (anything held now → 409 `busy`) and the person's keys go in one round (the `forgetPersonIfAlone` list: `person:`, `orgs:`, `lastorg:`, passkeys, two-step state, the waiting address change, the Google link both ways, every device session, the login index, plus `invitesfor:`); this device is signed out.
8. **Invitations inbox.** `createInvite` adds the invite id to `invitesfor:{email}` (TTL 7 days, refreshed) in the same round; accept, cancel, discard and a replaced invite remove it. `GET /api/workspaces/invites` reads the set for the signed-in person's own verified address only, re-reads each invite in one round and lists the live ones (the address matches, not expired, `inviteHolds`) as `{workspace, inviter, role, expiresAt}`: never an id, a token or the account id. Show-only: accepting stays on the mailed link (the token is never stored).
9. **Team log read.** `GET /api/team/log` (`team.log.view`: owner, admin; MULTI_ORG off 404). Rows carry `{at, kind, actor:{email}, target:{email}, role?, via}`: no person ids. Console rows show the owner as actor (never staff, as written).
10. **People view.** `GET /api/admin/people/{email}`: `isAdmin` (the handler's admin auth) and `staffMay(consoleRole, "workspace.view")`, then `getLogin` → the person → `heldAccounts` → one `pmap` round of each account (handle, workspace name, role, plan, suspended, paused) and the person's last sign-in. The answer has no hash, no secret, no token, no account id; an audit row is written before the answer. Read only (a `db` spy pins no write but the audit row).
11. **Rule 2131 pre-R1 half.** `resolveLegacy` reads `person:{email}` in its first round (one more command, no more rounds) and refuses a suspended person; when the resolved person id is not the address (an owner record with `ownerPid`, a member with a frozen other pid) the row is read in the member's second round, or in one more round for an owner (rare: such sessions predate the id change).

## Release step and rollback

- **Release step:** M3 lifecycle, **expand**. New keys `xfer:{aid}` and `invitesfor:{email}`; no stored shape changes; everything behind `MULTI_ORG` (false), so the release changes nothing live until the flag flips.
- **Rollback:** back to M2. M2 code never reads `xfer:` or `invitesfor:` (both expire in 7 days by themselves). A transfer made under M3 (flag on) leaves an `a_` account whose `ownerPid` names the new owner and an `admin` membership for the old one: both are M2 shapes M2 reads correctly. A deleted person is gone in both.

## Review focus

- The transfer cannot run without the owner's fresh password (+ code) and the new owner's own signed-in accept with the mailed token; a stolen token alone does nothing.
- After a transfer: no card on the account, renewal off, no MCP token or grant, old owner admin, new owner without a membership, exactly one `ownership_transferred` row.
- Delete person never touches an account it owns (refused) and leaves no key of the person behind.
- No new route reads an account id or person id from the request.
