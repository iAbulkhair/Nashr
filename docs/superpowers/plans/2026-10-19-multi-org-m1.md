## Global Constraints

Every task respects all of these. Quoted lines are from the spec or `CLAUDE.md`.

- **Switch.** `export const MULTI_ORG = false` in a new import-free module `src/lib/multi-org.ts`: "A code constant `MULTI_ORG = false` (not an environment variable, as `OPAQUE_IDS`): invites to existing logins still answer `unavailable`, no create-workspace route, no switcher. Production behaviour is identical." `docs/system/variables.md` does not change.
- **Ids.** `PersonId` and `AccountId` are branded strings modelled on `Scope` (`src/lib/keys.ts`). "A plain `string` from a request does not type-check in any builder (rule 2137)." Legacy owner: `pid = acct(u)` (the frozen first address while `OPAQUE_IDS` is off). Legacy member: `pid = memberPid(m)` (its address while `OPAQUE_IDS` is off, security review M1 of R1). New persons: `pid = "p_" + base32(crypto.randomBytes(15))` (26 characters, the `newAccountId` alphabet in `src/lib/account-id.ts`); in M1 only tests create them.
- **Ownership.** `ownerOf(u): PersonId = u.ownerPid ?? acct(u)`: "The only function that answers 'who owns this account'." The owner is never a membership row; `MembershipRow.role` is `"admin" | "member"` and "a row claiming it does not parse and grants nothing".
- **Keys** (all built in `src/lib/keys.ts`, new group `personKey`, plus two `accountKey` builders), exact bytes:
  - `person:{pid}` json `Person`; `lock:person:{pid}`; `orgs:{pid}` set of `AccountId` ("a hint for listing only. Every decision re-reads the forward records", rule 2136); `lastorg:{pid}` string `AccountId`;
  - `mbr:{aid}:{pid}` json `Membership`; `teamlog:{aid}` capped list (cap 500, `pushCapped`);
  - `activebrand:{pid}:{aid}`, `sec:feedof:{pid}:{aid}`, `sec:bookof:{pid}:{aid}:{prov}`;
  - existing `members:{aid}` keeps its builder; its values are `PersonId`s (a legacy member's pid is its address, so today's values already are).
  - Legacy `activebrand:{login}`, `sec:feedof:{login}`, `sec:bookof:{login}:{prov}` "stay readable in M1-M3 as the fallback for a person's HOME account" (a legacy owner's own account, a legacy member's `memberOf`), and M1 keeps writing them for the home account so a rollback reads current values.
  - `xfer:`, `invitesfor:` are M3: not built. "No family uses SCAN or KEYS."
- **Shapes** (`src/lib/stored.ts`, `z.looseObject`, read through `parseStored`): `PersonRow` and `MembershipRow` exactly as spec section 6; `User.ownerPid?: PersonId`; `Invite.aid?` (= `owner`, written beside it) and `Invite.invitedByPid?`; the session already carries `pid?`/`acct?` (R1). "A membership row that fails the schema reads as 'no membership' and is logged without values."
- **Adapter precedence** (rule 2134): `getPerson(pid)`: `person:{pid}`, else legacy `user:{pid}` (credential fields only), else legacy `member:{pid}`. `getMembership(aid, pid)`: `mbr:{aid}:{pid}` AND `members:{aid}` contains `pid`; else legacy `member:{pid}` with `memberOf === aid` AND the roster lists `pid`; else none. "A membership row without its roster entry, or a roster entry without a row, grants nothing."
- **Isolation.** "Tenant isolation: every read or write of tasks, files, conversations, brand, connections or plans uses the caller's scope from `sc(u)`. Never build a Redis key from an id, email or scope taken from the request." `sc(u)` keeps its body `storedScope(u.scope ?? acct(u))` with `u` the ACTIVE account. The active account comes only from the session record; `resolveSession` re-checks `roleIn` on the forward records on every request (rule 2111). No route reads an account id or pid from a request in M1 (the switch route's handle is M2).
- **Mirroring** (rule 2132). Every membership write (accept, role, pause, resume, removal, leave) writes `mbr:` + `members:` + `orgs:` AND the legacy `member:` fields for a home membership. Every credential write (password, name, language, two-step stamp fields, `sessionsAfter`, `devicesAfter`, `emailVerifiedAt`) takes `lock:person:{pid}`, writes `person:{pid}`, and writes the same fields to the legacy record it came from under that record's own lock.
- **Lock order** (rule 2139, with `lock:member` placed by this plan, see reconciliation 9): `inviteuse` → `lock:team:{aid}` → `lock:login:{email}` → `lock:person:{pid}` → `lock:member:{email}` → `lock:user:{aid}`. Locks are not reentrant; a callee that runs under a held lock takes a `locked` flag (the `releaseLogin` pattern).
- **Redis.** "Redis is HTTP per command: no `await db.*` inside a loop. Use `Promise.all` or `pmap`." A session with `pid`/`acct` resolves in one parallel round after the session read; "a session written before M1 resolves as today" (rule 2135).
- **Expand only.** Old builds ignore every new key and field; a rollback from M1 to any earlier build is safe. No conversion script in this release (S1 is out of scope). No contract step.
- **Docs in the same commit** as the behaviour: `docs/system/architecture.md` (sections 3, 4(f)), `flows.md` (new section 89, section 5), `permissions.md` (sections 0, 0.1, 3.1), `docs/system/tests/2110-multi-org.md`. `CLAUDE.md` does not change in M1 (the handle-as-selector sentence comes with the M2 switch route).

Before the last commit also `npx next build`. Commit per task; push nothing until the plan is done; then one push and a draft PR (CLAUDE.md CI rules).

## Spec reconciliation

The spec was written against `615b0624`; account-id R1 (#387) is now on `main`. Where they disagree the spec's intent wins; each line says what changes relative to the current code.

1. **Login index.** Spec forced change 1 is already built: `login:{e}` = `{kind:"person", pid}` (`LoginIndex`, `loginIndexOf`, `claimLogin`, `releaseLogin` under `lock:login:{e}` in `src/lib/auth.ts`, `src/lib/account-id.ts`). M1 reuses them unchanged and adds no index writer.
2. **Member ids and index.** Forced change 2 is half built: `Member.id` exists, `insertMember` claims `login:{memberEmail}`, `scripts/account-ids.ts` writes missing member indexes, `memberHolds` guards the legacy member step. Kept: while `OPAQUE_IDS` is off a member's pid is its address (`memberPid`, security review M1). So S1's `SET NX login:{memberEmail}` is already R1's script's job.
3. **Session `acct`.** R1 writes `pid`/`acct` (`sessionIds`) but resolves a member session only when `acct === m.memberOf` and an owner session only when `acct === acct(owner)`. M1 changes the test to the spec's: `acct` resolves when `roleIn(account, pid)` is not null on the forward records, whatever account it names. In production M1 only ever writes the home account (sign-in picks owned, then home membership), so behaviour is identical; an R1 build reading an M1 session that names a non-home account fails closed (`acct !== memberOf` → null).
4. **`getLogin`.** R1 returns `{kind:"owner", user, pid} | {kind:"member", member, owner, pid}`. M1 adds `person: Person` and `acct: AccountId | null` (the account sign-in would pick) to both variants and makes `member: Member | null` (null for a person known only through `mbr:` rows: test persons in M1, real ones from M2). A `p_` index resolves through `person:{pid}`; the owned account is found through `orgs:{pid}` forward-checked with `ownerOf`.
5. **Person precedence vs roll-forward.** The spec says `person:` wins (rule 2134) and calls M1 "safe to any earlier build". A rollback to a pre-M1 build that then changes a password writes only the legacy record, and on roll-forward a `person:` copy would win with the OLD hash. Spec intent (a rollback never leaves a stale password usable) wins: `getPerson` prefers `person:` unless the legacy record is provably newer (its `sessionsAfter` later than the person's, or its birth, owner `createdAt` / member `acceptedAt`, later than the person's `createdAt`); then the legacy fields are read and the mismatch is logged (`person stale`, shape only). Every M1 credential write mirrors both, so in steady state they never differ.
6. **Creation overwrites.** Signup (`createUser`) and accept-as-new (`acceptInvite`) are credential writes: they `SET` `person:{pid}` fresh under `lock:login` → `lock:person`. A leftover `person:{address}` from a deleted member can therefore never lend its hash to a new owner at the same address.
7. **Deletion and leaving keep persons, gated.** The spec keeps a person with no workspace (decision 10, rules 2124/2126) but M1 must behave as today, and today a removed or deleted member's address is free to sign up and cannot sign in. M1 rule: removing a membership never deletes the person while another live membership or owned account remains; when none remains and `MULTI_ORG` is false, the person goes exactly as the member login goes today (`member:`, `person:`, login index, devices, two-step, Google link, address change). With `MULTI_ORG` true (M2) the person is kept. `wipeTeam` is replaced by `wipeMemberships(aid)`.
8. **Class B per-login families** (`devs:`, `mfa:*`, `emailchange*`, `googlesub:`, `verify:*`): the spec makes them person-keyed "in meaning; for legacy persons the key bytes are the same". M1 keeps keying them by the sign-in address (identical bytes for every legacy person; test `p_` persons use their address too). Re-keying by pid belongs to account-id R2 (rule 1990), shipped with M2 (decision 11). Only the new per-(pid, aid) families are keyed by pid.
9. **Lock order.** Spec rule 2139 lists `inviteuse → team → login → person (→ user)` and omits `lock:member`, which R1 still uses for every member-record write. M1 places it after `lock:person` and before `lock:user`. One known exception stays: the unverified owner's address move (`src/lib/verify-email.ts`) calls `wipeAccount` holding `lock:login` and `lock:user`, and `wipeMemberships` then takes `lock:team`; an unverified account cannot have members or invites (rule 767), and every lock wait is bounded (3 s). The rule 2139 scan lists that one caller.
10. **`members:{aid}`.** Builder and bytes unchanged (`accountKey.members(owner: string)`); its values are read as `PersonId`. Every reader of the roster that treated values as addresses (`wipeAccount`'s `logins`, `onRoster(acct(u), partner.email)` in `src/lib/partners.ts`, `admin-workspace.ts`) moves to pids.
11. **`emailVerifiedAt`.** A person field (spec section 6), but rule 767 reads it on the ACCOUNT for every member's request. M1 writes it on the person and on every account the person owns (its contact address is the owner's), so `resolveSession` reads no owner person.
12. **`User.passHash` becomes optional** in the type (an account owned by a `p_` person has none). Every reader moves to `getPerson`; the compiler lists them.
13. **`currentPerson()`** is built and tested in M1 with an empty route allowlist: its callers (workspaces page and routes, switch, join for an existing person) are M2. Sign-out and the security settings keep `currentUser()` in M1.
14. **Invites.** R1 already writes `owner: acct(owner)`; M1 writes `aid` (same value) and `invitedByPid`, and reads `inv.aid ?? inv.owner`. With `MULTI_ORG` false `createInvite` keeps answering `unavailable` for any existing login (code path unchanged).
15. **Founder console.** `src/lib/admin-workspace.ts` has a local `ownerOf(chosen)`; it is renamed `accountForChosen` and resolves through `getLogin` (owned account, else home, else oldest membership) so `p_` test persons open. The people view (rule 2130) stays M3.
16. **`teamlog`.** `pushCapped` and `CAPS` exist in `src/lib/db.ts`; M1 adds `CAPS.teamLog = 500`. Rows are written in M1 (rule 2129, write half); the reader (`team.log.view`, Team log tab) is M3.
17. **Rules pinned in M1:** 2110 (session-based half), 2111, 2112 (scan and session half), 2115, 2118, 2119 (M1 half), 2120, 2121, 2122, 2124 (M1 half), 2125, 2126 (M1 half), 2129 (write half), 2131, 2132, 2134, 2135, 2136, 2137, 2139 (without transfer). Not pinned until later: 2113, 2114, 2116, 2117, 2123 (M2); 2127, 2128, 2130 (M3); 2133 (S1); 2138 (M4).
18. **Membership conflict reads the stricter field (Task 2 review ruling).** When `mbr:{aid}:{pid}` and the legacy `member:{pid}` both exist for the same account and disagree, `getMembership` reads the stricter value of each field (`member` over `admin`, paused over enabled, the later `acceptedAt`) instead of the plain "`mbr:` wins" of the spec's precedence. Plain precedence fails open after a rolled-back build pauses or demotes a member: the rolled-back build writes only the legacy record, so on roll-forward the stale `mbr:` row would restore the access the owner removed. The cost: a resume or a promotion made by a rolled-back build (legacy record only) is not honoured after roll-forward; the owner repeats it once. Pinned by "reads the stricter value" and "fails closed: a resume or promotion made only on the legacy record" in `tests/multi-org-adapters.test.ts` (rule 2134). The person stale guard (reconciliations 5 and 6) is the opposite case on purpose: a credential change by a rolled-back build (a new password, an address with its verification cleared) ends access or proves less, so the provably newer legacy record wins there.
