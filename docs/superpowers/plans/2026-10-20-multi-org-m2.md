## Global Constraints

- **Switch.** `MULTI_ORG` (`src/lib/multi-org.ts`) stays `false`. Every M2 path checks it and, while it is off, does exactly what M1 does: the proxy rewrites nothing and strips nothing new, `currentUser()` ignores any handle, the guard never answers 409, the new routes answer 404, `appHref()` returns today's `/{lang}/app/…`, invites to existing logins answer `unavailable`, signups are legacy. Tests turn it on per file with `vi.mock("@/lib/multi-org", async (orig) => ({ ...(await orig()), MULTI_ORG: true }))`; no test-only branch in product code.
- **Isolation.** "Never build a Redis key from an id, email or scope taken from the request." The only request value that picks an account is a workspace handle, used "only as a selector among the person's own memberships, re-checked on every request" (spec section 7). No route reads an account id or pid from a request (rule 2112 scan). The handle is matched against `wsHandle(aid)` of `aid`s read from `orgs:{pid}` and the session's `acct`; the match then goes through the full `resolveIds` check on the forward records (rule 2111).
- **Handle.** `wsHandle(aid) = "w_" + base32lower(HMAC-SHA256(CONNECT_SECRET, "ws:handle:v1:" + aid))[:16]` (rule 2114), with the same dev fallback as `booking-token.ts`. Never stored, never indexed, never contains an address.
- **Answers.** A foreign, unknown, stale or (for an impersonation) other-account handle: `notFound()` from `currentUser()`/`currentUserUnverified()`, so pages show the 404 page and routes answer 404, the same for every case (rule 2112). The switch route answers `{ ok: false, error: "not_found" }` 404 with the same body for each case.
- **Rounds.** No handle, or the handle of the session's `acct`: the two rounds of M1. Any other handle: one more round (`orgs:{pid}`), then M1's round for the matched account: three (rule 2135). No `await db.*` in a loop.
- **Writes of `acct`/`lastorg:`.** Only sign-in (M1 `pickAccount`), the switch route, create workspace and accept write them. Visiting a `/w/{handle}` link writes neither.
- **Expand/contract (rule 679).** M2 adds no stored shape an M1 build cannot read: a `p_` person, an `a_` account with `ownerPid`, `mbr:` rows, `orgs:`, `lastorg:`, `PersonRow.trialUsedAt` and `PersonRow.ownedCap` are all M1 shapes or optional loose fields. While `MULTI_ORG` is off none of the new writers runs in production, so this branch is an expand step and is safe to roll back to M1 or any earlier build. Once the flag is on, the rollback floor is M1 ("A build before M1 cannot sign in a `p_` person and ignores `mbr:`"): the flip PR says "rollback floor: M1". Nothing is contracted here (M4).
- **No data script.** No script runs, none is added. Account-id R2's re-keying of class B families (rule 1990) is not built here: decision 11 merges the two RELEASES, and M2 builds the signup half (a new signup is born `p_` person + `a_` account when the flag is on). The flip PR must carry R2's own preconditions (founder checklist).
- **Part C.** Not built. The path parser and `appHref()` accept and keep a `b/{brandId}` segment after `w/{handle}` untouched, so Part C later nests `/w/{handle}/b/{brandId}/…` without a second link migration.
- **Docs in the same commit** as the behaviour: `CLAUDE.md` (the handle-as-selector sentence), `docs/system/architecture.md` (sections 3, 4), `flows.md` (93.2, section 5), `permissions.md` (sections 0, 0.1, 3.1, 3.2), `docs/system/tests/2110-multi-org.md`. `variables.md`: no change (no new variable; `wsHandle` uses `CONNECT_SECRET`).

## Spec reconciliation

1. **Route segment as a proxy rewrite.** The spec says "a route segment `w/[handle]`". Moving every page folder under `src/app/[lang]/app/w/[handle]/` would change every production URL while the flag is off, which the flag must prevent. So the pages stay where they are and `src/proxy.ts` serves `/{lang}/app/w/{handle}/rest` from `/{lang}/app/rest` by `NextResponse.rewrite`, setting `x-thakeen-ws` to the handle and `x-pathname` to the address the browser shows. The URL contract, the header contract and the 307 are the spec's. Part C nests the same way (`b/{brandId}` read beside `w/{handle}`).
2. **The second guard lives in the proxy AND the wrapper.** Only 8 of 167 API routes use `handler()` (`src/lib/api-handler.ts`); about 60 call `sc(u)` directly. So the 409 `workspace_missing` check is one pure function `workspaceMissing(method, pathname, hasSession, header)` in `src/lib/ws-path.ts`, called by the proxy for every `/api/` request (it sees them all) and by `handler()` (defence in depth). Outside it: the `WORKSPACE_FREE` prefixes (auth, workspaces, team accept, the person's own security routes, the founder console, OAuth consent, staging access, webhooks, crons, MCP: the paths `crossSiteRefusal` already exempts, and any request without the session cookie). The coverage test: every route file with a state-changing export that calls `sc(` or `currentUser(` is covered (not under a `WORKSPACE_FREE` prefix), and every `WORKSPACE_FREE` prefix is a person-level, bearer, cron or webhook route.
3. **The `api()` helper is a fetch wrapper.** There is no `src/lib/api-client.ts` and about 120 raw `fetch("/api/…")` calls in 55 files. `src/lib/api-client.ts` exports `wsHeaders(pathname)` and `installWorkspaceFetch()`, which wraps `window.fetch` once (module load of the app shell's client provider, before any effect runs) to add `x-thakeen-ws` to same-origin `/api/` requests, read from `window.location.pathname`. With the flag off it installs nothing.
4. **Handle in pages and links.** Server components read the handle from the request (`x-thakeen-ws`, set by the proxy from the path) through `currentHandle()`; client components from the existing `WorkspaceProvider` context (`handle`, from the layout). `appHref(lang, path, handle)` builds every app link; `useAppHref()` binds the handle on the client. Active-link comparisons strip the handle (`stripWs`) so a pathname read before or after the rewrite compares the same.
5. **404 answer.** `notFound()` (Next 16 docs: works in route handlers) gives routes a 404 without the `{ error: "not_found" }` JSON body; the wrapped routes and the switch route answer the JSON body. Same status for every foreign handle, which is the rule's point.
6. **Owned-workspace cap per person.** Decision 3 ("you raise it per person from the console"): `PersonRow.ownedCap?` (loose, optional), default 3. No console control in M2 (the console people view is M3); the founder action is on the checklist.
7. **Trial once per person** (decision 4): `PersonRow.trialUsedAt` is set by signup (the first workspace) and by the first create; a second owned workspace starts on `trial` with 0 credits and `trialEnds` now (the plan picker shows). Legacy persons without the field: their own account counts as the used trial (a person who owns any account has used it).
8. **Accept for an existing person.** The join page with a token shows "sign in to accept" when `peekInvite` says the address has a person (`hasPerson`); sign-in keeps `next` to the join page (the token stays in the fragment, re-read by the page script). `POST /api/team/accept {token}` without a password, behind `currentPerson()` with the person's verified address equal to the invite's. A `p_`-less legacy person counts as verified when the account they own is verified or they are a member (a member was verified by accepting a mailed link).
9. **Old URLs.** The proxy cannot read the session's account, so the 307 is in the app layout (it reads `x-pathname`): signed in, flag on, no handle in the path, not a person-level page → `redirect()` (307 in a server component render) to `appHref(lang, rest, wsHandle(acct(u)))` with the query kept. Signed in with a valid person and no valid account → `/{lang}/app/workspaces`.

## Review focus

- With `MULTI_ORG` false nothing changes: the proxy, `currentUser()`, the guard, the links, invites and signup all give M1's answers (every existing test passes unchanged).
- A handle is only ever compared with handles computed from the session's own `acct` and `orgs:{pid}`, and the match is resolved through `resolveIds` on the forward records. It is never a key and never looked up.
- No route reads an account id or a pid from a request; the switch route takes a handle.
- Accept never creates a membership for an existing person by address alone.
