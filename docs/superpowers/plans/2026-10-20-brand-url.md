# Brand in the URL (Part C) Implementation Plan, with the Part B reconciliation

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Every brand page carries its brand id in its path (`/{lang}/app/b/{brandId}/…`), every browser API call carries the page's brand as a selector, old URLs answer 307, and one `appHref()` builds every app link, so two tabs on two brands each save into their own brand and multi-workspace M2 can later prefix `/w/{handle}` in one place.

**Architecture:** The brand id travels in the path for pages and in the `x-thakeen-brand` request header for APIs. `src/proxy.ts` strips any incoming header on page paths and sets it from the `b/{id}` segment; the client `api()` helper sets it from `location.pathname`. `currentUser()` reads it and, inside `resolveSession`, keeps it only as a selector among the session account's own active brands (no new round for sessions written from R1 on); a bad selector is `notFound()`. A proxy guard refuses a browser mutation to a brand-scoped route that carries no header (`brand_missing`), shipped in `log` mode in this expand release and switched to `enforce` in the contract release.

**Tech Stack:** Next.js 16.3 app router (`src/proxy.ts`, dynamic segments, `notFound()` in route handlers), Upstash Redis via `src/lib/db.ts`, vitest, Playwright e2e.

**Spec:** `docs/superpowers/specs/2026-10-09-admin-shell-and-brand-workspaces-design.md` Part C (C1-C8), read together with `docs/specs/2026-10-18-multi-org.md` section 7 "Workspace in the link" (decision 7, amended 2026-10-19) and rules 2112, 2113, 2135 in `docs/system/tests/2110-multi-org.md`.

## Rulings (founder delegated decisions, 2026-10-13; recorded in the PR body and `docs/system/tests/0885-brand-url.md`)

- R-C1 Header name `x-thakeen-brand` (not the spec's `x-nashr-brand`), matching M2's `x-thakeen-ws`.
- R-C2 The guard lives in the proxy (`src/lib/brand-guard.ts`, beside `crossSiteRefusal`), not in the route wrapper: only 8 of the 60 routes that call `sc(` use `handler()` today. A coverage test holds the guarded list to the routes on disk. M2's `workspace_missing` guard (rule 2113) can reuse the same list and place.
- R-C3 A bad selector (unknown, archived, another account's, malformed) is `notFound()` thrown from `currentUser()`/`currentUserUnverified()`: pages render the 404 page, APIs answer 404. The spec's `brand_not_found` body is not given (Next's 404 carries no JSON); the status is the contract.
- R-C4 Release step: **expand**. The guard ships with `BRAND_GUARD_MODE = "log"`: a mutation without the header is logged (`brand_missing`, path only) and proceeds on the session's brand, so a tab opened before the deploy (old JS, no header) keeps saving. The contract release flips it to `"enforce"` (409) after one release. Both modes are tested now.
- R-C5 `/{lang}/app` goes to the last chosen brand (`/{lang}/app/b/{u.brandId}`) whatever the brand count. The all-brands overview page (C5) is deferred to its own change; `/app/settings/brands` stays the management page.
- R-C6 Settings splits by the spec's rule (under `b/` when what the page shows or saves goes through `sc(u)`): `settings/brand`, `settings/connections` and `settings/governance` move to `/{lang}/app/b/{id}/settings/{section}`; the other sections stay at `/{lang}/app/settings/{section}`. `settingsHref` takes the brand for the three brand sections.
- R-C7 A session written before R1 (owner branch of `resolveLegacy`) that sends a selector reads `brands:{acct}` in one more round; rule 2135's "as today" stays true for requests without a selector. Pre-R1 sessions expire within 30 days.
- R-C8 Links from an account page to a brand section use the session's brand (`u.brandId`), passed from the layout; a client component never guesses a brand.
- R-C10 (from the scope map) `settings/notifications` reads and writes `profile:{sc(u)}` (`readPrefs(sc(u))`, `PUT /api/notifications/prefs`), so by the spec's rule it moves under `b/` with the other three brand settings sections.
- R-C11 The guard's list covers the five routes scoped only through `handler({ auth: "user" })` (`brand`, `brand/proposals/[id]`, `conversations`, `files`, `tasks`): the coverage test treats a route file that calls `sc(` OR uses `handler({ auth: "user"` with a mutating export as brand-scoped unless listed in `ACCOUNT_SC_API`.
- R-C12 Mixed `PUT /api/profile` (account fields and brand fields) is in `BRAND_API`. Shell components shown on account pages that mutate a brand route (Sidebar's new conversation, AccountSettings' profile save) send the session's brand explicitly from `WorkspaceContext.brandId` (`api(url, { headers: { [BRAND_HEADER]: brandId } })`); on a `b/` page the path's brand wins.
- R-C13 Browser navigations to brand GET routes (exports, the pptx download, `connect/{id}/start`, the calendar link start) cannot carry a header: they go through `apiHref(path)` (`src/lib/api-client.ts`), which appends `brand={id}` from the page path, and the proxy copies a `brand` query value into `x-thakeen-brand` on GET/HEAD `/api/` requests that carry no header. It is the same selector, checked the same way in `resolveSession`. Mutations never take it from the query.
- R-C9 Rules: 885-896 from the spec's block; 897-899 spare. No rule from 2500-2549 is needed.
