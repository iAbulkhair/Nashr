# Multi-workspace membership, release M4 (contract) and Script S2: implementation plan

**Goal:** Build the spec's "M4 contract" row and Script S2 (`docs/specs/2026-10-18-multi-org.md`, "Releases"): stop reading credentials from `user:`/`member:` and memberships from `member:`; stop writing them; drop the legacy per-login fallbacks `activebrand:{login}`, `sec:feedof:{login}` and `sec:bookof:{login}:*`; refuse sessions without `pid`. Then `scripts/multi-org-contract.ts` (S2) removes `passHash`, `sessionsAfter` and `devicesAfter` from legacy account records and deletes legacy `member:` records whose `mbr:` twin exists (rule 2138; differences are information only from fix round 1).

**Release step:** contract (rule 679). It is the only step that removes legacy reads. **Draft only:** it merges no earlier than 30 days after the M2 switch-on (the session TTL), on the founder's word.

**Base:** branch `claude/wave3a-m4-contract` at `main` `fe37b1d5`. Rules: pins rule 2138 (range 2110-2139). New numbers only from 2760-2769, listed in `docs/system/tests/2760-multi-org-m4.md` (rule 788). Flows: subsection **93.4** under section 93.

## Preconditions the release PR must check (all of them, written in the PR)

1. M2 (`MULTI_ORG = true`) has been live in production for at least 30 days (the session TTL), so no session written before R1 (no `pid`) can still be alive. A session without `pid` is refused from M4 on.
2. Script S1 (`scripts/multi-org-index.ts`, PR #426) ran with `--apply`, and a dry run of it, run from the live M3 build right before the M4 merge, reports every "set"/would-write count at 0 (`personsSet`, `membershipsSet`, `orgsSet`, `loginsSet`) and 0 conflicts and 0 orphans. Its refusals alone (conflicts, orphans, busy) do not prove that every person has `person:{pid}`, every membership an `mbr:` row and an `orgs:` entry and every address a `login:` index; the zero would-write counts do. M4 reads nothing else. S1 is retired in M4 (fix round 1): the M4 branch deletes the script and its test, so it runs only from a pre-M4 build.
3. No session without `pid` is left: the S2 dry run is not enough (sessions are not enumerable), so the 30 days of item 1 are the proof; the founder confirms the M2 switch-on date.
4. M3 (lifecycle, `claude/wave3a-m3-lifecycle`) is merged and live: the rollback floor of M4 is M3. That includes the M3 links script (rule 2756), which adopts the calendar and booking links made before M1 (sets `pid`/`aid` and the (pid, aid) pointer) so none dies at the M4 deploy.
5. The S2 dry run, run against production before the merge, reports `personMissing: 0`, `notInOrgs: 0` (the lock-out check of every owner and member, rule 2765), `twinMissing: 0` and `preM1Links: 0` (rule 2764: a link made before M1 that the M3 links script did not adopt would die at the M4 deploy). Any non-zero count is exit 1 and blocks the merge.

## Rollback

Back to M3 only. M3 (and M2, M1) read `person:` and `mbr:` first and the legacy records as a fallback, so everything M4 writes reads the same there. A build before M1 is forbidden: it reads credentials only from `user:`/`member:`, which S2 has emptied (no `passHash`: nobody could sign in) and whose `member:` records S2 deleted (every legacy member locked out), and it ignores `person:` and `mbr:` entirely. A build before M2 is forbidden as well (M2's rollback row: memberships only in `mbr:` and `p_` persons exist from M2 on). The release PR says "rollback floor: M3". After any rollback to M3 and roll-forward to M4, run the S2 dry run again (then `--apply` on the founder's yes): the M3 build writes the legacy copies again.

## Tasks

1. **Plan** (this file), committed first.
2. **Person reads `person:` only** (`src/lib/person.ts`): `getPerson` and `personFromRaw(pid, rawPerson)`; the stale guard, `fromOwner`/`fromMember` and the mirror go; `updatePerson` writes `person:` alone and stamps every owned account's `emailVerifiedAt`; `Person.source` is `"person"`.
3. **Membership reads `mbr:` only** (`src/lib/membership.ts`): `getMembership`, `membershipFromRaw(aid, pid, rawRow, listed)`; `legacyHome*` go; `heldAccounts`/`homeAccountOf`/`pickAccount` read `orgs:` only.
4. **Sessions and logins** (`src/lib/auth.ts`, `src/lib/login-finish.ts`): `resolveSession` refuses a session without `pid` (and one without `acct` resolves no account, as before); `resolveLegacy` goes; `resolveIds` reads no `user:{pid}`, `member:{pid}` or `activebrand:{email}`; `resolveInHandle` reads `orgs:` only; `sessionPerson` refuses without `pid`; `getLogin` reads the index, `person:` and `orgs:` only (a paused-only member still gets "disabled" while `MULTI_ORG` is off); `Login`'s `member` becomes `membership`; `createUser` writes no credentials on the account; `Actor.home` goes.
5. **Per-login brand and link fallbacks** (`src/lib/brands.ts`, `src/lib/feed-token.ts`, `src/lib/booking-token.ts`, `src/lib/secretary-feed.ts`, `src/lib/mcp.ts`, `src/app/api/brands/route.ts`): only `activebrand:{pid}:{aid}`, `sec:feedof:{pid}:{aid}`, `sec:bookof:{pid}:{aid}:{prov}`; a link record without `pid` is dead; revoking by address becomes revoking the person's links in each account `orgs:` names (`personLinks`).
6. **Team writes** (`src/lib/team.ts`, `src/lib/account.ts`, `src/lib/verify-email.ts`, routes that call `getMember`): no `member:` record is written or read for a decision; `writeMembership`/`deleteMembership` lose `home`; removal paths still DELETE a leftover `member:{email}` and `activebrand:{login}` (cleanup, never a read for access).
7. **Script S2** (`scripts/multi-org-contract.ts` + `tests/multi-org-contract.test.ts`), modelled on `scripts/account-ids.ts` and S1: dry run by default, `--apply`, counts only, idempotent, `pmap` 50 at a time, every write re-read under `lock:user`/`lock:member`.
8. **Tests and docs:** rewrite the M1 adapter tests to pin M4 (rule 2138), fixtures without `homeLogin`; `docs/system/tests/2110-multi-org.md` row 2138; `docs/system/tests/2760-multi-org-m4.md`; flows 93.4; architecture and permissions where they name the legacy reads.
