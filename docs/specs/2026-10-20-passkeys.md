## ملخص للمؤسس

- العميل (المالك أو العضو) يستطيع أن يضيف «مفتاح مرور» (passkey) من صفحة الأمان، ثم يدخل بضغطة زر أو من اقتراح المتصفح في خانة البريد، ببصمة الإصبع أو الوجه أو رمز قفل الجهاز. لا يُطلب رمز التحقق بخطوتين بعده، لأن المفتاح نفسه يتطلب التحقق من الشخص على الجهاز.
- كل بوابات الدخول بكلمة المرور تبقى كما هي (الإيقاف، تأكيد البريد، العضو الموقوف لعدد المقاعد، اختيار مساحة العمل، سجل الأجهزة)، لأن الدخول بالمفتاح يمر في الدالة نفسها.
- إضافة مفتاح أو حذفه تحتاج كلمة المرور (أو رمز التطبيق إن كانت الخطوتان مفعلتين)، ويصل بريد «أُضيف مفتاح مرور جديد» بالعربية أو الإنجليزية.
- الحد 10 مفاتيح للشخص. حذف آخر مفتاح مسموح، وكلمة المرور تبقى تعمل.
- مفتاح تشغيل وإيقاف في صفحة «التكاملات» في لوحة المؤسس، مفعّل افتراضياً، يحتاج سبباً ورمز الخطوة الثانية ويُكتب في السجل.

## Goal

A customer person (an owner or a member) can register up to ten WebAuthn passkeys and sign in with one instead of the password. A passkey sign-in passes through exactly the same post-proof function as the password sign-in, so every gate that refuses a password sign-in refuses a passkey sign-in too. A passkey is bound to the person (`pid` as M1 resolves it), never to an address string from the request or to a workspace, and is deleted with the person.

## Today (read on this branch, `b6c95f45`)

- Sign-in proofs are the password (`POST /api/auth/login`) and Google (`/api/auth/google/*`). Both end in `finishLogin(l, { via, next, codeDone })` (`src/lib/login-finish.ts`): `loginRefusal` (account suspension, member owner checks, unverified owner, member `disabled` for seats, person suspension), then the two-step challenge when `mfaActive` and `codeDone` is false, else `createSession(email)` (which writes `pid`/`acct` through `sessionIds` → `pickAccount` and calls `recordDevice`) and `track(account email, "login")`.
- Two-step sign-in (rules 1930-1956, flows section 80) is TOTP plus recovery codes, keyed by the login address (`mfaKeys(login)`, M1 reconciliation 8). Its setup re-checks the acting login's password with the `mfapw:{login}` bucket (10 per hour, `giveBack` on a right one).
- `actingLogin(u)` (`src/lib/own-password.ts`) gives `{ kind, pid, email, bornAt }` of the human behind the session, or null for an impersonating founder or a token. `ownPasswordMatches(u, password)` checks that login's own password. There is no customer "fresh authentication" helper; the staff console has its own (`admin-2fa` step-up, `markFreshCode`) which is not reused here.
- `appOrigin()` (`src/lib/origin.ts`) reads `APP_ORIGIN` and falls back to `https://thakeen.com`.
- Runtime switch pattern: `skills:paused` in `src/lib/instructions-store.ts` (`"1"` = paused, absent = running), flipped by `/api/admin/skills` with `adminActor` → `secondFactorRefusal` → `adminAudit`.
- No WebAuthn code and no `@simplewebauthn/*` package exist.

## Threat model

| Threat | Today | With this change |
|---|---|---|
| Phishing (a look-alike page relays the password and the TOTP code in real time) | Not addressed for customers | Closed for a person who signs in with a passkey: the browser binds the assertion to the real origin, and the server checks the origin and the RP ID taken from `appOrigin()`, never from the request (rule 2406). Not closed for the same person's password, which still works (passkey-only accounts are out of scope) |
| Password reuse or a leaked password | The password plus, when on, a TOTP code | Unchanged for the password path. A passkey holds no shared secret: the server keeps only a public key |
| A stolen session adds the attacker's passkey for lasting access | n/a | Adding needs the password (or a TOTP code when two-step is on) in the same request that opens the 5-minute registration challenge, the challenge is bound to that session (rule 2407), and the person gets a "new passkey added" email (rule 2415) |
| An impersonating founder or an MCP/API token adds or removes a passkey | n/a | `passkeys.manage` is in `IMPERSONATION_BLOCKED`; `actingLogin` is null for tokens and impersonation (rule 2412) |
| One person's credential signs in another person (cross-tenant) | n/a | The credential is looked up through a hashed reverse index, then MUST be in the forward list of that pid, and the pid MUST be what `getLogin(person.email)` resolves (rules 2405, 2419); a credential id already held by anyone is refused at registration (rule 2404). Property-tested (rule 2428) |
| A leftover passkey record of a deleted person signs in a new person at the same address (legacy pid = address) | n/a | Deletion wipes the set and its reverse entries (rule 2425); a set stamped with another birth than the person's is ignored, which also covers a rollback build that deleted the person without knowing passkeys (rule 2402) |
| Cloned authenticator | n/a | Signature counter must strictly increase when either side is above 0; a regression refuses the sign-in and writes an audit row (rule 2421) |
| Replay of a captured assertion or registration | n/a | Challenges are single-use (`getdel`) and last 5 minutes (rules 2407, 2408) |
| Account enumeration through the sign-in routes | Login answers are uniform | The options route names no person (discoverable credentials, empty `allowCredentials`); every verify failure before the person is known answers the same `passkey_failed` (rule 2423) |
| Brute force or flooding of the public routes | Login 20 per IP / 8 per address per 15 min | Options 60 per IP per 15 min; verify 20 per IP and 10 per credential per 15 min (rules 2417, 2418) |
| User verification skipped (a security key without a PIN) | n/a | `userVerification: "required"` in both option sets and a verify that refuses a response without the UV flag (rule 2409), which is why no TOTP is asked after a passkey (rule 2420) |
| A library or browser defect in WebAuthn | n/a | Runtime off switch, default on, owner-only, audited (rule 2426); passwords keep working, so switching off locks nobody out |

## Decisions (delegated by the founder, taken by the coordinator on 2026-10-20)

1. **Scope.** Customer persons only (owners and members). Staff console passkeys stay staff phase 2 (rule 1656). MCP tokens, OAuth grants and API tokens are unchanged.
2. **Library.** `@simplewebauthn/server` and `@simplewebauthn/browser`, exact versions (no `^`/`~`), each published at least 7 days before install (`.npmrc` `min-release-age=7`, rule 699). On 2026-10-20 that is `@simplewebauthn/server@14.0.3` (published 2026-09-25) and `@simplewebauthn/browser@14.0.0` (2026-09-02). The lockfile is regenerated from `package.json` alone in an empty directory with npm 11.10 or later and checked for `@rolldown/binding-linux-*` entries (CLAUDE.md). Only `src/lib/webauthn.ts` imports the server package (rule 2427).
3. **Keys.** By the person id as M1 resolves it. `passkeys:{pid}` holds the set (shape below). Reverse index `pkcred:{sha256(credentialId)}` → pid. Challenges single-use (`getdel`), 5 minutes: registration bound to the session, sign-in bound to a random cookie nonce. Every builder in `src/lib/keys.ts`; the raw-key ratchet does not rise. At most 10 passkeys per person.
4. **Sign-in.** "Sign in with a passkey" button on the log-in page plus conditional UI (`autocomplete="username webauthn"` on the address field). User verification required, so no TOTP step after a passkey. Every gate of the password path through `finishLogin` (reused, not copied). Counter regression: refused plus an audit row. Public routes rate-limited per IP and per credential.
5. **Manage.** Security settings: list, add, rename, remove. Add and remove need fresh re-authentication within 5 minutes (the password, or a TOTP code when two-step is on). Add sends a notice email (ar/en). Removing the last passkey is allowed. Locks follow rule 2139.
6. **RP ID and origin** from `appOrigin()`: RP ID = `new URL(appOrigin()).hostname`, expected origin = `appOrigin()`. No new variable.
7. **Reset and deletion.** A password reset keeps passkeys. Person deletion deletes the set, its reverse entries and any open registration challenge.
8. **Release** expand-only (rule 679).
9. **Off switch** at runtime, default on, on the `skills:paused` pattern.
10. **Copy** Arabic and English in the dictionary files; no claims; no model output.
11. **Tests** behind the seam `src/lib/webauthn.ts`, with a real-crypto ES256 test, an isolation property test, both `TEST_PERSONS` modes, and the rule 788 tests file.
12. **Docs** flows.md section 92, permissions.md, architecture.md key table; variables.md unchanged.
13. **Out of scope:** passkey-only accounts, the staff console, recovery by passkey, hybrid (cross-device) tuning beyond library defaults, M2 workspace URLs.

### Choices made inside the decisions

- **User handle.** WebAuthn needs a stable user handle (`user.id`). It is a random 32-byte value per person (`uid`), stored in the set, NOT the pid: a legacy pid is the address (personal data handed to every authenticator) and changes on an address move. Every assertion must carry a `userHandle` equal to `uid`: sign-in uses discoverable credentials (empty `allowCredentials`), where WebAuthn L3 section 7.2 requires the handle, so a missing one is refused (pre-flight ruling 7).
- **Birth stamp.** The set records `born`, the person's `createdAt` (`getPerson(pid).createdAt`) when the set was created, read the same way on the manage routes, at sign-in and in `movePasskeys` (pre-flight ruling 1: the login-level `bornAt` differs between home, membership and acting contexts, so it would disown real passkeys). A set whose `born` differs from the person's is ignored; a read never deletes it, and only adding, inside the person lock, replaces a stale set and deletes its `pkcred:` entries that still name the pid. This is what makes a rollback safe: a pre-passkey build that deletes a person does not know these keys, and a new person at the same address (same legacy pid) has another birth.
- **Fresh re-authentication without a helper.** None exists for customers, so the proof travels in the request: `register-options` takes `password` (two-step off) or `code` (two-step on), and the registration challenge it opens is the 5-minute freshness window; `remove` takes the same proof in its own request. Rename needs only the session. Wrong proofs count in the bucket `pkpw:{login}` (10 per hour, `giveBack` after a right one), the `mfapw:` pattern.
- **A Google-only person with no password and two-step off** cannot prove freshness: add and remove answer 403 `reauth_unavailable`, and the card says to set a password through "Forgot password" first. Recorded as a choice, not a deviation.
- **When the switch is off:** sign-in options and verify answer 404 `unavailable`, `register-options`/`register-verify` answer 404 `unavailable`, the log-in button and autofill are not rendered; list, rename and remove keep working (removing is always safe). Stored passkeys are untouched.
- **Counter check lives in our code.** The seam hands the library a stored counter of 0, so the library never refuses on the counter, and `counterOk(stored, next)` in `src/lib/passkeys.ts` decides (rule 2421): one place, one audit row, testable without crypto.
- **References in the UI.** The list never returns a credential id or a public key. Each entry carries `ref` = the first 16 hex characters of `sha256(credentialId)`; rename and remove match `ref` only inside the caller's own set.

## Data shapes and keys (rule 679: new keys only, no existing shape changes)

```ts
// src/lib/stored.ts, read through parseStored (z.looseObject)
const PasskeyCred = z.looseObject({
  id: z.string().regex(/^[A-Za-z0-9_-]{16,1366}$/), // credential id, base64url as the authenticator gave it
  pk: z.string().min(1).max(2048),                  // COSE public key, base64url
  counter: z.number().int().min(0),
  transports: z.array(z.string().max(20)).max(8).default([]),
  name: z.string().min(1).max(40),
  createdAt: z.string(),                            // ISO
  lastUsedAt: z.string().optional(),                // ISO, absent until first sign-in
  aaguid: z.string().max(36).default(""),
  backedUp: z.boolean().optional(),                 // shown as "synced" in the list
});
const PasskeySet = z.looseObject({
  v: z.literal(1),
  uid: z.string().regex(/^[A-Za-z0-9_-]{43}$/),     // 32 random bytes, base64url: the WebAuthn user handle
  born: z.string().optional(),                      // the person's createdAt when the set was created (rule 2402)
  creds: z.array(PasskeyCred).max(10),
});
type RegChallenge = { challenge: string; sess: string /* sha256 of currentSessionKey() */; at: number };
type AuthChallenge = { challenge: string; at: number };
```

The cookie `thakeen_pk` holds the sign-in nonce (32 random bytes, base64url): `httpOnly`, `Secure` outside loopback http (`sessionCookie`), `SameSite=Lax`, `path=/api/auth/passkey` (pre-flight ruling 19: only the two sign-in routes ever receive it; clearing it names the same path), `maxAge=300`. The nonce is never stored in clear and never logged.

`passkeys:off` cannot collide with `passkeys:{pid}`: a pid never equals `off` (an address contains `@`, a `p_` id has the prefix); the key test pins it.

## Flows

### A. Add a passkey (security settings)

1. `POST /api/account/passkeys { action: "register-options", password? , code? }`: `currentUser()` (401) → `actingLogin(u)` (null: 403 `forbidden`) → `forbid(u, "passkeys.manage")` → switch on (404 `unavailable`) → the set has fewer than 10 (409 `limit`) → proof: two-step on → `checkMfaCode(req, login, bornAt, code)`; off → password through `ownPasswordMatches`; no password and no two-step → 403 `reauth_unavailable`; bucket `pkpw:{login}` 10 per hour counts every try before the compare and gives one back after a right one (429 `slow_down`). Then: read or create the set (new `uid`, `born`), `generateRegistrationOptions` through the seam (rpID, rpName "Thakeen", `userID` = `uid`, `userName` = the login address, `userDisplayName` = the person's name, `excludeCredentials` = the set's ids, `residentKey: "required"`, `userVerification: "required"`, `attestationType: "none"`, algorithms ES256, EdDSA, RS256), store `pkreg:{pid}` = `{challenge, sess, at}` for 300 s, answer the options JSON.
2. The browser runs `startRegistration({ optionsJSON })`.
3. `POST /api/account/passkeys { action: "register-verify", response, name }`: same gates except the proof → `getdel pkreg:{pid}` (missing or older than 300 s: 410 `expired`; `sess` not this session: 410 `expired`) → `verifyRegistrationResponse` through the seam (expected challenge, origin, RP ID, `requireUserVerification: true`) → under `withPersonLock(pid)`: re-read the set, re-check the cap of 10, `SET NX pkcred:{hash}` = pid (taken: 409 `credential_taken`, nothing stored), append the credential, write the set → after the lock, send the notice email (failure logged, never undoes) → `{ ok: true, item }`.

### B. Rename, remove, list

- `GET /api/account/passkeys`: same gates as A without the proof and without the switch check; answers `{ items: [{ ref, name, createdAt, lastUsedAt?, synced, transports }], max: 10, enabled }`.
- `POST { action: "rename", ref, name }`: under the person lock, rename the entry whose `ref` matches in the caller's own set (404 `not_found` otherwise). No proof.
- `POST { action: "remove", ref, password?, code? }`: the proof of step A1 → under the person lock remove the entry, `DEL pkcred:{hash}` only when it still holds this pid, write the set. The last one may go.

### C. Sign in with a passkey

1. `POST /api/auth/passkey/options` (public): switch on (404) → `allow(pk:ip:{ip}, 60, 900)` (429) → `generateAuthenticationOptions` (rpID, `allowCredentials: []`, `userVerification: "required"`) → new nonce, `pkauth:{sha256(nonce)}` for 300 s, cookie `thakeen_pk` → options JSON. The log-in page calls it on load for conditional UI (`useBrowserAutofill: true`) when `browserSupportsWebAuthnAutofill()`, and again when the button is pressed.
2. `POST /api/auth/passkey/verify { response }` (public): read and delete the cookie first, so every outcome clears it (pre-flight ruling 8) → switch on (404) → `allow(pkv:ip:{ip}, 20, 900)` → `getdel pkauth:{sha256(nonce)}` (missing: 401 `passkey_failed`) → `hash = sha256(response.id)` → `allow(pkv:cred:{hash}, 10, 900)` → `pid = GET pkcred:{hash}` → `getPerson(storedPersonId(pid))` → `getLogin(person.email)` and `login.pid === pid` → the set is valid, its `born` equals the person's `createdAt`, it holds `response.id` → `userHandle` is present and equals `uid` (missing or different: 401 `passkey_failed`) → `verifyAuthenticationResponse` through the seam (UV required, origin, RP ID, stored counter passed as 0) → under `withPersonLock(pid)`: re-read the set, `counterOk(stored, new)` (false: audit row `passkey.counter_refused`, 401 `passkey_failed`), write `counter` and `lastUsedAt` → `finishAnswer(await finishLogin(login, { via: "passkey", codeDone: true }))`. Any failure before `finishLogin` answers 401 `passkey_failed`; a refusal from `finishLogin` keeps the password path's answer (for example 403 `suspended`).

### D. Address moves, reset, deletion

- Password reset changes `passHash` and `sessionsAfter` only; the set is untouched.
- The two address moves, `moveOwnerLogin` (`src/lib/verify-email.ts`) and `moveMemberLogin` (`src/lib/team.ts`), call `movePasskeys(fromPid, toPid, { personLocked: true })` beside their `carry` callback, with the pids they already resolved (`carryLogin` in `src/lib/email-change.ts` takes addresses, not pids, so it is not the hook; the settings address change reaches both moves). The set moves to the new pid with the same `uid` and the destination person's `createdAt` as `born` (read after the move writes the person), every `pkcred:` entry is rewritten to the new pid, the old `passkeys:` and `pkreg:` keys go. When both pids are equal (a `p_` person), or when `from` has no set and `to` already holds one with the same `uid` (a retried move after "unfinished"), nothing moves (pre-flight ruling 21). Both moves hold both person locks when they call it: `moveMemberLogin` already took them (team → login → person → member), and `moveOwnerLogin` takes `lock:person` of the old owner person and of the new address, the smaller pid first, between the two login locks and `lock:user` (rule 2139; Task 6 replaced the earlier `userLockHeld` exception, so an `addPasskey`, an `updatePerson` or a sign-in counter write of either person waits for the move; a held lock answers 409 `busy` in both routes). The call runs after `carry` and before the old pid's deletes. A resumed move whose destination person was written again between the runs re-stamps `to` with the current birth (same `uid`, same credentials). When `movePasskeys` answers `skipped` (a person could not be read; unreachable in practice, both persons are read or written just before), the move logs the reason, finishes, and keeps the old pid's passkey keys for good (`wipeAccount` with `keepPasskeys`; nothing retries the move), inert under rules 2402 and 2405. Both moves' person locks expire after 60 s, like the owner move's `lock:team`, since they span the whole move. The sign-in counter write uses `setXx` (rule 2422) so a set deleted by a move or a wipe in between is never re-created under the old pid.
- Person deletion: `passkeyKeys(pid)` (the set, every reverse entry it lists that still names the pid, `pkreg:`) is added to `wipeAccount`'s `personal` list (read in the same parallel round as the Google link, deleted only when `alone`), to `forgetPersonIfAlone` (unconditionally, not only when the login index still names the person: pre-flight ruling 6), and to the old-pid deletes of the member move (the owner move's old pid goes through `wipeAccount`).

### E. Off switch

`POST /api/admin/passkeys { on: boolean, reason }`: `adminActor(req)` (401) → `staffMay(consoleRole(req), "passkeys.switch")` (owner only, 403) → `secondFactorRefusal(req, who)` → `reasonRefused(reason)` → set or delete `passkeys:off` → `adminAudit({ actor, section: "system", action: on ? "passkeys.on" : "passkeys.off", target: "passkeys", before, after, reason })`. `GET` reads the state for the Integrations page toggle.

## Rules 2400-2429

- 2400. A passkey set is keyed only by a pid taken from our own records (`actingLogin`, the reverse index forward-checked, a move's resolved pids), through `personKey.passkeys`; never by an address, an account id or any request value; the raw-key ratchet does not rise.
- 2401. `passkeys:{pid}` parses through `PasskeySet`; a record that fails reads as "no passkeys" (fail closed) and is logged by shape only; at most 10 credentials; a name is 1-40 characters after trimming, control and bidi-override characters removed.
- 2402. A set whose `born` is not the person's `createdAt` (`getPerson(pid).createdAt`, the same on manage, sign-in and moves) is ignored for sign-in, listing and adding; a read never deletes it; only adding, inside the person lock, replaces a stale set (and deletes its `pkcred:` entries that still name the pid).
- 2403. The WebAuthn user handle is a random 32-byte `uid` per person, never the pid or the address, kept across moves; an assertion without a `userHandle`, or whose `userHandle` differs from `uid`, is refused.
- 2404. Registration writes `pkcred:{sha256(credId)}` with `SET NX`; a credential id held by any pid (this one included) answers 409 `credential_taken` and stores nothing.
- 2405. The reverse index is a hint: sign-in also needs `getPerson(pid)`, `getLogin(person.email).pid === pid` and the credential in that pid's forward set; an orphaned entry grants nothing and answers `passkey_failed`.
- 2406. RP ID is `new URL(appOrigin()).hostname` and the only accepted origin is `appOrigin()`; the request's Host, Origin or forwarded headers are never used to derive either; no new variable.
- 2407. The registration challenge `pkreg:{pid}` lives 300 s, is taken with `getdel`, and is accepted only from the session that opened it (`sha256(currentSessionKey())`); a second use, another session or a late answer is 410 `expired`.
- 2408. The sign-in challenge `pkauth:{sha256(nonce)}` lives 300 s and is taken with `getdel` by the request carrying the `thakeen_pk` cookie; the verify route reads and clears the cookie first, so it is cleared on every outcome (404 and 429 included).
- 2409. Options ask `userVerification: "required"`, registration asks `residentKey: "required"` and `attestationType: "none"`, and verification refuses a response without the UV flag or with an origin, RP ID hash or challenge that does not match.
- 2410. `register-options` needs the acting login's password (two-step off) or a TOTP or recovery code (two-step on); every try counts in `pkpw:{login}` (10 per hour), a right one is given back; the 5-minute challenge is the freshness window.
- 2411. `remove` needs the same proof in its own request; `rename` needs only the session; a person with no password and two-step off gets 403 `reauth_unavailable` for add and remove.
- 2412. The manage routes run `currentUser()` → `actingLogin(u)` → `passkeys.manage` (member-level, in `IMPERSONATION_BLOCKED`); an impersonating founder, an MCP or API token, or a session without an acting login gets 401/403 and never reads or writes a set.
- 2413. The list answers `ref`, name, dates, `synced` and transports only, never a credential id or public key; `ref` is matched only inside the caller's own set.
- 2414. Every write to `passkeys:{pid}` and `pkcred:` happens under `lock:person:{pid}` with the set re-read inside the lock, except the wipe deletes (both address moves hold both person locks, taken in rule 2139's order, with a 60 s expiry); a lock timeout answers 409 `busy`; no person lock is taken out of rule 2139's order (the owner move's `lock:team` after `lock:user` is multi-workspace M1's documented exception, not a person lock).
- 2415. A successful add sends one notice email in the person's language (ar/en) through `sendEmail` with the `notice` template, naming the passkey and the time and pointing to Security settings; no credential data; a mail failure never undoes the add.
- 2416. Removing the last passkey is allowed and leaves password sign-in working; a remove deletes the forward entry and its reverse entry (only if it still names this pid).
- 2417. `POST /api/auth/passkey/options` is public, answers 404 `unavailable` when the switch is off, is limited to 60 per IP per 15 minutes, and names no person (`allowCredentials` empty).
- 2418. `POST /api/auth/passkey/verify` is limited to 20 per IP and 10 per credential hash per 15 minutes, both counted before any person is read.
- 2419. A passkey sign-in ends in `finishLogin(login, { via: "passkey", codeDone: true })` with `login` from `getLogin(person.email)`, so every refusal, the account pick, the device record, the session ids and the login count of the password path apply unchanged.
- 2420. No two-step code is asked after a passkey; `finishLogin`'s `via` accepts `"passkey"` and no two-step challenge record is ever written with it.
- 2421. When the stored or the new counter is above 0 the new one must be strictly greater; otherwise the sign-in is refused, the counter is not written, and an `adminAudit` row (actor `system`, section `users`, action `passkey.counter_refused`, target the person's address, before/after counters and an 8-hex hash, never the credential id) is written.
- 2422. The new counter and `lastUsedAt` are written under the person lock with `setXx` (a set deleted in between is never re-created) before `finishLogin` runs.
- 2423. Every verify failure before `finishLogin` (no challenge, unknown or orphaned credential, wrong signature, user handle, birth, counter) answers the same 401 `passkey_failed`.
- 2424. A password reset keeps passkeys; an address move or carry moves the set to the new pid with the same `uid`, rewrites every reverse entry and leaves no key under the old pid.
- 2425. Every person wipe (account deletion, `wipeAccount` when alone, `forgetPersonIfAlone`, the old pid of a move) deletes `passkeys:{pid}`, every `pkcred:` it lists that still names the pid (read in one parallel round, so a wipe never removes another person's reverse entry; pre-flight ruling 22) and `pkreg:{pid}`.
- 2426. `passkeys:off` = `"1"` turns off sign-in and adding (404 `unavailable`, button and autofill hidden) and keeps list, rename and remove; only a console owner flips it, with the second factor, a reason and an audit row in section `system`.
- 2427. Only `src/lib/webauthn.ts` imports `@simplewebauthn/server`, only client components import `@simplewebauthn/browser`, and both are pinned to exact versions in `package.json`.
- 2428. Across random persons and credentials, one person's passkey never signs in another person, and a credential id registered by a second person is refused (isolation property test, both `TEST_PERSONS` modes).
- 2429. Every passkey string is in the Arabic and English dictionaries, makes no claim beyond what the code does, involves no model output, and the add button is not rendered when the browser has no WebAuthn (the card still lists, renames and removes, with a line saying this browser cannot add a passkey; corrected 2026-10-20 in Task 4 so a lost device's passkey can be removed from any browser).

## Release step

**Expand** (rule 679), one release. Everything is new keys and new routes; no existing stored shape changes (`finishLogin`'s `via` is a parameter, not a stored value). Old builds ignore every new key. Rollback to any earlier build is safe: passkey users still have their password (passkey-only accounts are out of scope), the old build simply shows no passkey UI, and a person it deletes leaves a set that rule 2402 ignores and the reverse index cannot use (rule 2405). No contract step and no conversion script. The release pull request names the step "expand".
